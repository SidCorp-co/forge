+ comments, memory, jobs, runners, projects, config, knowledge, metrics…		 → adapter mỏng gọi REST, hoặc xoá hẳn khi CLI đã phủ Xong — ISS-889 §3, 2026-08-31: không tool nào trong mcp/tools/ còn giữ handle DB; mỗi truy vấn đã về một service dưới domain của nó, và no-transport-db.test.ts giữ bất biến đó. Việc trích ra làm lộ bốn chỗ hai transport đã lệch nhau: cột list của agent-session, tập status chiếm slot runner, filter orphan, và 23505 slug-hay-apiKey. Đo lại 2026-09-01 bằng cách liệt kê 107 route mount trong index.ts (không phải bằng import chung, vì db/schema thì file nào cũng import): khoảng trống REST thật chỉ còn 4 — forge_divergence_charters, forge_ux_improver, forge_ops_health, forge_version. Con số "~12" trước đó là nhiễu của phép đo sai.
✕ Hai đường create viết tay → issues/create-service.ts — đã trích, cả hai transport dùng chung Cả hai bên đều insert(issues) nội tuyến: REST ở issues/routes.ts trong một db.transaction, MCP ở mcp/tools/forge-issues.ts. issues/creator.ts không phải đường create — nó là attribution (hydrateCreatorsForIssues, buildOriginCondition, isAgentChannel), không có hàm create nào. Là gốc của bug "create mặc định open, không lùi về draft".
✕ X-Total-Count header → lib/pagination.ts — envelope đã lên, header còn lại là bản sao tương thích Hai hợp đồng "đã đủ chưa" khác nhau: REST trả header, MCP trả {returned, hasMore, truncated}. CLI dùng REST sẽ thừa hưởng cái yếu hơn — trừ khi REST lên envelope trước.
✕ Quan hệ blocks nguyên tử chỉ có ở MCP → REST nhận relations ngay trong transaction của create/update REST đã đặt được blocks — issues/dependency-routes.ts có GET/POST/DELETE /api/issues/:id/dependencies, và mcp/tools/issue-relations.ts có cm:edge contract trỏ về nó. Khoảng trống thật hẹp hơn: chỉ MCP commit được edge trước khi issueCreated phát ra. Đó đúng là race mà red flag open-then-block nói tới.
✕ Không có hợp đồng lỗi → taxonomy → exit code, in trong --help, retryable trong JSON stderr Forge đã phân loại server-side (failureKind/failureAction). CLI chỉ phơi ra, không phát minh lại.

Buzz giữ đúng 5 MCP tool bên cạnh một CLI 22k dòng. Con số tương ứng của Forge là ~6, không phải 45.

Đã kiểm và BỎ — ba chỗ trông như lệch nhưng không phải, đừng vẽ thành mũi tên:
· sanitize chỉ ở MCP → là thiết kế. forge-issues.ts:365 có cm:guard: "REST/web-v2 serialize separately, so the human UI never shows the framing."
· apply-transition chỉ ở MCP → chỉ là bố cục file; REST chạm nó qua issues/transition.ts mount riêng.
· dispatch-tick chỉ ở MCP → cả hai đều bắn hook issueCreated; MCP chỉ tick thêm trực tiếp.

Thứ tự làm — REST phải lên trước

BướcRàng buộc
0Nâng REST lên ngang MCPXong (ISS-889 §1–§2): issues/create-service.ts dùng chung, relations nguyên tử cùng transaction với create, và lib/pagination.ts trả envelope trong body.
1MCP tool → adapter mỏng trên RESTXong (ISS-889 §3): drizzle đã ra khỏi mcp/tools/ — nhưng thành adapter trên service dùng chung, không phải gọi REST qua HTTP. Test cũ là lưới an toàn đúng như dự đoán; chỗ nào assertion chỉ còn soi mock thì bị thay bằng integration test trên Postgres thật.
2CLI trên cùng REST đóMỏng. Chuẩn hoá ở tầng transport, subcommand chỉ in — như buzz.
0bREST nhận PATXong 2026-09-01: requireAuth nhận PAT, hai tầng. Tầng 1 — allowlist PAT_ALLOWED_PREFIXES (middleware/pat-rest-surface.ts): route nào không resolve project thì từ chối thẳng, vì không có gì cho hàng rào cắn vào; allowlist chứ không phải deny-list, quên một dòng thì mất quyền (có người báo) chứ không phải rò (không ai báo). Tầng 2 — AsyncLocalStorage mang project ids hiệu lực của token, effectiveProjectRole đọc: một chỗ đọc, rào 228 call site, trả đúng null mà project không tồn tại trả về nên không dùng token dò được id thật. Scope theo method: GET/HEAD/OPTIONS cần read, còn lại write. Các endpoint liệt kê phải rào riêng vì chúng không nêu tên project nào — loadVisibleProjectIds và projection rộng hơn mà GET /api/projects tự viết nay dùng chung một predicate.

Đo lại: PAT bound project A → /api/projects/A 200, /api/projects/B 404, /api/issues/<issue của B> 404 (project resolve gián tiếp từ issue row — case mà middleware đọc :projectId sẽ trượt), /api/pat 403. Sweep duyệt toàn bộ app.routes: tắt thử tầng 1 thì nó gọi tên 12 route sẽ rò, /api/pat, /api/me/attention, /api/admin/whoami trong đó.

Không phải "82 file cần sửa" như đề xuất này viết trước đó: đúng một file requireAuth và đúng một choke point authz, không route module nào phải đổi.
0cCLI cầm PATXong 2026-09-01: forge-runner api dùng PAT chứ không phải device token — device token nêu tên một cái máy, mà REST rào theo project mà credential được phép nói thay. login --pat lưu cạnh device token (read-modify-write, không đạp lên nhau), $FORGE_PAT thắng bản lưu, doctor báo có/không.
3forge api <path>Xong 2026-09-01: forge-runner api (packages/runner/crates/forge-runner-core/src/api/) — taxonomy status → exit code, retryable dạng JSON trên stderr, body lỗi không bao giờ ra stdout. Đặt trong binary runner chứ không phải package TS mới: nó đã có trên mọi máy fleet, đã tự update, đã cầm core_url + device token. Chính nó là thứ đo ra bước 0b ở trên.
4Xoá MCP tool đã được CLI phủXoá thật, không deprecate. Còn hai đường là còn hai đường. Không có đống xoá miễn phí: server.ts đăng ký 69 tool từ 46 module, và các module forge-pm-* trông như shim ISS-145 thật ra vẫn là handler sống mà forge_project_pm gọi lại — xoá file là hỏng dispatcher. Chỉ hai registration còn dư (forge_pipeline_runs_get ← forge-skill-audit, forge_pm_set_dependency ← forge-plan), mỗi cái xoá được sau khi skill gọi tên nó chuyển đi.
Bước 0b đã mở. Mặt phẳng REST nay trả lời một PAT, có rào theo project, nên bước 2 dựng được như một cái thay thế MCP chứ không phải một cái bổ sung. Bước 4 vẫn chưa xoá được gì: xoá một tool MCP chỉ an toàn khi mọi skill gọi nó đã chuyển sang forge-runner api và chạy xanh — 31/69 tool đang được ít nhất một trong 245 skill body gọi tên.

Bước 0 là chỗ dễ bỏ qua nhất và là chỗ hỏng đắt nhất. Không phải vì REST thiếu blocks — nó có endpoint rồi — mà vì REST chưa đặt được edge trong cùng transaction với create, nên một CLI dựng trên nó chỉ tái hiện được đúng cái race open-then-block.

Honest costs

Trả bằng gìCụ thể
Một client thứ hai phải giữ đồng bộ Buzz gánh nổi 22k dòng CLI vì relay nói một giao thức event ổn định. Bề mặt REST của Forge đổi nhanh hơn. forge api giảm chứ không xoá được khoản này.
Một giai đoạn hồi quy có thật Giữa bước 1 và bước 4 tồn tại cả MCP adapter lẫn CLI. Đúng cái "hai đường sống" mà đề xuất này nói là phải diệt — chỉ chấp nhận được vì nó có hạn, và hạn đó là bước 4.
Viết lại test, không phải chỉ chuyển code Đã trả (ISS-889 §3): test của mcp/tools/*.test.ts test drizzle-qua-tool, nên khi tool thành adapter chúng test nhầm tầng. Chỗ nào chỉ cần đổi hình mock thì đổi; chỗ nào assertion đã thôi đo gì (soi một truy vấn đã chuyển đi) thì xoá và dựng lại thành integration test trên Postgres thật.
Bước 0 không sinh ra giá trị nhìn thấy được Nâng REST lên ngang MCP không cho người dùng thêm thứ gì. Nó là điều kiện cần thuần tuý, và vì thế là bước dễ bị cắt nhất khi hết kiên nhẫn.
Mất tính năng nếu làm sai thứ tự REST đặt được blocks qua endpoint riêng, nhưng chưa nguyên tử với create. Đảo thứ tự ⇒ CLI đẻ ra đúng race open-then-block, mà blocks là thứ duy nhất chặn dispatch.
