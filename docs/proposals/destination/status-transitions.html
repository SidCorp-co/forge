Fourteen statuses, and which hops are legal

advisory — nothing refuses a hop today
  • the one status that dispatches
  • rung — a party owes a move
  • park — a person owes a move
  • end
  • conditional on the project
  • rejection path

One dispatch door (open), a reading rung and a plan rung, one worker, two rungs where a proof is owed then run, one gate a person holds, one release middle, two ends that differ only in whether merged_at is stamped. A rung earns its place when a different party owes the next move at it — the owner's test, 2026-09-10. confirmed and approved failed it under a single-driver pipeline and pass it under the wave model, where triage and execution are different runs (ISS-976).

  • closednobody · stamps merged_at
  • droppednobody · no stamp

Claims nothing about evidence

A status says which gate the work sits at, never that code exists. The evidence fields are merged_at, sessionContext.branch and the handoff's commitSha — read those (pipeline/status-assertions.ts, ISS-940).

Where it goes wrong

GapWhereWhat it costs
Nothing refuses a hopcanTransitionFreeRefuses two things: draft as a target, and a draft leaving outside DRAFT_EXIT_TARGETS. releasing → open and closed → in_progress both succeed, and the map that would call them illegal is read only by prompt generation and the UI picker
A park forgets the rung it leftpipeline/answer-resume.tsSends an answered needs_info to open unconditionally — a park taken at awaiting_release is merged work, and open races a fresh agent onto shipped code. Making the table the gate cannot land until a park records its origin
Rows stranded on retired statuses31 rows · 10 projectsMeasured 2026-09-11 (433 on 09-09). sid-desk 9, codemap 6, sidpeak 5 — sidpeak's five sit at approved, three critical and already merged, while its config names no approved. Half fixed: the rung is pool-admissible again, but each project must declare it in poolBacklog.statuses
An aborted release waits foreverreleasing → reopenDeliberately no self-heal — a failed release re-driven automatically is how a half-landed batch becomes two. The cost: an unwatched fleet accumulates aborted releases at reopen
Neither new rung is a driver statusBACKLOG_ADMISSIBLE_STATUSESOn purpose — the set is issueStatuses minus AUTONOMOUS_DRIVER_STATUSES, so adding them takes them OFF the backlog menu, which is how a dead session at either rung is recovered. It would also stop every project naming them: an inadmissible element answers invalid_value for the whole config — cfg = null, no dispatch, in silence

Do not

Do notBecause
Force a project with no release gate through releasingresolveReleaseGate returns null for most projects; inventing a release step they do not have is what in_progress → closed exists to avoid
Let anything but finish and abort write out of releasingThey own the outcome edges. An agent that could leave it would be declaring its own release finished — the guard release-gate-hold.ts was written from, after epodsystem ISS-141 self-closed with the reported bug still reproducing
Send reopen to openA reopened issue has a branch and a worktree; offering it to the pool races a fresh agent against the tree that already exists
Rename a status without moving its pipelineConfig.states keyzod answers invalid_key, the config parses to null, and the project stops dispatching with nothing reporting it — measured on 29 configs before migration 0228 moved them in the same transaction
Drain a retired status before its writers are refusedThe writers refill it behind you. The order is freeze, then drain, then enforce
Read a rung as evidence that code existsA status says which gate the work sits at and nothing else (status-assertions.ts). Four runs on 2026-09-06 reached one state and recorded four different statuses because the promise was undefined (ISS-940)
