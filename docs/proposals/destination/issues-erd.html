3b · Removing jobs and pipeline_runs — what actually goes

jobs is the staged pipeline's unit of execution, and the staged pipeline is gone. What rides on it splits cleanly in two: the machinery that only existed to run staged jobs goes with them, and the lanes that merely used jobs as transport move onto agent_sessions + a claim. Nothing here is an open question.

Not removed, and not the same thing: pipeline_outbox. It is a trigger on issues.status that wakes the masters — propagation, not execution. It predates the staged lane in purpose and outlives it: under master → subagent it is the only thing that turns a status write into work starting.

The one thing that must not be lost: ISS-923 measured 98 of 114 runs stuck running with every job terminal. That invariant lives in runs-cascade.ts, runs-concluded.ts and loop-monitor.ts. Removing both tables removes the bug and the defence together — which is correct only if nothing can enter that state again. The claim lease is what has to make that true, and it has to be shown doing it before these tables come out.

4 · issue_claims, in full

issue_claims
  id           uuid  PRIMARY KEY
  issue_id     uuid  NOT NULL  REFERENCES issues(id)   ON DELETE CASCADE
  project_id   uuid  NOT NULL  REFERENCES projects(id) ON DELETE CASCADE
  claimed_by   uuid            -- the agent_session holding it; SET NULL, never the authority
  device_id    uuid
  claimed_at   timestamptz NOT NULL DEFAULT now()
  expires_at   timestamptz NOT NULL
  released_at  timestamptz
  release_reason text          -- done | handed back | lease expired | cancelled

  UNIQUE (issue_id) WHERE released_at IS NULL
  INDEX  (issue_id, claimed_at DESC)

Claiming is one transaction, and the database writes the refusal:

UPDATE issue_claims SET released_at = now(), release_reason = 'lease expired'
 WHERE issue_id = $issue AND released_at IS NULL AND expires_at < now();

INSERT INTO issue_claims (issue_id, project_id, claimed_by, expires_at) VALUES (…);
-- a live claim survives the UPDATE, so this INSERT hits the partial unique and is refused

The time test cannot live in the index, so it lives here: an expired claim is reaped by the next claimant, in the same transaction that replaces it. A background sweeper becomes hygiene for rows nobody comes back for — not the thing correctness rests on. release_reason is what separates finished from gave up from the box died, which is the question the run-session reaper could never answer.

What the table owes, being a table: a reader. Claim history with no consumer is kernel_transitions again — 1 writer, 0 readers, kept alive only by the sweep that deletes it. Name the surface that reads it (how long issues wait, which box abandons work, how often a lease expires) or the history is weight.

5 · The one thing being lost, said plainly

tasks carried assignee_id, priority and sort_order — a checklist that could be handed to a named person and ordered. issues.plan is free text and cannot do that; the todos block does not survive the session. If any rows use those three columns, this is a feature being withdrawn, not dead weight, and the migration says so by counting them.
