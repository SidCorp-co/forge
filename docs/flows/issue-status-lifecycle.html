issue-status-lifecycle — twelve statuses, and which hops are legal

What an issue may be, and where it may go from there. Decided by the owner 2026-09-09 and 2026-09-10, replacing a seventeen-status enum whose retired ladder still held rows. The table below is the target: every hop absent from it is refused. Today it is not — canTransitionFree permits any non-draft hop to any non-draft status, which is the gap this flow exists to close.

One dispatch door (open), one worker (in_progress), two rungs where a proof is owed and then run (developed, testing), one gate a person holds (awaiting_release), one release middle (releasing), two parks reachable from every live rung, one park a person routes (reopen), and two ends differing only in whether merged_at is stamped.

Why developed and testing are rungs and the other four are not. Added 2026-09-10 by the owner. A rung earns its place when a different party owes the next move at it: at developed the code exists and a reviewer owes a verdict; at testing the proof is running and a tester owes a result. confirmed, clarified, approved and tested never did that — each only recorded that a phase inside one session had finished, which the handoff already says, so the issue stood there waiting for nobody. A rejection at either rung goes to reopen rather than down the ladder, so the count of rejections stays readable in one place (isReopenEntry).

Neither is an autonomous driver status, on purpose. BACKLOG_ADMISSIBLE_STATUSES is issueStatuses minus AUTONOMOUS_DRIVER_STATUSES, so adding them there would take them OFF the backlog menu — and the backlog is exactly how a dead session at either rung is recovered: the next master can claim the work where it stands. It would also stop the dispatcher on every project whose poolBacklog.statuses names them: measured 2026-09-10, an inadmissible element answers invalid_value for the whole pipelineConfig, so cfg = null, isAutonomous is false, and that project silently dispatches nothing.

Why the gate is a status and the trigger is a button. The old lane had no button, so moving an issue to released was how a release started — a trigger standing in for an action, and a name in the past tense for a thing that had not happened. Splitting the two gives each half an honest name: awaiting_release is where the work waits, the RELEASE button is the action, and releasing is the middle while a batch runs. Renamed from released in migration 0228; the board has called this rung awaiting_release since ISS-970, so only the kernel status was ever lying.

A park resumes onto the rung it LEFT, not onto open. Corrected 2026-09-10: the first version of this matrix gave on_hold and needs_info a single exit to open, and that is wrong for a park taken at awaiting_release — an issue merged and waiting for production, parked and then answered, would be pushed back into the dispatch queue, racing a fresh agent onto shipped work and losing its place at the gate. The parks therefore exit to open, in_progress AND awaiting_release. The live defect this exposes: pipeline/answer-resume.ts sends an answered needs_info to AUTONOMOUS_ENTRY_STATUS = open unconditionally, because nothing records the rung a park left. That is harmless only while this table is advice. Step 5 (making the table the gate) cannot land until a park records where it came from.
Both parks are enterable from every rung, and from each other. This is what prompt/facts/registry.ts already tells agents — “From ANY state you may set needs_info … on_hold … don't force the ladder” — so the instruction was right and the map was the narrow half. Two exclusions, each with a reason: draft cannot park because it already is a resting place (DRAFT_EXIT_TARGETS is the one existing real gate), and closed/ dropped cannot park because a park after an end is a reopen, which closed → reopen already is.

Where it goes wrong

Nothing refuses a hop today. pipeline/state-machine.ts:transitions holds a map over every enum member, retired ones included, and its own first guard says “ADVISORY, NOT A GATE. Nothing enforces this map”. The one runtime check is canTransitionFree, which refuses exactly two things: draft as a target, and a draft leaving to anything outside DRAFT_EXIT_TARGETS. So releasing → open or closed → in_progress are permitted, and the map that would call them illegal is read by prompt generation and the UI's next-state picker — a retired ladder teaching itself to agents and operators.
A status whose meaning left and whose rows stayed has no way out. Measured 2026-09-09: 433 rows sit on statuses the kernel does not drive. Sidpeak holds five issues at approved while that project's config has no approved entry at all — no pool offers it, no stage accepts it, so those five cannot move by machine. Three are critical and already merged. Four more enum members (confirmed, clarified, testing, reopen) hold zero rows anywhere while still appearing in 33 source files.
FIXED — one status used to mean two things during a release. The issue stood at released for the whole batch and the in-flight fact lived only in issues.release_batch_run_id, so the status read as both waiting for a person to press it and being released right now. 16 release_batch jobs have run — 4 failed and 2 cancelled — which are exactly the cases where the two meanings diverge. releasing is now the middle (migration 0227), awaiting_release is the waiting rung (0228), and a batch that ends without either outcome hands its issues to reopen rather than leaving them mid-release.
A gate is not a trigger, and a name in the past tense is not a place to wait. released was BOTH: the old lane had no release button, so moving an issue to that status was how a release started. That is why the status could not be renamed without also building the button — and why the board had already been calling this rung awaiting_release since ISS-970 while the column said something that was not true. The rename in 0228 also had to move states.released on 29 project configs: pipelineConfig.states is a partialRecord(z.enum(STAGE_NAMES)) and zod 4 answers invalid_key rather than stripping, and a config that fails to parse reads as cfg = null — isAutonomous false, no dispatch, in silence.

It is the only status carrying a second column — waitingKind — with a refusal family around it (WAITING_KIND_REQUIRED, WAITING_KIND_NOT_APPLICABLE) named by code in guides/registry.ts and prompt/facts/registry.ts, which is text an agent reads. Of the six, five are real external dependencies: an unpublished npm package, two people, unmeasured production data, and a GitLab push credential the runner does not have. No amount of deciding produces a push credential, so whether needs_info inherits the kind is the open question, and five rows need re-parking by hand either way.

Why reopen stays, and its rewrite goes

issues/autonomous-park.ts rewrites reopen → open for every actor on an autonomous project. It was written from an incident — epodsystem ISS-141 sat at reopen for over an hour on 2026-08-24, rendering as a live session while the reconciler re-read it every 60s and counted a rescue each time — and its stated reason is a claim about meaning: the staged pipeline read reopen as “a step rejected this”, and the autonomous driver has no steps.

This vocabulary changes that meaning. reopen names a person disagreed with a close, and a person routes what follows — not a step. Three readers measured 2026-09-10 say the wedge cannot return through this door:

ReaderWhat it does with reopen
pipeline/reconciler.ts:183selects AUTONOMOUS_INFLIGHT_STATUSES, which resolves to ['in_progress'] — the every-60s pass that counted ISS-141's rescues does not read reopen at all
notifications/notify-transitions.ts:41already classes it in PROBLEM_STATUSES — “a person is needed”, with an auto-resolve key. The same reading this vocabulary gives it
me/attention-buckets.ts:100NEEDS_REVIEW_STATUSES = ['developed', 'reopen'] — surfaced to a human, never to a dispatcher

Two already agree and the third does not read it, so the rewrite is now the only thing asserting the old meaning. It holds 0 rows across 28 projects, so nothing is stranded either way. Cost: releasing → reopen does not self-heal — a failed release parks for a person and stays there. That is the right trade for a half-landed batch, but a fleet nobody watches accumulates aborted releases at reopen.

Do not

Force a project with no release gate through releasing — resolveReleaseGate returns null for most projects, and inventing a release step they do not have is what in_progress → closed exists to avoid. Let anything but finish and abort write out of releasing: they own the outcome edges, and an agent that could leave it would be declaring its own release finished — the guard release-gate-hold.ts was written from, after epodsystem ISS-141 self-closed with the reported bug still reproducing. Send reopen to open: a reopened issue has a branch and a worktree, and offering it to the pool races a fresh agent against the tree that already exists. Rename a status in the enum without also moving its pipelineConfig.states key: zod answers invalid_key, the config parses to null, and the project stops dispatching with nothing reporting it (measured on 29 configs before migration 0228 moved them in the same transaction). Drain the retired statuses before their writers are refused — the writers refill them, which is why the order is freeze, then drain, then enforce.
