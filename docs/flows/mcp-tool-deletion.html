mcp-tool-deletion — a tool leaves the registry, or is refused by name

The decision path one MCP tool walks on its way out of REGISTERED_TOOLS, after ISS-931 left /mcp with a single credential species. Owner: packages/core/src/mcp/registered-tools.ts, packages/core/src/mcp/server.ts, packages/core/src/middleware/require-pat.ts. The rule in prose: docs/architecture/agent-surface.md.

Why this flow changed shape

Until ISS-931 the gate was one number: a tool was clear when its mcp_audit_log device count was zero. ISS-931 did not make that number meaningless — it changed what it is a statement about. requirePat refuses a device, so no new device rows are written and the counts stop rising; but the sessions behind them are paused, not retired. A box installs a runner-v* that writes the job token and the same Claude MCP client resumes against the same tool list, on a PAT.

So a non-zero device count is a forecast of returning traffic, not a record of dead traffic, and it stays a refusal. What genuinely went obsolete is the rule's second clause: it asked for a replacement route that accepts a device token, and every caller that comes back holds a forge_pat_* instead.

Two things this page previously got wrong about that are worth stating, because both are easy to re-derive. The counts do not fall because of ISS-931 — they could not fall before it either, since mcp_audit_log declares 90-day retention and nothing calls enforceMcpAuditRetention. And wiring that pruner would drain every device count to zero, which must not be read as clearing twenty tools at once: the refusal is about callers who return, not rows that expire.

The question therefore moved from who called this to who will lose it, and there are three populations rather than one.

Rule 2 is a version, and it is readable from a box

The forge CLI is built in forge-plugin, not here, so this repo cannot see which tools it names. ISS-508 moved every verb to a path under /api; the fleet has not installed that build. The copy on a runner box is the authority, and it is a directory you can grep:

~/.config/forge-runner/marketplaces/sidcorp-co__forge-plugin/plugin — version 3.35.140, carrying src/tracker/rpc.mjs and no src/tracker/rest.mjs. When rest.mjs is present on every box, the wrapped verbs are discharged together. That is the observable end state for them, and it is a file rather than an issue. It does not cover forge call, the raw tools/call passthrough whose purpose is the tools no verb wraps — whether 3.35.141+ still ships it against /mcp is not knowable from this repo, and guessing is what the forge-plugin carve-out exists to prevent.

This CLI holds a forge_pat_prd_* — a PAT, not a device token — so requirePat admits it. ISS-931 did not take its access away, and its calls land as token_id traffic that a device split cannot see. The nine, with the call site in the installed copy:

forge_memory.search, forge_projects.get and forge_projects.list were all filed free to go until this was measured, and forge_projects.create was listed as blocked with zero call sites in the installed copy.

What deleting one costs differs per call site, and only one of the three is a hard break. callTool (src/tracker/rpc.mjs:189) returns a refusal object instead of exiting when its soft flag is set. forge_projects.list is reached through idOfProject(false) — not soft — so it exits: that one is the 7f0c5a56 shape, where six tools went on a bad measurement and the fleet read not_found the same day. forge_memory.search degrades to a note (neighbours.mjs returns {hits: [], note: …}) and forge_projects.get degrades to null. A silent degradation is still a caller losing a capability — that is the reason to refuse, not a reason to discount it — but the blast radius is "recall quietly stops working" rather than "every command exits", and a rule whose stated cost is overstated is one a reader eventually stops trusting.

Rule 3 has a source the database does not hold

forge_memory.search has a second live caller that no audit query would have surfaced: packages/runner/crates/forge-runner-core/src/workspace/orientation.rs writes "Recall memory FIRST — forge_memory_search({...})" into every project workspace's orientation. Every agent on every box is told to call it by name, in text this repo ships. Grep the runner's bundled prose as well as the tables.

Rule 3 cannot be finished from a runner box. It needs whole-table mcp_audit_log counts, and the only route over that table is GET /api/pat/:id/audit — one token, last-N rows — with /api/pat off PAT_ALLOWED_PREFIXES by design. An agent session that reaches this node stops and does not estimate. ISS-946 decides whether the fence grows a read-only aggregate or the rule stops being written against a number no agent can read.

What refuses, and what must never happen instead

NodeRefusalThe failure it exists to prevent
rule 2blocked on a fleet upgrade Deleting a tool the fleet's CLI names. The caller does not degrade — it reads not_found mid-run, on a box nobody is watching
rule 3name the caller Widening a filter, or keeping the tool quietly registered. Both leave two live paths, which is the condition this whole shrink exists to remove
rule 3, unmeasurablestop, do not estimate A green that means nothing. The runtime could not represent the failure, so a pass is not weak evidence — it is none
replacement twinwrong middleware /api/skill-facts: forge_skill_facts.get had 23 callers and requireAuth() answered them 401. A mounted route is not a reachable one

One thing the deletion cannot honour, and the commit says so rather than pretending otherwise: three cm:guards in mcp/server.ts record that callers pin to tools/list order. Those guards govern insertion — a new tool is appended, not spliced in. A deletion shifts every index below it and there is no position that leaves the tail where it was. A caller that pins by index is already broken.
