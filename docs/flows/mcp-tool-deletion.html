mcp-tool-deletion — a tool leaves the registry, or is refused by name

The decision path one MCP tool walks on its way out of REGISTERED_TOOLS, after ISS-931 left /mcp with a single credential species. Owner: packages/core/src/mcp/registered-tools.ts, packages/core/src/mcp/server.ts, packages/core/src/middleware/require-pat.ts. The rule in prose: docs/architecture/agent-surface.md.

Why this flow changed shape

Until ISS-931 the gate was one number: a tool was clear when its mcp_audit_log device count was zero. That number no longer moves. mcp/server.ts stamps device_id NULL on every row it writes, so every tool's device count is frozen at whatever it reached — and the clause that number fed asked whether the callers a tool had could reach its replacement. Those callers are un-upgraded runner boxes, which requirePat now answers 401 on every /mcp call, whatever is registered. A gate keyed on a number that can never fall, protecting a population the same change already made unreachable, never opens. The shrink would not have been blocked under it; it would have been unable to finish.

So the question moved from who called this to who can still call this. There are exactly two answers, and only one of them is in the database.

Half 1 is a version, and it is readable from a box

The forge CLI is built in forge-plugin, not here, so this repo cannot see which tools it names. ISS-508 moved every verb to a path under /api; the fleet has not installed that build. The copy on a runner box is the authority, and it is a directory you can grep:

~/.config/forge-runner/marketplaces/sidcorp-co__forge-plugin/plugin — version 3.35.140, carrying src/tracker/rpc.mjs and no src/tracker/rest.mjs. When rest.mjs is present on every box, half 1 is discharged for all nine tools at once. That is the observable end state; there is no issue to wait on.

This CLI holds a forge_pat_prd_* — a PAT, not a device token — so requirePat admits it. ISS-931 did not take its access away, and its calls land as token_id traffic that a device split cannot see. The nine, with the call site in the installed copy:

The last three were filed free to go until this was measured, and forge_projects.create was listed as blocked with zero call sites in the installed copy. Deleting forge_memory.search on the old list would have broken every box's forge — the 7f0c5a56 shape, where six tools went on a bad measurement and the fleet read not_found at 09:07 the same day.

Half 2 has a source the database does not hold

forge_memory.search has a second live caller that no audit query would have surfaced: packages/runner/crates/forge-runner-core/src/workspace/orientation.rs writes "Recall memory FIRST — forge_memory_search({...})" into every project workspace's orientation. Every agent on every box is told to call it by name, in text this repo ships. Grep the runner's bundled prose as well as the tables.

Half 2 cannot be finished from a runner box. It needs whole-table mcp_audit_log counts, and the only route over that table is GET /api/pat/:id/audit — one token, last-N rows — with /api/pat off PAT_ALLOWED_PREFIXES by design. An agent session that reaches this node stops and does not estimate. ISS-946 decides whether the fence grows a read-only aggregate or the rule stops being written against a number no agent can read.

What refuses, and what must never happen instead

NodeRefusalThe failure it exists to prevent
half 1blocked on a fleet upgrade Deleting a tool the fleet's CLI names. The caller does not degrade — it reads not_found mid-run, on a box nobody is watching
half 2name the caller Widening a filter, or keeping the tool quietly registered. Both leave two live paths, which is the condition this whole shrink exists to remove
half 2, unmeasurablestop, do not estimate A green that means nothing. The runtime could not represent the failure, so a pass is not weak evidence — it is none
replacement twinwrong middleware /api/skill-facts: forge_skill_facts.get had 23 callers and requireAuth() answered them 401. A mounted route is not a reachable one

One thing the deletion cannot honour, and the commit says so rather than pretending otherwise: three cm:guards in mcp/server.ts record that callers pin to tools/list order. Those guards govern insertion — a new tool is appended, not spliced in. A deletion shifts every index below it and there is no position that leaves the tail where it was. A caller that pins by index is already broken.
