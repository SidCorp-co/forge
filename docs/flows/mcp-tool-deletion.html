Since ISS-931 the device count is a forecast of returning traffic, not a record of dead traffic: requirePat refuses a device, so the counts stop rising while the sessions behind them are paused — a box installs a runner-v* and the same client resumes on a PAT. The counts could never fall anyway (mcp_audit_log declares 90-day retention and nothing calls enforceMcpAuditRetention); wiring that pruner would drain every device count to zero and must not be read as clearing twenty tools. What did go obsolete is the rule's second clause — it asked for a replacement accepting a device token, and every caller that returns holds a forge_pat_*.

When rest.mjs is on every box, the wrapped verbs are discharged together — a file, not an issue. It does not cover forge call, the raw passthrough for tools no verb wraps; whether 3.35.141+ still ships it against /mcp is not knowable from this repo, and guessing is what the forge-plugin carve-out prevents. Rule 3 has a source the database does not hold

Grep the runner's bundled prose as well as the tables. forge-runner-core/src/workspace/orientation.rs writes "Recall memory FIRST — forge_memory_search({…})" into every workspace: every agent on every box is told to call it by name, in text this repo ships, and no audit query would surface it.
Rule 3 is two-party by design. GET /api/admin/mcp-audit/tools (ISS-946) returns whole-table per-tool counts — deviceCalls, tokenCalls, unattributedCalls, notFoundCalls, firstSeen/lastSeen, plus oldestRow so the window is read rather than assumed — registry FULL OUTER joined so a never-called tool comes back at zero. It sits behind requireAdmin because a tool's callers span every project, which resolves no project for the PAT fence to bite on. So an agent gathers the refusals (rules 1 and 2, both greppable on the box) and a human runs this route for the clearance. A project-scoped twin is refused by name: a tool idle here and busy in the next project would read clear — the 7f0c5a56 substitution again.
