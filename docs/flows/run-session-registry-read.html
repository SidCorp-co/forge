run-session-registry-read — how a box's session registry becomes readable off the box

Until ISS-934 the only record of which pane belonged to which run, which master started it, what pid it was and which worktree it held was a SQLite file at ~/.local/share/forge-runner/ledger.sqlite. Machine-local: core did not know, the web UI did not know, another box did not know. This is the hop that carries it out, and the three places it declines to answer rather than answering wrongly.

The hop

sequenceDiagram
  autonumber
  participant L as ledger.sqlite (the box)
  participant P as daemon publisher task
  participant W as transport/ws.rs
  participant S as core /ws
  participant D as device_run_ledger
  participant R as GET /api/projects/:id/run-sessions

  loop every 20s
    P->>L: unclosed_runs() + issues(run)
    P->>W: watch::send(one whole snapshot)
  end
  W->>S: runner:sessions {bootId, runs[]}
  Note over W,S: on connect too, before the read loop
  S->>S: device principal? strict schema?
  S->>D: DELETE this device's runs not named, then upsert each — ONE transaction
  R->>D: rows for this project
  R->>R: LEFT JOIN agent_sessions for status + last activity
A snapshot, never a delta. The whole unclosed set goes every time and the newest replaces the last. A dropped frame, a reconnect and a daemon restart therefore all self-correct on the next tick with nothing remembering what it failed to send — which is also what keeps the ledger a registry rather than the queue ISS-933 refused it becoming.
The replace is scoped to one device, in one transaction. Two statements would leave a window in which the box holds nothing, and a reader landing in it reports a working box as idle. A predicate wider than one device would have one box's snapshot retire another's runs.

Where it declines instead of guessing

ConditionWhat happensWhy not the other thing
a ledger row written before ISS-934, with no projectthe box logs it by run id and leaves it out of the snapshotthe read surface authorises per project, so a guessed project id shows one tenant's worktree and pid to another
the frame arrives on a user principaldropped, loggeda user socket carries its owner's account authority; accepting it would let any signed-in person rewrite what a box is running, and the surface presents it as the box's own word
one run carries a field this core does not knowthe WHOLE snapshot is refusedthe two sides ship on separate release clocks; a snapshot core half-understands is worse than one it rejects loudly
the box stops sendingthe rows stay, with observedAt ageinga dead box cannot write that it died, so staleness is the only honest signal — deleting on silence would erase the evidence a reader needs

Who owns which field

FactAuthority
parent master session, pid, worktree path, boot, incarnation, work state, blockerthe box — nothing else can see them
issue membership and per-issue lease returnthe box's ledger, mirrored; pipeline_runs.metadata.runIssues is core's own copy and the two disagreeing is a signal
session status and last activitycore's agent_sessions row, joined at read time and never mirrored
Last activity is not the box's to report. A box reporting its own liveness is a box marking its own homework. The heartbeat core already receives is the independent reading, so the read surface joins for it — and a box whose snapshot is fresh while its session's heartbeat is stale is exactly the state an operator needs to see.

Do not

Add a status column to device_run_ledger that restates something agent_sessions already says — that gives the fact two writers and the losing one is invisible. Put a foreign key on session_id: a run naming a session core's reaper has already removed would fail the whole statement and take every other run on the box down with it. Suppress an unchanged snapshot: a silent box would then be indistinguishable from a steady one.
