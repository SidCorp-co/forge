issue-work-module-knowledge-refresh — how a passing test keeps a module's knowledge current

The loop that feeds the knowledge nodes every later tier of ISS-587 renders from. issue-work-module-attribution owns how an issue acquires a primary module and where a bad one is refused; web-v2-module-taxonomy owns the slug and the 1:1 node binding this resolves through. This file owns what happens after both: a test handoff arrives, and the node of the module that work landed against stops being stale on its own. Owner: packages/core/src/labels/module-knowledge-refresh.ts, triggered from packages/core/src/pipeline/issue-context-store.ts.

The trigger is a passing test, not a status change. The asymmetry is ISS-587's and is not re-litigated here: a status is a claim somebody made, a green test is a thing that happened. The consequence is that an autonomous project does not feed this loop at all — its driver writes a drive handoff, whose outcome: advanced says the turn finished and never that anything passed. Widening the filter to drive is a decision about which outcomes count as work landing, and it is nobody's to take inside a refactor.
The primary gets the flow, the secondaries get the append. There is exactly one primary (issue_labels_primary_uq), so there is never a question about which node's flow to touch. Every module the issue touched — primary included — is appended to its node's related_issue_ids, and the append is deduped, so the same issue landing twice leaves one entry.
metadata.moduleFlow is a claim about a specific body, which is why nothing clears it. The record is { staleSince, staleByIssueId, bodyHash } and reads as: as of the node body that hashes to bodyHash, the stored flow is behind the work of staleByIssueId. A landing that finds the same hash leaves the record alone (that is both the idempotency and the "a second issue does not steal the first one's name"); a landing that finds a different hash re-arms against the new body, which is what an author redrawing the flow looks like from here. So a reader treats the record as live only while the node's current body still hashes to bodyHash — there is no second writer that has to notice the redraw and no boolean anybody has to remember to clear.
Core cannot draw the diagram, and does not pretend to. ISS-587 has the user-flow diagram render from a Mermaid flow stored inside the module-<slug> node. That content is authored — by a person, or by an agent rewriting the node — and core has neither an LLM nor a repo checkout at the moment a handoff lands. So the engine refreshes what it can measure (the related issues) and records what it cannot author (that the flow is behind, and since when), rather than writing a placeholder diagram that a reader could not tell apart from a real one.
