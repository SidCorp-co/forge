master-wake — what makes a box look at a project

Before ISS-933 nothing pushed: daemon/master.rs polled every 30s and that interval was the latency from an issue arriving to an agent touching it. core/src/ws/master-wake.ts · forge-runner-core/src/daemon/{master,mod}.rs · .../transport/ws.rs

A wake carries no job, no token and no decision — it says look now, and the box reads the pool through the same call its timer already used.

The timer is the floor and it must stay. ws/rooms.ts:publish is fire-and-forget — 0 for a room with no subscriber, skips any socket not OPEN, no buffer, no queue, no replay. A wake published while a box's socket is down is gone and nothing records it. With the timer that drop costs 30s; without it, it costs the work.

The dropped-wake hole, and what covers it

sequenceDiagram
  participant C as core
  participant WS as transport/ws.rs
  participant D as daemon/mod.rs
  participant M as master.rs::run

  Note over WS: socket is DOWN
  C->>C: issue → open
  C-)WS: publish master.wake
  Note over C,WS: room has no subscriber → publish returns 0
THE FRAME IS GONE. Nothing records it.
  WS->>WS: reconnect, then subscribe device:<id>
  WS->>D: local frame { event: "ws.connected" }
  D->>M: Wake::Reconnect
  M->>M: sweep — reads the WHOLE pool, so it finds the missed issue
The catch-up is the same wake path on a different trigger, never a second reader — a reconnect handler that read the pool itself would be a second dispatcher on the box, and the two would drift the moment either grew a condition. The transport knows nothing about masters or pools: it reports its socket came up, and mod.rs decides what that means.

Coalescing — why the channel holds exactly one

flowchart LR
  A["5 master.wake frames
within ~5ms"] --> B{"wake_tx.try_send"}
  B -- "1st: channel empty" --> C["queued"]
  B -- "2nd-5th: channel full" --> D["dropped, logged at debug
'coalesced — a sweep is already pending'"]
  C --> E{"last sweep
less than WAKE_FLOOR ago?"}
  E -- yes --> F["sleep the remainder
— waits, never discards"]
  E -- no --> G
  F --> G["sweep: reads the WHOLE pool"]
  D -.->|"covered by"| G
Core publishes one frame per issue arrival; promoting five drafts delivers five in milliseconds. A dropped frame costs nothing because the sweep that follows reads the entire pool, so one sweep covers every wake pending. try_send rather than an awaited send also matters because this arm shares the frame loop with job.cancel — blocking it would stall a kill behind a sweep that was already going to cover the wake.
WAKE_FLOOR must stay below POLL_INTERVAL. A floor at or above 30s makes every wake wait longer than doing nothing; a_wake_cuts_latency_rather_than_adding_it is the assertion that fails.

The close-the-loop half is the known hole, and it is unowned. When a run ends, three things must happen — the agent_sessions row reaches terminal, the worktree is removed, the tracker lease is returned. Nothing performs them and nothing checks; it rests on the master remembering. Measured on forge-dev 2026-09-06: a master reported a loop closed having done one and a half of three, and the third is currently impossible — forge claim gates on wall clock rather than liveness, so a lease held by a dead pid refuses every claim for its full duration (forge-plugin ISS-602). Wave 2 multiplies this by one loop per run. Any reaper must consult the lease, never cwd, mtime or "no tmux session by that name" — a session working a second worktree is held from a cwd outside it — and the lease cannot be that authority until it can tell a live holder from a dead one.

Read this before

  • Adding a status to MASTER_WAKE_STATUSES — the driver's mid-run statuses (in_progress, needs_info) are issues a master already handed to a run, so waking on them turns one lifecycle into a burst of pool reads that find nothing by construction.
  • Filtering devicesServing on runners.status — declining work is the box's act, not core's (master.rs:accepts_new_work).
  • Removing the timer or the catch-up — each covers a different half of a transport that loses frames without saying so.
  • Widening the wake channel past capacity 1 — that is not losing fewer wakes, it is one redundant full sweep per queued frame.
