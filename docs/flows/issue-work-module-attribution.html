issue-work-module-attribution — a label becomes an issue's primary module

One labels[] write, from the request body to the junction rows, and the four points at which it is refused. A module is a label (labels.kind='module'), so this is the ordinary label-attach path with one extra claim riding on it: which of those labels is the issue's primary module. Owner: packages/core/src/issues/label-service.ts. The last section covers the hop before the request: how an agent comes to know the project has modules at all.

Where a write is refused, and what has been written when it is

Every refusal above happens before or inside the transaction, so a rejected write leaves the issue exactly as it was. That is the property to preserve: an attach that partly applied would leave an issue labelled with a module nobody chose, and no reader could tell it from a deliberate one. Two of the four checks (MULTIPLE_PRIMARY, PRIMARY_NOT_MODULE) exist only because SQL cannot see labels.kind from an issue_labels row — which is also why the index below them is not redundant with them.

Reading it back

Every surface that lists an issue's labels reports kind and isPrimary per entry (listIssueLabels, REST issue detail, by-display), and ModuleAttribution in @forge/contracts is that entry's shape. There is no other source for an issue's primary module — no column on issues, no second table — so a client that wants it reads the array and picks the isPrimary one.

Filtering by module (?module=, filters.module) resolves the name or uuid against kind='module' labels only and then reuses the ordinary label EXISTS-join. An unresolved module returns no issues, never every issue: dropping the narrowing would hand the caller the whole project and read as "nothing matched".

Where the write comes from — how an agent learns there is a taxonomy at all

Everything above starts at a labels[] payload. This is the hop before it: nothing in the product asks a human to attribute an issue, so on a Forge project the writer is almost always a pipeline agent, and an agent only writes what its prompt told it exists. Owner: packages/core/src/prompt/facts/resolve.ts.

The taxonomy's existence is the switch. There is no per-project flag for module attribution and no setting to turn it on: a project acquires the prompt section the moment its first kind='module' label exists, and loses it if the last one is deleted. That is deliberate — an instruction to attribute, sent to a project with nothing to attribute to, is an invitation to invent a module, and an invented primary is worse than none because the filters and the reports are counted from it.

Two things this hop deliberately does not do. It does not write an attribution: Forge never guesses an issue's module, so an issue whose agent was unsure stays unattributed, which is a legal state at every status. And it does not reach the mandatory preamble — that text is byte-identical across projects for the prompt cache, so a per-project section could only ever live in the contextual, project-resolved tier.
