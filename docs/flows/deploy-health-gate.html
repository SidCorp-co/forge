deploy-health-gate — proving a deploy serves, and undoing one that does not

Coolify answers a question about the build. Nothing in Forge used to ask the one that matters: is the thing it built serving? Owners: packages/core/src/integrations/coolify/health-gate.ts (the probe, the verdict and the rollback decision), packages/core/src/integrations/coolify/confirm.ts (which hands the hold over), packages/core/src/integrations/coolify/controls.ts (the rollback and its refusals), packages/core/src/pipeline/deploy-confirmations.ts (the hold the verdict settles).

The incident this exists for produced no HTTP response at all. On 2026-09-07 a pg-boss 10 → 12 bump crash-looped the forge-beta API for ~40 minutes: v12 aborts at start() on a DB schema below 25, beta sat at 24, the container never opened its port and the proxy answered no available server. Coolify reported the deployment finished and it was telling the truth. So a probe that treats connection-refused as “no reading, try later” is blind to exactly this failure: unreachable is an unhealthy reading and it counts against the deadline.

The hops, and where each one refuses

What each refusal costs, and why it is a refusal

WhereRefuses whenBecause
healthGateForthe target declares no healthUrl Forge cannot know an arbitrary application’s health path. A derived default would arm automatic rollback on every target whose path it guessed wrong, so absence is the off switch.
probeHealthnever — every outcome is a reading Unreachable, 503, ok:false and an unparseable 200 are four named reasons, not an absence. The one this was written for is the first.
pickRollbackImagenothing is listed but the current image rollback_images answers 200 {images:[]} when the application’s server is unreachable, so empty and clean are the same bytes. Falling through to images[0] would restore the broken build and call it a rollback.
runCoolifyRollbackthe tag is not one Coolify lists, or the binding is prod without human confirm Coolify does not check the tag itself. performed:false is a rollback that did not happen, and it pages rather than being read as done.
the rollback’s own gatealways — it never rolls back again A restored image that also cannot serve is a state no further automation improves; a second rollback walks the application down a list of builds nobody chose while the outage continues.
The circuit breaker does not gate the rollback, and that is deliberate. breakerAllowsDispatch is consulted by coolifyAdapter.dispatchOutbound and by nothing else; runCoolifyRollback goes through performControl, which never asks it. The breaker exists to stop repeated outbound deploys against a Coolify that is refusing them — a rollback it swallowed would leave the dead build serving, which is the worst outcome on this diagram.
One writer of the run’s outcome, still. The gate does not close a run. It calls applyDeploySettlement, the same function confirm.ts calls, which settles the hold and performs the deferred close. A gate watching a rollback carries no deliveryId and settles nothing — the failed deploy already owns that hold.
