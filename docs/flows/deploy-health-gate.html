deploy-health-gate — proving a deploy serves, and undoing one that does not

Coolify answers a question about the build. Nothing in Forge used to ask the one that matters: is the thing it built serving? Owners: packages/core/src/integrations/coolify/health-gate.ts (the probe, the verdict and the rollback decision), packages/core/src/integrations/coolify/confirm.ts (which hands the hold over), packages/core/src/integrations/coolify/controls.ts (the rollback and its refusals), packages/core/src/pipeline/deploy-confirmations.ts (the hold the verdict settles).

The incident this exists for produced no HTTP response at all. On 2026-09-07 a pg-boss 10 → 12 bump crash-looped the forge-beta API for ~40 minutes: v12 aborts at start() on a DB schema below 25, beta sat at 24, the container never opened its port and the proxy answered no available server. Coolify reported the deployment finished and it was telling the truth. So a probe that treats connection-refused as “no reading, try later” is blind to exactly this failure: unreachable is an unhealthy reading and it counts against the deadline.

The hops, and where each one refuses

What each refusal costs, and why it is a refusal

WhereRefuses whenBecause
healthGateForthe target declares no healthUrl Forge cannot know an arbitrary application’s health path. A derived default would arm automatic rollback on every target whose path it guessed wrong, so absence is the off switch.
healthGateForthe confirmation hold has less than HEALTH_MIN_WINDOW_MS (grace + 60s) left The gate is scheduled entirely inside the hold’s own 30-minute deadline so two mechanisms cannot decide one deploy. Below the floor that clamp would leave one probe taken after the deadline, against a container 30 seconds into boot — a healthy deploy rolled back. So the gate does not open: confirm.ts settles on the build verdict and logs that the deploy is not proven to serve. An unproven deploy is the state before this gate existed; a rolled-back healthy one is a new outage.
probeHealthnever — every outcome is a reading Unreachable, 503, ok:false and an unparseable 200 are four named reasons, not an absence. The one this was written for is the first.
pickRollbackImagenothing is listed but the current image, or nothing in the list says which image is running rollback_images answers 200 {images:[]} when the application’s server is unreachable, so empty and clean are the same bytes. And is_current is optional on Coolify’s row while current can be null: a list that identifies nothing has the just-failed build sitting at the top of it, so it is refused rather than restored. An unparseable created_at sorts last, because a comparator returning NaN would silently make “the newest image” mean “the first one Coolify printed”.
restorePreviousthe Coolify connection is inactive — the circuit breaker is open The breaker writes connections.active = false, and activeCoolifyIntegrations filters on it, so the rollback would surface as no active Coolify integration — a sentence about configuration for a condition that is about Coolify refusing calls. Three failed deliveries in five minutes is Coolify refusing everything, a rollback included, so the gate names the breaker and pages.
restorePreviousa health-rollback:<uuid> delivery already exists for this deploy Anything throwing after the dispatch makes pg-boss re-run the job, and by then is_current names the restored image — so an unguarded retry picks the build that just failed. That marker, written before the dispatch, is the one dedup key in the module that must not move.
runCoolifyRollbackthe tag is not one Coolify lists, or the binding is prod without human confirm Coolify does not check the tag itself. performed:false is a rollback that did not happen, and it pages rather than being read as done.
the rollback’s own gatealways — it never rolls back again A restored image that also cannot serve is a state no further automation improves; a second rollback walks the application down a list of builds nobody chose while the outage continues.
An open circuit breaker DOES block the rollback, and the gate says so by name. runCoolifyRollback never consults breakerAllowsDispatch — only dispatchOutbound does — but the breaker trips by writing connections.active = false, and every path to a rollback resolves the binding through activeCoolifyIntegrations, which filters on exactly that column. So a rollback attempted with the breaker open dies as no active Coolify integration, which reads as a configuration fault. The gate checks the connection first and pages naming the breaker instead. Reactivating the connection to force the rollback through is not the fix: that column is the breaker’s state, and three failed deliveries in five minutes is Coolify refusing everything a rollback would need.
One writer of the run’s outcome, still. The gate does not close a run. It calls applyDeploySettlement, the same function confirm.ts calls, which settles the hold and performs the deferred close. A gate watching a rollback carries no deliveryId and settles nothing — the failed deploy already owns that hold.
