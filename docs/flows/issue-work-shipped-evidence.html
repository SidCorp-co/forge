issue-work-shipped-evidence — how finished work becomes a countable "shipped"

Every path that writes issues.merged_at, and the one predicate that decides whether an issue counts as shipped or as closed with no evidence it shipped. This is a lifecycle question with an adversary built into it: merged_at is also what releases every blocks dependent, so a stamp is a claim that code shipped rather than a date field, and the counter has to tell a deliberate claim apart from the one the kernel writes on its own. Owners: packages/core/src/issues/merged-at.ts (the automatic writers), packages/core/src/issues/merge-marker.ts (the deliberate one) and packages/core/src/issues/progress.ts (the predicate).

Three writers, one predicate

What has been written when the count is wrong

  • An over-count is unrecoverable by reading. If stampedByCloseItself is ever dropped, every close counts as shipped and the figure is indistinguishable from a true one — which is why tests/integration/progress-shipped-evidence-e2e.test.ts pins the timestamp identity itself, not just the resulting number.
  • The identity is a real coupling, not a coincidence. The auto-stamp and the close's activity_log row are written in ONE transaction, and Postgres now() is transaction-start time, so the two land on the same instant. Split those writes apart and the shipped figure silently inflates — issues/apply-transition.ts carries the cm:edge lockstep that says so.
  • An under-count is silent too, and it is what ISS-791 measured. Nothing is lying: the record is made, the API is truthful, and the work is simply not counted. The only signal is a person noticing that a project they shipped reads as having shipped nothing.
  • An agent cannot make the claim on evidence it does not have. applyMergeMarker runs pipeline/work-evidence.ts when the actor's agency is agent: no branch, no commit and no code handoff is a refusal, and a human's own claim is not gated because a human is accountable for it.
