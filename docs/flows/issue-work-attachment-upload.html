issue-work-attachment-upload — how a file becomes an attachment, which hop refuses it, and what a refused upload leaves behind

Six entry paths, one decision point, and four ways out. The question this answers is the one a person actually arrives with — my upload was refused, at which hop, and what do I do about it — so every refusal below names the field that tells you. Owners: packages/core/src/lib/attachment-mime.ts (the type decision and the allowed set), packages/core/src/{issues,comments,agent-sessions}/attachment-service.ts (the three persist funnels), packages/core/src/uploads/ticket-service.ts (the mint hop) and packages/core/src/uploads/routes.ts (the presigned PUT).

Six ways in, one place the file is judged

The convergence is the whole reason a single change fixes every surface: REST multipart, the presigned PUT and the base64 MCP paths all end at one of three persist*Attachment functions, and the type resolution lives inside those rather than at any entrance.

What each hop refuses, and what it leaves behind

HopRefusesBody carriesLeft behind
createUploadTicket (mint) A type the caller explicitly declared that the target's set does not hold; a name already on the target. details.allowed or details.existing. Nothing — no ticket row, no bytes sent.
resolveAttachmentMime not-allowed: a type the client CLAIMED that the target's set does not hold, whatever the bytes are; or binary bytes under a guessed type it does not hold. not-text: a text-format type (text/*, image/svg+xml) whose bytes are binary. Binary means a control byte no text carries, anywhere in the file — not a failed UTF-8 decode, so a Windows-1252 CSV and a BOM-marked UTF-16 .txt still land. details.allowed = {mimes[], extensions[]} — the whole set, so a client prints it instead of keeping a copy that goes stale. Nothing — the check runs before storage.put.
findIssueAttachmentByName / findCommentAttachmentByName A name already stored on this issue (or this comment), compared on the sanitised name. details.existing = {id, name, url}. Nothing. On an issue the id it hands back is exactly what DELETE /api/attachments/:id takes, so refuse → delete → retry closes. On a comment it does not close — there is no delete for comment attachments (see the gap below), so the only way out is a different name.
persistDecoded*Attachments (a batch) The whole batch, if any member fails validation. One entry per failing member: {index, name, code, message, details}. Nothing. Every member is judged before any is written, and a failure part-way through the writes discards the rows and blobs already made.
The mint hop got MORE permissive and the PUT got stricter, in the same change. An extension the table does not know used to be refused at mint as application/octet-stream; it now mints as text/plain, because a ticket is a capability and not a verdict. The refusal for an unknown extension therefore moved one hop later: a binary .log now pays its bytes before it is told no. That is the price of a plain-text .log attaching at all, and it is why the refusal carries the allowed set — the client that just spent the upload should not have to guess what would have worked.
The two refusals are one fix seen from two ends. A half-landed batch is what creates the duplicate names the identity check then refuses: the measured incident was a batch refused on its third file that left the first two up under names that could not be re-sent. Fixing identity while batches still half-land would leave the generator of the problem running, which is why whole-batch atomicity and name identity shipped together (ISS-957 + ISS-963).

Where a reader gets this wrong

  • A claim binds; a guess does not. A file of plain text named photo.png is stored image/png — the name asks for a type the target allows, and retyping a believed declaration would be a silent substitution. What the bytes rescue is the guess: report.log, schema.sql and every unmapped extension guess text/plain, and text bytes make that guess stand even when the guessed type is one the target refuses. application/octet-stream counts as no declaration at all, because the multipart routes write it themselves for every .log a person drags in. image/svg+xml survives a text sniff because SVG is XML source; no other image, video or office type does.
  • The symmetric half bites too. A notes.txt whose bytes are binary used to be stored as text/plain and is now refused not-text. That is a removal, not an addition.
  • Sessions have no name guard. Not an omission: no record cites a session attachment by name, so uniqueness there would refuse uploads for nothing.
  • Comment attachments have no DELETE. DELETE /api/attachments/:id covers issue attachments only. A refused comment upload is still escapable — a comment is written once with its files and a fresh comment is a fresh namespace — but the recovery loop above is issue-only.
