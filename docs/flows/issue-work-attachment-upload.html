issue-work-attachment-upload — which hop refuses a file, and what it leaves behind

Six entry paths, one decision point, four ways out — every refusal below names the field that tells you which. core/src/lib/attachment-mime.ts · core/src/{issues,comments,agent-sessions}/attachment-service.ts · core/src/uploads/{ticket-service,routes}.ts

Six ways in, one place the file is judged

REST multipart, the presigned PUT and the base64 MCP paths all end at one of three persist*Attachment functions, with type resolution inside those rather than at any entrance — which is why one change fixes every surface.

What each hop refuses, and what it leaves behind

HopRefusesBody carriesLeft behind
createUploadTicket (mint) A type the caller explicitly declared that the target's set does not hold; a name already on the target. details.allowed or details.existing. Nothing — no ticket row, no bytes sent.
resolveAttachmentMime not-allowed: a type the client CLAIMED that the target's set does not hold, whatever the bytes are; or binary bytes under a guessed type it does not hold. not-text: a text-format type (text/*, image/svg+xml) whose bytes are binary. Binary means a control byte no text carries, anywhere in the file — not a failed UTF-8 decode, so a Windows-1252 CSV and a BOM-marked UTF-16 .txt still land. details.allowed = {mimes[], extensions[]} — the whole set, so a client prints it instead of keeping a copy that goes stale. Nothing — the check runs before storage.put.
safeName + the byte budget A sanitised name over 180 bytes of UTF-8 — INVALID_NAME. Bytes, because the storage key is a filesystem path component: ~81 CJK characters overflow where 200 ASCII ones did not. The limit, and the instruction to rename. Nothing — the check runs before storage.put. It refuses rather than trimming, because a trim maps every name sharing its first 180 bytes onto one row, which is the collapse the identity rule exists to prevent.
findIssueAttachmentByName / findCommentAttachmentByName A name already stored on this issue (or this comment), compared on the sanitised name. details.existing = {id, name, url}. Nothing. On an issue the id it hands back is exactly what DELETE /api/attachments/:id takes, so refuse → delete → retry closes. On a comment it does not close — there is no delete for comment attachments (see the gap below), so the only way out is a different name.
persistDecoded*Attachments (a batch) The whole batch, if any member fails validation. One entry per failing member: {index, name, code, message, details}. Nothing. Every member is judged before any is written, and a failure part-way through the writes discards the rows and blobs already made.
The mint hop got MORE permissive and the PUT got stricter, in one change. An unknown extension used to be refused at mint as application/octet-stream; it now mints text/plain, because a ticket is a capability and not a verdict. So the refusal moved one hop later — a binary .log pays its bytes before it is told no. That is the price of a plain-text .log attaching at all, and why the refusal carries the allowed set.
The check, the storage.put and the INSERT are one transaction under a name lock. Without it the check is a read then a write with no constraint underneath and the blob write in the window between — measured 2026-09-07, four concurrent uploads of one name stored four rows and refused none. pg_advisory_xact_lock on scope:parentId:sanitisedName, never the _try_ form: a caller that cannot take it must wait and then see the row, because failing open is the bug it closes. UNIQUE (parent_id, name) would be stronger but pre-rule rows already violate it, and this repo does not discard a row so an ALTER succeeds. Price: the lock is held across the storage write on a pooled connection.
A name is an identity, so the sanitiser may not merge two of them. Keep-class \p{L}\p{M}\p{N}._- after NFC: [^A-Za-z0-9._-] sent 报告.pdf and 设计.pdf both to __.pdf, and dropping \p{M} does the same to Devanagari, Arabic harakat and Hebrew niqqud. NFC is the one merge it makes on purpose — the two spellings of café.pdf are one document. The read path pays too: a Content-Disposition value is a ByteString, so the served name goes out RFC 5987 encoded (lib/attachment-headers.ts) or a file that uploaded fine 500s on download.
The two refusals are one fix from two ends. A half-landed batch creates the duplicate names the identity check refuses — the measured incident was a batch refused on its third file, leaving two up under names that could not be re-sent. So whole-batch atomicity and name identity shipped together (ISS-957 + ISS-963).

Where a reader gets this wrong

  • A claim binds; a guess does not. Plain text named photo.png stores as image/png — retyping a believed declaration would be a silent substitution. The bytes rescue only the guess: report.log, schema.sql and every unmapped extension guess text/plain, and text bytes make that stand even where the guessed type is refused. application/octet-stream is no declaration at all — the multipart routes write it themselves. image/svg+xml survives a text sniff because SVG is XML source; no other image, video or office type does.
  • The symmetric half bites too. A notes.txt whose bytes are binary used to be stored as text/plain and is now refused not-text. That is a removal, not an addition.
  • Sessions have no name guard. Not an omission: no record cites a session attachment by name, so uniqueness there would refuse uploads for nothing.
  • Comment attachments have no DELETE. DELETE /api/attachments/:id covers issue attachments only. A refused comment upload is still escapable — a comment is written once with its files and a fresh comment is a fresh namespace — but the recovery loop above is issue-only.
