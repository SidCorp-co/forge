release-record

How an issue reaches closed, what must be written before it may, and the one hop on this path where the record can still be lost in silence.

Why this flow exists

closed is what every reader takes as this shipped — the blocks gate, the release roster, pipeline health, and markMergedOnClose, which stamps merged_at on the way past and thereby releases every dependent. So a close is a claim, and the whole of this flow is the set of things that must be true before an automated hand may make it.

The claim used to be free. Six issues closed on 2026-08-27 with no changelog entry, two of them with releaseNotes null; a batch closed two more the same way. Both doors below were built from those measurements (ISS-863, ISS-880, ISS-897).

The two doors are one rule

A release note must exist on the issue before an automated close. It is checked in two places because two different callers reach closed with an automated hand on them, and the second is exempt from the first because of the second check:

DoorWhereRefuses
the transitionissues/release-record-required.ts refuseUnrecordedClose an agent's closed while issues.release_notes is null
the batch claimrelease-batch/service.ts createReleaseBatch the WHOLE batch, before anything moves, if any issue has no note

finishReleaseBatch closes with viaReleasePath, which the first door exempts. That exemption is sound only while the claim preflight exists — delete the preflight and the batch path silently closes unrecorded issues again. The pair carries cm:edge lockstep in both directions for exactly this reason.

The three exemptions, and why each one is right

ExemptWhy
a human actorAn operator closing by hand makes the shipped claim deliberately and owns it. The check asks agency, not actor.type: a job token is an agent writing as the person who queued it.
viaReleasePathThe note was already required at the claim. This is the only flag that must not be widened — the shared skip flag rides on every internal transition, so exempting on it would open the door from all of them at once.
droppeddropped means this was not work. It is terminal with no exit, and it stamps no merged_at — which is what makes it the honest discard, and why closing an abandoned issue is the wrong one.

Where the record is still lost

Everything above guarantees a note exists on the ISSUE. Nothing here reaches CHANGELOG.md. Core never reads that file, and CI never reads the issue table, so no single process sees both halves.

  • RELEASE_RECORD_REQUIRED is blind to whether the note ever became a bullet.
  • scripts/check-release-record.mjs (no-silent-loss) is blind to an entry that was never written — it only defends entries that existed at the base revision.

Measured consequence: four issues reached main with nothing in the record — ISS-877 (08-29), ISS-854 (08-30), ISS-870 (09-02) and ISS-903 (09-03). Every one was found by a scheduled sweep days later and backfilled by hand: the first two by ISS-870, the last two by ISS-896. Three of the four had releaseNotes populated at their close, so the refusal above held and the reader still got nothing — which is the point. The one that did not, ISS-854, was closed by hand, where the refusal exempts by design.

This is a known open decision, not an unnoticed hole: whether a close should prompt for its note, and whether that prompt should also write the bullet, is held for a human in docs/proposals/changelog-omission-is-unguarded.md along with the reason both obvious gates are refused. Do not close it from a diff.
