issue-work-conditional-field-write — a write that carries the value it read

How two writers of one issue field are separated by the tracker rather than by etiquette, and where the loser is told what the field now holds. The field is issues.session_context, which is where a driver's lease lives: two runs that both read no holder both claimed, and the later write erased the earlier with neither able to tell. Owners: packages/core/src/issues/update-service.ts (the statement), issues/session-context.ts (the shape) and the two doors, issues/routes.ts and mcp/tools/forge-issues.ts. Drawn for ISS-959.

The hop that decides, and where it must sit

The four decisions, and what each one refuses

DecisionWhy it went this way
IS NOT DISTINCT FROM, not = = null is NULL in SQL, so every legitimate FIRST claim — the case where the field holds nothing yet — would be refused. Absent has to be an expressible expectation.
The refusal carries details.current A bare 409 tells the loser its write failed and nothing about what to do next, so the only move left is to read again and write unconditionally — the overwrite the refusal exists to prevent. MCP has no details channel, so that door serialises the value into the message instead.
Zero rows re-reads the row before answering Zero rows means the row is gone OR the field moved, and a caller told the wrong one retries forever or gives up wrongly. The re-read runs inside the doomed transaction; no row at all is a 404, never a mismatch.
The jsonb parameter carries an explicit ::jsonb cast A bare sql`${json}` is an untyped parameter whose type Postgres cannot infer — a live 500 on forge-beta for the sibling merged_at write.
expect is absent from SHARED_ISSUE_PATCH_FIELDS It is a precondition, not a field. In that list, the value a client read back would be written into a column.
The ISS-820 verified-claim walk is deliberately NOT applied to expect That walk judges a claim being WRITTEN. expect is a value read back off the row, and re-judging it would make the field unwritable by the very client that read it — the walk already ran on the write that stored the value.

What breaks this

ChangeWhat goes wrong
Reading the current value above the UPDATE and comparing in TypeScript The rule reads identically and enforces nothing: both writers pass the check and the later one still erases the earlier. The suite that catches it is tests/integration/session-context-expect-e2e.test.ts, which runs two writes against a real Postgres; a mocked query builder never executes a WHERE and cannot tell the two apart.
Making expect required Every client that predates the field starts failing. A write with no expect behaves exactly as before, on purpose.
Answering the mismatch with 404, or the missing row with 409 A client cannot tell "somebody else holds this" from "this issue is gone", and the two demand opposite responses.

The half that is not in this repo

The lease rule itself — how long a claim lasts, when a reclaim counts, what a wave's id may hold — lives in github.com/SidCorp-co/forge-plugin (forge claim, the issue-flow skill). This repo supplies only the compare-and-set the rule needs to be enforceable; the CLI still says the lease is advisory until the plugin half reads expect. The five plugin issues waiting on it (forge-plugin ISS-491, ISS-602, ISS-467, ISS-581, ISS-612, filed as ISS-7) stay theirs.
