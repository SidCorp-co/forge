What a status claims, and who is owed the next move

a status says placement — never evidence

1The five exits from draft, and the one that mints work

Only open mints anything. A session already in the worktree takes in_progress; one that pushed its branch and cannot merge takes developed. Promoting to open instead races a runner-dispatched agent against the session already building the branch (ISS-933).

2When the run that owed the close dies

The mirror failure. Code merged and deployed, the mark landed, and the session that owed the close was gone before it wrote one. The issue reads open — which means claimable — and the reconciler re-dispatches it every minute. Observed on ISS-920 and ISS-931, both serving production traffic while the tracker said the work had not started. The refusal and the notification are one decision split across two passes: drop the detector and the exclusion becomes a silent skip, which is worse than the re-dispatch it replaced. Neither pass closes the issue — merged_at is caller-asserted, so the honest act is to put it in front of someone who can check.

Where each claim lives

  • Which gate, and whose movepipeline/status-assertions.ts → STATUS_ASSERTIONSExhaustive Record<IssueStatus, {gate, nextActor}> — both fields placement. A status added to the schema without an entry fails tsc.
  • Did it landissues.merged_atCaller-asserted: any hop out of the base merge state stamps it, merge or not. The first stamp wins — a later mark answers already_merged rather than moving it.
  • At which commitissues.merged_commit_shaISS-959. Same conditional statement as merged_at, so the pair is stamped together or not at all. The two automatic writers know no commit and leave it null.
  • Does a branch existsession_context.branchWritten by the session; the project's own base/production branch does not count.

  • Is there a commitissue_step_contexts kind='handoff'From a code/fix/drive step. An empty handoff is not evidence.

What a master reads on a backlog row

The declared backlog (ISS-917) excludes an issue only when work has been opened for it — a job, or a live run. A pipeline run mints a job and never appears; an issue built by hand mints neither, so a draft somebody finished and a draft nobody touched arrive as the same row. The fix is to carry the evidence fields and let the master decide: a row carrying a merge mark is not filtered out. Show the fact; never take the decision.

A status answers placement — which gate the work sits at, and whose move is next. It answers nothing else. Evidence — whether code was written, pushed or merged — is answered by three fields on the row, read directly.

The two were welded together until 2026-09-06, and developed is where they broke apart: this repo's lifecycle guide read it as placement (work built outside the pipeline enters at the review gate), the driver plugin's contract read it as evidence (the mark is earned by the merged commit and the base it landed on). Four runs reached one identical real state — built, gates run, branch pushed, PR open, nothing merged — and recorded four different statuses. None was careless; each honoured a different documented promise (ISS-940).

The generalisation is what the fix is shaped by: the tracker had assumed the actor who finishes work can also land it. For an actor bound not to merge, placement is earned when the branch is pushed and the merge evidence is never earned at all — so no single rung can be honest about both.

The half that is not in this repo. forge guide contract developed ships from github.com/SidCorp-co/forge-plugin and still describes the mark as earned by “the merged mark with its commit and the base it landed on” — the evidence promise this flow removes from the status. Nothing here gates that pair. Reported there; until it lands, a driver session reads two definitions and this page is the one core enforces.

Every content rule on the transition writer used to return early unless the actor was an agent. transition-evidence.ts, release-record-required.ts and release-gate-hold.ts all short-circuited on agency !== 'agent', so the same status set from the tracker's own screens was neither earned nor refused. Measured twice on forge-dev on 2026-09-07: an ordinary forge record write and an ordinary forge comment write each moved an issue from needs_info back to open — and on that project open is what makes an issue claimable, so a silent un-park is a live path to two agents on one issue.

The rule nowAnd the bound on it
A project DECLARES which records a status entry requires, as pipelineConfig.statusEntryCriteria, checked for every actor Vocabulary is core's — plan, acceptance_criteria, release_note, work_evidence, merged_mark — and every key reads the TRACKER RECORD, never a working tree: a check that read a checkout would answer differently on every machine. Which criteria a status carries is the project's decision, not this repo's.
Resolved from the project config outside the transaction and handed in ISS-863 removed a projects SELECT from inside every status transition; doing it inside would put one back.
Keyed on the status the actor asked for, not the park rewrite's target Otherwise a project declaring criteria for waiting refuses a needs_info park it never mentioned.
Skipped entirely under options.skip The orchestrator's curated soft-skip chain is the highest-volume status writer in the product and the checker exempts it anyway — a read there is a query whose answer is discarded.
A project that declares nothing is byte-for-byte unchanged And a config that cannot be read declares nothing, rather than freezing every status write on the project.
no_work_evidence stays agent-only — on the RULE, not the checker An operator advancing by hand makes the shipped claim deliberately and owns it. A project wanting it held against people too declares work_evidence, which is the door built for that decision.

Excluding rows with merged_at set from the declared backlog The kernel silently hides an issue whose stamp may be wrong, and the master cannot tell that from an empty backlog.
