issue-status-placement

What a status is allowed to claim, which exits a draft has, and what happens to work whose author is bound not to land it.

The split, and why it exists

A status answers placement — which gate the work sits at, and whose move is next. It answers nothing else. Evidence — whether code was written, pushed or merged — is answered by three fields on the row, read directly.

The two were welded together until 2026-09-06, and developed was where they broke apart: this repo's lifecycle guide read it as placement (work built outside the pipeline enters at the review gate), the driver plugin's own contract read it as evidence (the mark is earned by the merged commit and the base it landed on). Four runs reached one identical real state — built, gates run, branch pushed, PR open, nothing merged — and recorded four different statuses. None was careless; each honoured a different documented promise (ISS-940).

The generalisation is worth stating plainly, because it is what the fix is shaped by: the tracker had assumed the actor who finishes work can also land it. For an actor bound not to merge, placement is earned when the branch is pushed and the merge evidence is never earned at all, so no single rung can be honest about both.

Exits from draft, and which one dispatches

What a master can tell from a backlog row

The declared backlog (ISS-917) excludes an issue only when work has been opened for it — a job, or a live run. A run built by the pipeline mints a job and so never appears. An issue built by hand mints neither, which is exactly the shape a session-per-run design produces, so a draft somebody finished and a draft nobody has touched arrive as the same row.

The fix is the one the module already applies to blockers, extended to the issue itself: carry the evidence fields, and let the master decide. mergedAt and branch are on the row; there is no derived shipped flag, and a row carrying a merge mark is not filtered out — merged_at is caller-asserted, so it is a fact to show a reader, never grounds for the kernel to hide the row and take the decision away.

When the run that owed the close dies

The mirror failure. The code merged and deployed, the mark landed on the row, and the session that owed the close was gone before it wrote one. The issue reads open, which means claimable, and the reconciler re-dispatches it every minute. Observed on ISS-920 and ISS-931, both serving production traffic while the tracker said the work had not started.

The refusal and the notification are one decision split across two passes. Drop the detector and the exclusion becomes a silent skip — the issue is neither worked nor reported, which is worse than the re-dispatch it replaced. The exclusion is silent at the reconciler on purpose: that pass runs every 60 seconds and a warn there prints the same ids every minute.

Neither pass closes the issue. Closing is a claim about shipped work, and a pass that cannot read the repository must not make it — merged_at is caller-asserted, so the honest act is to put it in front of the person who can check.

The refusal every actor now meets (ISS-959)

Every content rule on the transition writer used to return early unless the actor was an agent — issues/transition-evidence.ts, release-record-required.ts and release-gate-hold.ts all short-circuit on agency !== 'agent'. The same status set from the tracker's own screens was therefore neither earned nor refused: measured twice on forge-dev on 2026-09-07, an ordinary forge record write and an ordinary forge comment write each moved an issue from needs_info back to open, and on that project open is what makes an issue claimable — a silent un-park is a live path to two agents on one issue.

A project now DECLARES which records a status entry requires, as pipelineConfig.statusEntryCriteria, and the declaration is checked for every actor. The vocabulary is core's (plan, acceptance_criteria, release_note, work_evidence, merged_mark) and every key reads the TRACKER RECORD, never a working tree — a check that read a checkout would answer differently on every machine that ran it. Which criteria a status carries is the project's decision, not this repo's.

Three things bound it, in the order they matter. The declaration is resolved from the project config outside the transaction and handed in, because ISS-863 removed a projects SELECT from inside every status transition and this would put one back. It is keyed on the status the actor asked for, not on the park rewrite's target. And it is skipped entirely under options.skip — the orchestrator's curated soft-skip/failover chain is the highest-volume status writer in the product, and the checker exempts it anyway, so a read there would be a query whose answer is discarded. A project that declares nothing is byte-for-byte unchanged, and a config that cannot be read declares nothing rather than freezing every status write on the project.

no_work_evidence stays agent-only, and the carve-out is now on the rule rather than on the checker: an operator advancing by hand makes the shipped claim deliberately and owns it. A project that wants that rule held against people too declares work_evidence, which is the door built for that decision.

What breaks this

ChangeWhat goes wrong
Putting the declared-criteria read back inside the transaction, or keying it on toStatus The first re-adds the per-transition projects SELECT that ISS-863 removed from inside the write. The second checks the park rewrite's target rather than the ask, so a project declaring criteria for waiting would refuse a needs_info park it never mentioned.
Moving the agency carve-out back onto the whole checker Declared criteria stop holding against a person, which is the entire half of the surface this rule exists for — and it fails silently, because the happy path passes either way.
A third field on StatusAssertion naming a commit, a branch or a merge An evidence claim is back inside a status and the next pair of runs splits on it again. The key set is compared literally in status-assertions.test.ts for exactly this.
Adding a status to AUTONOMOUS_DRIVER_STATUSES to mean “done, awaiting a human” It falls into AUTONOMOUS_INFLIGHT_STATUSES by subtraction, and resetAutonomousWedgesOnce rolls finished work back to open and re-dispatches it.
A wedge pass that stops requiring a prior drive job row draft → in_progress stops being safe: a live hand session gets an agent dropped into the worktree it is working in.
Reporting merged from applyMergeMarker when the stamp did not move The audit trail grows a corrected note beside a timestamp an earlier write set, and nobody can see that unmark then mark is the only correction — which itself re-blocks every dependent. The WHERE merged_at IS NULL predicate is what makes the question answerable; RETURNING reports the row AFTER the write and cannot.
Excluding rows with merged_at set from the declared backlog The kernel silently hides an issue whose stamp may be wrong, and the master cannot tell that from an empty backlog. Show the fact; do not take the decision.
Dropping the live-job or running-run arm from detectOwedCloses A reopened issue carries the mark of its first landing, so the alarm fires on every issue that has ever shipped anything.

The half that is not in this repo

forge guide contract developed ships from github.com/SidCorp-co/forge-plugin and still describes the mark as earned by “the merged mark with its commit and the base it landed on”. That is the evidence promise this flow removes from the status, and nothing in this repo gates the pair. Reported to that project; until it lands, a driver session reads two definitions and this page is the one core enforces.
