deploy-build-provenance — how a running instance comes to name the commit it was built from

One value moves here: the commit SHA, from a git push to two places a person can read it — GET /version and a Sentry release. coolify-deploy-controls owns how a deploy is triggered, stopped and undone; this file owns what the deploy carries, and every hop at which the answer can become null. It is the flow release-gate condition 4 is read against: the deploy is live and healthy, with SOURCE_COMMIT matching that merge.

That is the honest answer and the one release-gate condition 4 must read as no — never as a pass.

The workflow exits 0 — it is not a gate and the merge has already happened.
The Sentry organisation has no repository integration for SidCorp-co/forgeReleases are created; set-commits --auto fails.The workflow goes red on main, naming it. Deliberately loud: the alternative is a green run that registered nothing.
The commit is injected at build time and never read from git at runtime. Both images carry no .git — pnpm deploy materialises core's app tree and Next's standalone output copies a server bundle — so a git rev-parse placed in either would answer nothing on the one machine that matters and succeed on every box it was tested on. That asymmetry, not tidiness, is why the value arrives as a build argument.
A missing SHA is reported as missing, and that is a feature of the design rather than a shortfall. release-gate condition 4 is a gate: it decides whether an agent may call a deploy verified. A placeholder, an empty string or unknown in that field would make the condition pass on a deploy nobody can identify, which is a worse position than the gap it replaces — the gap at least announced itself. So the single reader accepts 7 to 40 hexadecimal digits and answers null to everything else, and null is a legitimate final answer that a caller must handle as no.
Two deploys are distinguishable from outside the box; two restarts of one deploy are not, and should not be. The value is frozen into the image, so every container from one build reports one SHA however many times it is restarted — which is the point: the field names the code that is running, and uptimeSeconds beside it names the process. Reading them together tells an operator which build, since when. Reading either alone answers only half of what an operator asked.
