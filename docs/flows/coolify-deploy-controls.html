coolify-deploy-controls — stopping a deploy, undoing one, and knowing what a target is

Forge calls four of Coolify’s operations to deploy. This is what the other three controls do and, more usefully, everywhere each one refuses. Owners: packages/core/src/integrations/coolify/client.ts (the HTTP surface and its ability table), packages/core/src/integrations/coolify/controls.ts (the refusals and the audit row), packages/core/src/integrations/coolify/confirm.ts (the poll that settles both).

A rollback and a cancel change production exactly as a deploy does, so they pass the same gate. prodActionNeedsHumanConfirm is the only writer of that rule: against a prod binding all three park for a human unless the project set pipelineConfig.autoProdDeploy. A second copy of the branch is how one of the three ends up weaker than the other two.

Rollback — four refusals before Coolify is called once

Refusal 3 is Forge’s, not Coolify’s. ApplicationsController::rollback_by_uuid runs validateGitRef on the string and queues the build — it never checks the tag against its own rollback-image list. And rollback_images catches its own failure and answers 200 with {current:null, images:[]}, so an unreachable server is byte-identical to a clean one. That is why an empty list refuses too: the read that proves least must not be the read that lets everything through.

A deploy target, before and after

A target used to be a resourceUuid copied out of another browser tab, with nothing in Forge able to say whether it was the application the operator meant. GET /api/v1/applications makes it a pick-list, and one call resolves every bound target of a binding: a uuid Coolify does not list comes back found:false and renders as a refusal in settings rather than as an ordinary row. The picker takes either a saved binding or the credential still in the create form — without the second, the list would arrive one save after the moment the transcription happens.
