agent-execution-session-turns — one session, many turns

What happens between a claude process starting and the job it belongs to finishing — which is no longer the same event. Since ISS-873 phase 6 there is exactly one process model: stdin is a pipe, the prompt is a message on it, and the process outlives the turn that started it.

The one thing to take away. A turn ending and a job ending are different events, and the runner cannot tell them apart on its own. The park is an issue-status move the driver made over MCP during the turn, so only core knows. The runner asks (GET /jobs/:id/turn-verdict) and fails closed to "the job ended" — a wrong "ended" finishes a job that is retryable, a wrong "did not end" wedges the box's only slot.

How an answer reaches a session that is still alive

This is the whole point of the change: under the deleted one-shot model the process was gone before anyone could reply, so a parked question waited on a human with nothing to wake.

sequenceDiagram
  actor H as Human
  participant C as core
  participant R as runner
  participant S as claude session
  S->>C: issue → needs_info (over MCP, mid-turn)
  S->>R: {type:result} ends the TURN
  R->>C: GET /jobs/:id/turn-verdict
  C-->>R: {done:false}
  R->>C: StateChanged("awaiting_input")
  Note over R,S: session stays resident, holding its slot
  H->>C: comment on the parked issue
  C->>R: session.send {kind:"answer", jobId, sessionId}
  R-->>C: delivered  (or gone — silence reads as unknown, and no caller may act on it)
  R->>S: the answer, written on the open stdin
  S->>R: next turn runs with the SAME context
  R->>C: applied (seq, turn) — reported from the turn that CONSUMED it, not from the write
Why applied is not reported at the write. A message written to a session that then dies was never read by the model. Core stands its durable inbox path down on the applied report alone, so reporting at the write would retire a question nobody answered.

Three things that look like print residue and are not

ISS-873 phase 6 listed these for deletion. Each was kept, and the reason is the same in all three: they are shared machinery the issue attributed to the mode.

KeptWhy it survives print
The 25s synthetic progress beat It has two jobs and only one was print's. The other keeps a long silent step (docker build, E2E) off the 3-minute heartbeat hop — and loop-monitor.ts exempts runtime_state = 'awaiting_input' and nothing else, so a session declaring working through a 15-minute build is on exactly the clock a one-shot process was. Deleting it also moves core's park clock from "time since the runner went quiet" to "time since the park", which is precisely the race the 5-minute grace exists to prevent.
RESULT_EXIT_GRACE It is a bounded wait for the stdout reader, not a kill, and the select holding it is entered only once the turn loop has returned with the reader still live — a reachable state, by the race below.
The job-level outcome derivation
result_seen · succeeded · result_error · per-job num_turns		 It is the session-failure path. duplex_turns selects over the result notify and reader-EOF, and tokio::select! picks randomly among ready branches — so a process exiting immediately after its final result can return through the EOF arm with that result never consumed and reset_turn never run. The job then reaches exit unreported with succeeded == Some(true), and this derivation is the only thing that reports it finished.

Where it goes wrong

FailureWhereWhat an operator sees
Every session permit on the box is heldacquire_session_permit, after the repo lock is released session_permit_saturated: all N permits on this box held after 600s → cause box_session_saturated, action failover. A parked session keeps its permit until residency ends, so this is what capacity pressure looks like.
A malformed line written to stdinthe CLI nothing. The process stays alive with nothing to answer and the turn hangs until the job timeout, with no diagnosis anywhere. The envelope is exact and the CLI rejects a bare string.
Core unreachable at the turn verdictturn_is_job_end the turn is treated as the job's end. Unreachable core, a 5xx, a renamed key and an unparseable body all answer the same way, deliberately.
The checkout moved under a resident sessionmoved_under_us the move is announced in-band. This is the one failure "I verified by reading the files" cannot catch — a stale checkout makes file contents and git log agree with each other.
A replayed user message read as a real one--replay-user-messages the prompt persisted twice. Replays come back as type:"user" with isReplay:true; chat's parser keys on assistant so it is inert there, and any future reader of user turns must skip them.
