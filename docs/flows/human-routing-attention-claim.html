human-routing-attention-claim — how a status becomes the claim "a human is needed", and the four surfaces that read it

One kernel column, issues.status, and four independent readers that each turn it into a sentence addressed to a person. This file owns the claim: which statuses mean somebody is owed an answer, where that decision is declared, and every hop that used to re-decide it on its own. The sibling flow issue-status-placement owns what a status is allowed to be; this one owns what it is allowed to say. Owner of the decision: packages/contracts/src/issue-vocabulary.ts.

Who is owed what, per status

The kernel enum has three non-terminal statuses in which no session is running. They are not interchangeable, and the difference is the whole of this flow:

StatusWho owes whomIs it a question for a person?How it is left
needs_infothe agent asked; a person owes an answeryesa comment wakes it — pipeline/answer-resume.ts
waitingblocked on a decision or a resource a person holdsyesa person transitions it; a comment does not wake it
on_holdnobody — the work was paused on purposenoan operator resumes it when they choose to
Why the third row is the one that breaks things. on_hold is not mostly written by a person deciding to pause. It is written by cancel, whose parkIssue flag defaults to true (packages/core/src/pipeline/runs-control.ts), so every duplicate run stopped by a dispatcher parks its issue. Any reader that folds on_hold in with the two above therefore emits one false "a human is needed" per cancellation, at whatever rate the dispatcher happens to cancel. Measured 2026-09-07: 3 cancels on ISS-932/933/964 produced 3 rows and 0 questions. ISS-970 was itself parked by that default 26 seconds after it was filed, and spent five hours in the bucket it was filed to empty.

The one hop that is a copy, and what holds it

packages/core may not value-import @forge/contracts: that package is absent from the production image, so a value import compiles green and then crashes at boot (core/src/contracts-runtime-boundary.test.ts, ISS-510). So AWAITING_INPUT_STATUSES is a hand-written mirror of the axis rather than a read of it, and the mirror is the hop that can drift in silence.

What stands between that and drift: packages/core/src/me/attention-parity.test.ts compares the core tuple against statusesForLabels('needs_human') — a value import of contracts, which is sanctioned in a test because test files never reach dist. It is the same arrangement core/src/pipeline/failure-causes-parity.test.ts uses for the failure taxonomy. Delete that test and the two sides can disagree with nothing failing, which is the state ISS-970 found them in.

Two readers this flow deliberately does not unify

  • notifications/notify-transitions.ts keeps its own NOTIFY_ON_STATUS set, and it is not the awaiting-input set: waiting notifies and needs_info does not, which is the inversion docs/proposals/autonomous-session-pooling.md recorded. A notification is a push at a moment; a bucket is a list that must still be true tomorrow. Merging them would make one of the two wrong.
  • projects/health-routes.ts#BLOCKED_STATUSES counts on_hold and needs_info into a KPI named blockers. It claims nothing about a human and is addressed to nobody, so it is a different question and keeps a different list.
