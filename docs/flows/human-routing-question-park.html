human-routing-question-park — how a question reaches a person once the process is gone, and how the answer gets a run restarted

The episode a park is: the agent asks and exits, the row waits with no time limit, a person answers whenever they answer, and something else entirely restarts the work. Nothing holds a socket open across it, and nothing holds a runner slot. The sibling flow agent-execution-blocked-branch owns which branch is taken; this one owns what happens after the human branch is. Owner of the decision: the four typed columns on the box's ledger (incarnation, work, blocker_kind, resume_id).

Asking is a declaration, not a call. The session writes the question and exits; nothing blocks waiting for a reply. So the answer cannot be delivered to it — it is read back off the row. With the websocket down for the whole episode nothing is lost but latency.
The kill comes after the ledger write, never before. A process killed first leaves the run reading live behind a dead pid — the one state the four columns exist to make impossible. Core is told last because it is the only step that may fail for free.

The four states, and why one status string cannot hold them

incarnation × workWhat is trueWho is holding what
live × runnablean agent is workingprocess, worktree, lease
live × blockedbounded wait — machine or peerprocess, worktree, lease
exited × blockedparked: a person owes an answerworktree, lease, resume_id — no process
exited × runnableanswered, and nothing has restarted itworktree, lease — owed a revival

A single status word collapses the middle two into “blocked” and cannot say the last one at all — which is the most stuck a run can be, because it is waiting on nobody. Reading the ledger alone distinguishes waiting from dead with no process inspected, and that is the property the design exists for.

The CAS predicate is work='runnable', and predicating it on blocked is the bug that looks right. An answered park is already runnable — so a CAS on blocked matches zero rows and the run is owed a revival forever. A failed startup returns the row to exited × runnable for the same reason: sent back to blocked it would wait for a second answer nobody sends.

The attempt carries a token and a startup deadline so recovery can tell an attempt on its way to exec from an abandoned one, and may reset only an expired one. Without the deadline, recovery resets the window between the CAS commit and the process registering, and a second wake wins while the first is still spawning.

Where it ends if nobody ever answers

A park waits with no time limit, but not under no clock: the asker sets park_deadline_at under a project ceiling, and expiry closes loudly — ended_reason=unanswered_<n>d, the question stays in the bucket flagged expired rather than being removed, and the worktree is released only after the diff is preserved. A NULL deadline is an unbounded wait and never matches, so the one wait the design says has no limit does not get one silently.

The failure kind is code, chosen for its ACTION and not its English. deriveActionFromKind maps infra to retry, and retrying a job whose park went unanswered puts a second agent on a question still nobody has answered.
