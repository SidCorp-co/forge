knowledge-memory-model-prose — how a model's words become a stored memory, and the one hop that refuses them

Three paths in this repo write prose a model composed straight into memories and knowledge_edges. This is what each one shows the model, what it stores, and where a rendering it invented is dropped instead. Owner: packages/core/src/memory/extraction.ts, packages/core/src/memory/consolidation.ts, packages/core/src/memory/script-guard.ts. The human write — a knowledge upsert and its embedding — is knowledge-memory-skills; nothing on this page touches it.

The three writers and the one gate

Each writer builds a prompt out of rows it has just read, calls callFastModel, and stores what comes back. foreignScriptChars(rendered, source) sits between the parse and the store: it returns the code points in the model's output whose script the prompt's own source never used, and a non-empty answer drops that one item.

What each writer counts as the source, and why the two differ

WriterGuarded outputSource the allowance is computed from
runExtractionForIssue each fact; each (subject, predicate, object, value) edge the issue title and its comments — not the existing-memories block that shares the prompt
runConsolidationForProject create[].content, update[].newContent the whole prompt, existing memories included
reconcileForReleasedIssue contradicted[].evidence the release text and the candidate memories
Extraction is the narrow one on purpose, and it is the asymmetry to preserve. Extraction is where prose enters the store, so it may only license the scripts a human wrote. Let it license the existing-memories block as well and one leaked character licenses the next one, and the store stops being able to correct itself. Consolidation and reconcile only ever rewrite what is already stored, so refusing the scripts of their own inputs would refuse a team's own memory the moment it was consolidated. The cm:guard naming this sits on extraction.ts:refuseForeignScript.
Latin, Common and Inherited are always allowed, and Inherited is the one that is easy to drop. Latin covers precomposed Vietnamese (Ạ–ỹ is Latin Extended Additional) and Common covers digits, punctuation and emoji — but an NFD spelling of the same Vietnamese word is a base letter plus combining marks, which is Script=Inherited. A guard written as a character range passes the NFC spelling and refuses the NFD one, which is the same word.

When it goes wrong

SymptomWhat it is
A fact you expected is missing and the log says refused output in a script its input never used Working as designed. The model wrote a character no comment on the issue used — the ISS-962 defect, where the Cyrillic for "bypass" reached a stored acceptance criterion. The log line carries the offending code points and the first 60 characters.
A legitimately non-Latin memory is refused at extraction The script was in an existing memory but not in the issue's own comments. Extraction reads the human signal only; consolidation, which does see the memories, will carry it.
refused > 0 but the run still reports work done The refusal is per item, not per batch. The clean items of the same response are stored.
Nothing is refused, ever, on a live project Expected. fastModelConfigured() is false without LITELLM_API_URL, and all three writers return skipped: 'disabled' before any prompt is built.
This gate is not the renderer. Core does not translate anything — the tracker's Vietnamese prose is rendered in forge-plugin, before a write reaches this repo. What is here refuses a model's own invented script at the point core stores it; choosing the words, and reading a project's .vi-glossary.json, belong where the text is produced (ISS-962).
