issue-work-comment-thread-read — how a client reads a whole comment thread

One issue's comments are longer than one response, on both transports. This is the walk that reads them all, and every way it goes wrong. The reason it is a flow rather than a signature is that four separate bounds sit between the rows and the caller — a page bound, a response-size budget, the write cap on one body, and the tree builder's refusal to promote an orphan reply — and each one, mishandled, produces a walk that terminates cleanly on an incomplete thread. Owners: packages/core/src/comments/service.ts (the keyset query), packages/core/src/comments/cursor.ts (the token both transports mint), packages/core/src/comments/routes.ts (REST), packages/core/src/mcp/tools/forge-comments.ts with packages/core/src/mcp/tools/list-envelope.ts (MCP), and packages/web-v2/src/lib/api/client.ts (the browser's walk).

The walk

The four bounds, and what each one does to the walk

BoundWhereWhat it boundsWhat it must never bound
page bound?limit / input.limit, default 50, max 200 How many root comments one page carries, each with its whole subtree The thread. A page short of the limit is not the end — nextCursor is.
response-size budgetMAX_RESPONSE_CHARS (38,000) in list-envelope.ts, MCP only Bytes in one MCP page; it sheds whole subtrees from the newest end. The trim item carries the root's id, not the root row — an item holding both the raw row and its serialized twin measures its body twice and sheds at roughly half the declared budget (ISS-958: a 25,235-character thread came back cut to 2 of 7). The thread, and the cursor. The token is minted from the last kept subtree, so the next page resumes at what the caller actually received.
the write capCOMMENT_BODY_MAX_CHARS (64,000) in comments/body-input.ts, every door One comment body, so a typed record of any block count is one write and one read (ISS-958) The read. It is deliberately larger than the page budget: trimToBudget's one-row floor keeps a single over-budget row, so a 64,000-character record comes back whole in a page of its own with a nextCursor to continue.
the tree builder's orphan rulebuildCommentTree in comments/tree.ts Nothing — it drops a reply whose parent is off-page rather than promoting it Anything, once the cursor walks roots. That rule is why it must: paging over comments would silently lose replies whose root fell on the previous page.

Every way it goes wrong

Goes wrongWhat happensWhy that shape was chosen
A cursor the route did not mint Refused — REST 400 BAD_REQUEST, MCP BAD_REQUEST: cursor: … A cursor silently ignored restarts the walk at page one, so a client paging a long thread loops over the same rows forever and reads that as a thread with no end.
The size cap cut an MCP page short A cursor is still returned, naming the last subtree in the response; truncated and truncatedBy: response-size disclose it and the notice's remedy is the cursor The pre-ISS-956 notice said "a higher limit will NOT help — read the full thread in the UI". That was true and left a CLI client with no move at all, which is the whole of the defect.
One comment alone exceeds the whole size budget It is returned anyway — the trim keeps at least one row whenever one matched An empty page under a cursor is a dead end: nothing to resume from and no progress made. A single 20K-character agent report over the budget is ordinary, not pathological.
A comment is written between two page reads It appears on a later page or not at all, never twice Keyset, not offset. A new row lands after the cursor's key, so it can only be ahead of the walk; under OFFSET it would shift every unread row by one and duplicate one per page.
Two roots share a created_at Ordered by id, and the cursor names both halves of the key A timestamp-only cursor either repeats one of them or skips it. Agent-written threads tie routinely.
A token is minted from a JS Date Every page repeats its predecessor's last root — measured at 47 rows read off a 40-comment thread at limit 7 Postgres keeps created_at to the microsecond; a Date holds milliseconds. The token therefore carries the DB's own to_char(… 'US') text and is compared back as ::timestamptz, so nothing rounds on either leg.
hasMore derived from returned < total A walk that never terminates total is a real count() of every comment flat, while a page carries roots — so on a fully walked thread returned < total is still true. hasMore is nextCursor !== null and nothing else, on both transports and in the browser client.
A server that always returns a cursor Refused after 200 pages — apiClientCursorAll throws rather than spinning A browser tab that hangs with no error is worse than a named failure.
?offset= is sent Validated and ignored; the rows are unchanged Pre-existing flat-list clients still send the limit/offset pair, and a contract break would 500-loop them. Keyset paging has no offset to honour.
