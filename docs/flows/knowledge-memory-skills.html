knowledge-memory-skills — something learned is written, found again, and delivered

The path a fact takes from the write that records it to the prompt or the search hit that returns it, and every place it can arrive without a vector. Owner: packages/core/src/knowledge/, packages/core/src/memory/, packages/core/src/embeddings/, packages/core/src/prompt/facts/.

The write, and the row that arrives without a vector

A knowledge upsert embeds inline, and an embeddings outage does not fail it — the row lands with embedding = NULL and is keyword-only until the backfill sweeps it. That is the whole reason a five-minute job exists on the other side.

flowchart TD
  W1["PUT /api/projects/:id/knowledge/:slug
or forge_knowledge action=upsert"] --> W2["knowledge/service.ts:upsertKnowledgeEntry"]
  W2 --> W3["knowledgeEmbedText(title, body)
cut at MAX_EMBED_CHARS"]
  W3 --> W4{"embed() ok?"}
  W4 -- yes --> W5["INSERT … ON CONFLICT (project, slug)
embedding = the new vector"]
  W4 -- "EmbeddingUnavailableError" --> W6["degraded: true
embedding = NULL, body kept"]
  W6 --> W7["memory/embedding-backfill.ts
runEmbeddingBackfill — every 5 min
memories first, then knowledge_entries"]
  W7 -- "re-embeds knowledgeEmbedInput,
the SAME string the upsert used" --> W5
  W5 --> DB[("knowledge_entries
embedding + text_search + ident_search")]
  W6 --> DB
The backfill must embed the string the upsert would have embedded, or a backfilled entry ranks differently from a freshly written one forever. The cm:guard sits on knowledge/service.ts:knowledgeEmbedInput, which is why both callers name that one function rather than rebuilding the text.

Found again — two transports, one service

Search is where the two stores meet. runUnifiedSearch queries each store independently and blends nothing: scores are not comparable across stores, so every hit carries origin and the caller decides. Since ISS-930 it is reachable from both transports, so a client leaving MCP for the REST data plane keeps the capability instead of losing it.

GET /api/projects/:id/knowledge/search is not this route — that path belongs to the /:slug entry handler and answers knowledge entry not found. The method is what keeps the two apart, with no ordering rule to preserve. Six probed paths and their answers are recorded on ISS-930.

Delivered — the half that never searches

An entry marked injection: 'always' is not retrieved at all: it is spliced into the prompt before the agent runs, and only the on_demand ones wait to be asked for.

When it goes wrong

SymptomWhat it is
A newly written entry is never returned by a semantic search It was written during an embeddings outage and carries embedding = NULL. It is keyword-reachable now and vector-reachable within five minutes, when runEmbeddingBackfill next runs. Until 2026-09-05 that sweep read only memories and such an entry stayed vectorless until its body changed.
A search answers 200 with degraded: true The provider was unreachable and the query ran keyword-only. The results are real, just not semantic — not an error, and not something to retry.
A search answers 503 EMBEDDING_UNAVAILABLE The memory arm at strategy: semantic, which does not degrade — search-service.ts degrades hybrid only. A knowledge-scoped search does not reach this path.
GET .../knowledge/search answers knowledge entry not found Working as designed: that is the /:slug handler with the slug search. The search route is a POST.
A CLI off MCP cannot search knowledge at all It predates ISS-930, or it is pinned to a core older than that route. There is deliberately no MCP fallback — a silent second transport is a precedence rule and a report that has to explain which one ran.

Read this before

Adding an argument to knowledge search — the two transports are a cm:edge contract pair and both must take it, or a client migrating between them loses a capability without a single test going red. Changing what the upsert embeds — the backfill embeds the same string and the pair is only visible in ranking, months later. And adding a store to runUnifiedSearch: scores are per-store by construction, so a new one arrives as its own labelled list, never merged into an existing one.
