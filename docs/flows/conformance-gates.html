When a check goes red, whose problem is it

Every check in this repo answers one question: does the code obey the rule? It can answer it only when its tools are on disk and nothing else is using the resources it needs. This is the fork from a check's outcome to the kind of statement it is allowed to make. Owners: scripts/lib/prerequisite.mjs (what a gate needs before it may speak), scripts/verify.mjs (the five marks), packages/core/tests/helpers/scratch-db.ts (per-run database names), packages/runner/crates/forge-runner-core/src/mcp/config.rs (per-run config directory).

A gate must distinguish “I ran and the code is wrong” from “I could not run”, and a failure must name which condition it represents. The two are answers to different questions — one about the repo, one about the machine — and a signal with no field for the difference hands the reader the wrong one in silence. The reader’s usual defence, “a red that survives a serial re-run is real rather than contention”, does not help: every failure on this page survives a serial re-run identically.

Where it went wrong, three times

All three are one defect: a fixed, unowned resource or an unstated prerequisite, reported in a signal with no field for the condition it represents.

The two shapes of the fix

Name the condition, or remove the sharing. Which one applies depends on whether the contention can be designed away.

  • ISS-938 — name it. The prerequisite genuinely is absent, and no amount of design makes tsc appear. So the gate says which prerequisite, and which command installs it, and still exits 2: an unrun gate is no evidence, and no-evidence is never forwarded as a pass. Nothing here goes green that did not go green before.
  • ISS-937 and ISS-939 — remove it. Nothing needs a fixed name for a mutable resource. The template becomes forge_test_tpl_<stamp>_<rand>, the per-job config moves into a directory the process owns, and the collision has nowhere left to happen. Both keep a condition-naming message for what remains: db.ts says this is an ENVIRONMENT condition, not a failure of the code under test when a clone still fails, and container.ts says it when no docker daemon answers.

What has to stay true

RuleBecause
Prerequisites resolve against the filesystem, never against a tool's output text. A missing binary and a genuinely broken import both print Cannot find module. Classifying by message turns a real defect into “could not run” — this bug inverted, and worse, because it goes green.
Preflight runs before the spawn. A checker without its tool produces a sentence about its own subject — archmap: scope matched no files — and once that sentence exists nothing downstream can unsay it.
n/a exits 2, exactly as FAIL does. The change is what the reader is told, never what the gate lets through. A softer exit code would make this an amnesty rather than a correction.
An unmeasurable axis is not level 0. Level 0 means “no checker exists”, a measured fact about the repo. Returning it for an absent binary reported three axes as having lost their gates.
A run drops only the databases it created; the rest leave by age. A reaper that cannot date a database can only reap by prefix, and reaping by prefix is dropping whatever another run is using — ISS-937 again, committed by its own fix. Postgres refusing a plain DROP on a database with sessions is the second defence behind the age cutoff.
The MCP config file name stays stable; only its directory varies. Two tests exist to assert the name is derived from slug and job id rather than randomised. Randomising it to dodge the collision would delete the property under test.
