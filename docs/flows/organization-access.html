organization-access — a principal resolves to what it may touch

One Authorization: Bearer header, from the byte that decides which verifier runs to the project ids the request is fenced to — and every place the answer is refused. Owner: packages/core/src/middleware/{bearer,auth,require-any-auth,require-device,require-pat,pat-rest-surface}.ts, packages/core/src/auth/{pat,pat-format,device-credential,agent-account}.ts, packages/core/src/lib/authz.ts.

The token decides the verifier, and the verifier decides who you are

There is one credential species left. isPatLike() reads the forge_pat_<env>_ prefix and that one test routes the whole request; everything else is tried as a user JWT and nothing else is tried at all. Since ISS-932 a box has no credential of its own either — devices is a registry of machines, and what authenticates on the control plane (/api/devices, /api/jobs, /api/skills, /ws) is an ordinary PAT or AAT whose device_id names the box. So the question a verifier answers is no longer which species is this but what does this one token carry: a device_id makes it a machine, an owner with users.kind = 'agent' makes it an agent, a job:/session: name makes it a piece of pipeline work.

The refusals stay loud in both directions, and they are the point. /mcp refuses a non-PAT bearer naming the credential class; requireDevice refuses a perfectly valid PAT that carries no device_id, naming the class and forge login as the remedy. Neither falls back to the other, and neither reads the token's owner as a stand-in for the box — the device.ownerId fiction, where a machine borrowed a person's whole account, is what this shape exists to remove.

Two questions, and the answer to one is not the answer to the other

actor_type — who OWNS the write. A job or session token is minted under the person the work belongs to, so its writes really are theirs and read as theirs.

agency — who was at the KEYBOARD. Two reads OR'd together, never one: users.kind === 'agent' answers for an AAT, whose owner IS an agent; the token's name prefix answers for job:/session:, which is minted from a HUMAN's jobs.created_by and would read human off the kind alone. This is what the ISS-786/812 evidence gates read. Dropping the name half is wave 4 of ISS-932 and cannot happen while those tokens are minted.

They disagree for exactly the rows those gates exist to catch, and nothing type-checks that a writer keeps them in step. Both are now persisted beside each other: activity_log.actor_agency and kernel_transitions.actor_agency.

When it goes wrong

SymptomWhat actually happened
403 PAT_NOT_PERMITTED on a route that plainly exists The path is not on PAT_ALLOWED_PREFIXES. That is a statement about the ROUTE, not the token: a route resolving no project has nothing for the fence to bite on, so a project-scoped token there would be an account-scoped credential wearing a project label. /api/me/collaborators and /api/me/ops-health are permanently in this class — they fan out over every project the caller can see, and there is deliberately no per-project twin because GET /api/projects/:id/members already is one.
An agent session's MCP calls all 401 at once, on a box that was fine Its .mcp.json carries the box's device token, and /mcp stopped accepting one (ISS-931). The fix is a forge-runner new enough to write the job's own token into the per-job config, which is why the refusal text says so. Core refuses at deploy and a box changes at binary install, so the two are never simultaneous — read this before deploying core ahead of a runner-v* release.
An admin-gated MCP tool 403s this token lacks the admin scope Working as designed, and new since ISS-931. A paired device carried no scopes, so assertPrincipalIsAdmin's scope half was skipped for it and only the project role was asked; a job:/session: token is minted ['read','write']. An operator who wants forge_skills.*, forge_runners writes, forge_config action=update, forge_schedules writes or forge_reconcile from an agent mints a PAT with admin and exports it as the box's $FORGE_PAT. Widening the machine mint instead would restore ambient admin authority, which is the thing ISS-927 removed.
An MCP tool answers NOT_FOUND: project not found or not accessible to a caller who IS a member Then they are not, on the effective role — or the token's projectIds allowlist excludes the project. Fourteen tools moved from assertDeviceOwnerIsMember (which answered FORBIDDEN and never read the allowlist) to assertPrincipalIsMember in ISS-931, so this reads as not-found by design: a 403 would confirm the project exists to a caller who cannot see it.
Every box in the fleet 401s at once, right after a deploy ISS-932 deleted the device credential. A token minted before it is argon2 in devices.token_hash, which core cannot map to a PAT, so there is no backfill and there was never going to be one: each box re-runs forge login once and is issued a PAT (or its project agent's AAT) carrying device_id. The migration refuses to drop those columns while any non-revoked device still holds one, and names the rows, so this should have been read at deploy time rather than discovered here.
A runner's REST call 401s where it used to work Either it is presenting a device token to requireAnyAuth — that branch is gone (ISS-927) — or it holds a PAT with no device_id on a device route, which ISS-932 refuses by name rather than accepting as its owner. An unattended caller holds a real token: job:<id> minted at claim, session:<id> on agent:start, device:<id> at pairing.
A person cannot sign in and the error says the account is an agent Working as designed. users.kind = 'agent' is refused at every entrance that mints a user JWT, and agent-login-refusal.test.ts scans the tree so a fourth entrance cannot be added without one. If a HUMAN's row carries that kind, it was created through POST /api/orgs/:orgId/agents and should be retired there.
A runner's REST call 401s and the token IS a PAT Its work went terminal. Both credentials die with the thing they were minted for, and for a session that is two writers: applyKernelTransition for cancel / sweeper / dispatch failure, and PATCH /api/agent-sessions/:id for the runner's happy path. The second is a direct db.update the kernel chokepoint never sees.
An agent's write shows in the feed as a person's The token's name lost its machine prefix AND its owner is not kind:'agent', so authenticatePat stamped agency: 'human'. Every consumer reads the FAMILY via isMachineTokenName, so a species added to MACHINE_TOKEN_NAME_PREFIXES is covered everywhere at once — and one minted without being added there escapes the PAT cap, the revoke sweep and the evidence gates together. device: joined that family in ISS-932 for exactly those three reasons.
A device principal 403s inside a handler that looked correct Working as designed. Three middlewares verify a device token and none sets userId, so loadProjectAccess(projectId, userId) fails closed unless the handler honours the device principal explicitly and scopes by row.deviceId. Fixing one half of a read/write pair leaves the other half failing closed.

Read this before

Adding a prefix to PAT_ALLOWED_PREFIXES — every entry must be reachable by a PAT today, which is what forces the grant to be made by someone looking at the route, and /api/pat and /api/orgs being absent is the whole reason an agent cannot mint another agent. requireUserOrDevice now HAS a PAT branch (ISS-932) and it resolves a device without setting userId; that list is the only thing keeping a token off GET /api/agent-sessions, which with no projectId returns every session of every visible project with messages[] attached. And minting a new species of machine token — it belongs in MACHINE_TOKEN_NAME_PREFIXES and nowhere else, or it is a credential three separate mechanisms silently disagree about.
