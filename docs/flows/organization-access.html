organization-access — a principal resolves to what it may touch

One Authorization: Bearer header, from the byte that decides which verifier runs to the project ids the request is fenced to — and every place the answer is refused. Owner: packages/core/src/middleware/{bearer,auth,require-any-auth,require-device,require-pat-or-device,pat-rest-surface}.ts, packages/core/src/auth/{pat,pat-format,deviceToken}.ts, packages/core/src/lib/authz.ts.

The token decides the verifier, and the verifier decides who you are

There is no negotiation and no fallback chain worth the name: isPatLike() reads the forge_pat_<env>_ prefix and that one test routes the whole request. Everything else is tried as a user JWT. A device token is verified on the control plane only — the runner's own /api/devices, /api/jobs and /api/skills sibling routers — and since ISS-927 it reaches nothing on the data plane at all.

Two questions, and the answer to one is not the answer to the other

actor_type — who OWNS the write. A job or session token is minted under the person the work belongs to, so its writes really are theirs and read as theirs.

agency — who was at the KEYBOARD. Derived from the token's name prefix, never from which verifier matched. This is what the ISS-786/812 evidence gates read, and it is the only field separating an agent's credential from a person's.

They disagree for exactly the rows those gates exist to catch, and nothing type-checks that a writer keeps them in step. Both are now persisted beside each other: activity_log.actor_agency and kernel_transitions.actor_agency.

When it goes wrong

SymptomWhat actually happened
403 PAT_NOT_PERMITTED on a route that plainly exists The path is not on PAT_ALLOWED_PREFIXES. That is a statement about the ROUTE, not the token: a route resolving no project has nothing for the fence to bite on, so a project-scoped token there would be an account-scoped credential wearing a project label. /api/me/collaborators and /api/me/ops-health are permanently in this class — they fan out over every project the caller can see, and there is deliberately no per-project twin because GET /api/projects/:id/members already is one.
A runner's REST call 401s where it used to work It is presenting a device token to requireAnyAuth. That branch is gone (ISS-927). An unattended caller holds a real token now: job:<id> minted at claim, session:<id> minted on agent:start. If a caller class has neither, mint it one — do not restore the branch.
A runner's REST call 401s and the token IS a PAT Its work went terminal. Both credentials die with the thing they were minted for, and for a session that is two writers: applyKernelTransition for cancel / sweeper / dispatch failure, and PATCH /api/agent-sessions/:id for the runner's happy path. The second is a direct db.update the kernel chokepoint never sees.
An agent's write shows in the feed as a person's The token's name lost its machine prefix, so authenticatePat stamped agency: 'human'. Every consumer reads the FAMILY via isMachineTokenName, so a species added to MACHINE_TOKEN_NAME_PREFIXES is covered everywhere at once — and one minted without being added there escapes the PAT cap, the revoke sweep and the evidence gates together.
A device principal 403s inside a handler that looked correct Working as designed. Four middlewares verify a device token and none sets userId, so loadProjectAccess(projectId, userId) fails closed unless the handler honours the device principal explicitly and scopes by row.deviceId. Fixing one half of a read/write pair leaves the other half failing closed.

Read this before

Adding a prefix to PAT_ALLOWED_PREFIXES — every entry must be reachable by a PAT today, which is what forces the grant to be made by someone looking at the route. Adding a PAT branch to requireUserOrDevice — GET /api/agent-sessions with no projectId returns every session of every visible project with messages[] attached, so that branch needs a project-scoped twin first, not an allowlist entry. And minting a new species of machine token — it belongs in MACHINE_TOKEN_NAME_PREFIXES and nowhere else, or it is a credential three separate mechanisms silently disagree about.
