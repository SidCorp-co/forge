That one test routes the whole request — everything not PAT-shaped is tried as a user JWT and nothing else is tried at all. Since ISS-932 a box has no credential of its own: devices is a registry of machines, and what authenticates is an ordinary PAT or AAT whose device_id names the box.

The direction of the grant default is the whole risk. A token granted nothing reaches every group, and “nothing” has three shapes that must stay one answer: a NULL column, an empty array, and a principal built without the field. The migration writes no values, so on the day the column landed all 26 active human tokens were in the first shape — reading any of them as permissionless would have locked every live integration out at once. Narrowing is opt-in; a non-empty array is the only narrowing there is.

The three gates

  1. patSurfaceCoversthe ROUTE — same answer for every token that exists
  2. scopeForMethodthe METHOD — read or write
  3. patGrantCoversthe CREDENTIAL — the only gate whose answer differs between two valid tokens (ISS-973)

Which is why the first is no longer called patAllowedFor: a name promising “allowed” on a predicate that reads nothing off the principal is how the third gate gets skipped by someone who believes it already ran.

Two questions, one is not the other

actor_type — who OWNS the write. A job or session token is minted under the person the work belongs to, so its writes really are theirs.

agency — who was at the KEYBOARD. Two reads OR'd, never one: users.kind === 'agent' answers for an AAT; the token's name prefix answers for job:/session:, minted from a HUMAN's jobs.created_by and would read human off the kind alone.

They disagree for exactly the rows the ISS-786/812 evidence gates exist to catch, and nothing type-checks that a writer keeps them in step. Both persisted side by side: activity_log.actor_agency, kernel_transitions.actor_agency. Dropping the name half is wave 4 of ISS-932 and cannot happen while those tokens are minted.

403 PAT_PERMISSION_REQUIRED wanting projects:read on a route that plainly reads issues A permission is as coarse as its mount. /api/projects is one prefix and the router under it serves issues, schedules, knowledge, members and jobs, so /api/projects/<id>/issues attributes to projects — which makes projects:read a near-universal read grant and issues:read cover only the four flat mounts. Measured live at b32bdc2d; pinned as a test, with the shape of a fix in docs/proposals/pat-permission-granularity-is-mount-shaped.md.
403 PAT_PERMISSION_REQUIRED on a route another token reaches fine The route is on the surface; this token was granted a narrower set of groups (ISS-973). The refusal names both halves, because a grant set is invisible from the caller's side and a bare “no” makes narrowing a token something nobody does twice. Absence of a grant is every group, never none — so a token never granted anything cannot produce this code.
“Which permission does this route need?” — asked without being refused first Read X-Accepted-Forge-Permissions off the response (ISS-974) — it is on the 200 too, so a caller narrows a token by walking the paths it will use. Two absences are meaningful and different: no header on a 403 PAT_NOT_PERMITTED means no permission covers that path at all; no header on a 200 means the grant fence never ran — a JWT, or a PAT carrying a device_id on a device route, which verifyDeviceCredential answers without reaching beginPatRequest. A browser reads it only because it is in corsMiddleware's exposeHeaders.
403 PAT_NOT_PERMITTED on a route that plainly exists The path belongs to no resource in PAT_PERMISSION_RESOURCES, so it is not in the PAT_ALLOWED_PREFIXES union. A statement about the ROUTE, not the token: a route resolving no project has nothing for the fence to bite on. /api/me/collaborators and /api/me/ops-health are permanently in this class — they fan out over every visible project, and GET /api/projects/:id/members already is the per-project twin.
An agent session's MCP calls all 401 at once, on a box that was fine Its .mcp.json carries the box's device token and /mcp stopped accepting one (ISS-931). The fix is a forge-runner new enough to write the job's own token into the per-job config. Core refuses at deploy and a box changes at binary install, so the two are never simultaneous — read this before deploying core ahead of a runner-v* release.
An admin-gated MCP tool 403s this token lacks the admin scope Working as designed, new since ISS-931. A paired device carried no scopes, so assertPrincipalIsAdmin's scope half was skipped for it; a job:/session: token is minted ['read','write']. An operator who wants forge_skills.*, forge_runners writes, forge_config action=update, forge_schedules writes or forge_reconcile from an agent mints a PAT with admin and exports it as $FORGE_PAT. Widening the machine mint would restore the ambient admin authority ISS-927 removed.
An MCP tool answers NOT_FOUND: project not found or not accessible to a caller who IS a member Then they are not, on the effective role — or the token's projectIds allowlist excludes it. Fourteen tools moved from assertDeviceOwnerIsMember to assertPrincipalIsMember in ISS-931, so this reads as not-found by design: a 403 would confirm the project exists to a caller who cannot see it.
Every box in the fleet 401s at once, right after a deploy ISS-932 deleted the device credential. A token minted before it is argon2 in devices.token_hash, which core cannot map to a PAT, so there is no backfill and never was going to be one: each box re-runs forge login once. The migration refuses to drop those columns while any non-revoked device still holds one, and names the rows — this should have been read at deploy time rather than discovered here.
A runner's REST call 401s where it used to work Either it is presenting a device token to requireAnyAuth — that branch is gone (ISS-927) — or it holds a PAT with no device_id on a device route, which ISS-932 refuses by name rather than accepting as its owner. An unattended caller holds a real token: job:<id> at claim, session:<id> on agent:start, device:<id> at pairing.
A person cannot sign in and the error says the account is an agent Working as designed. users.kind = 'agent' is refused at every entrance that mints a user JWT, and agent-login-refusal.test.ts scans the tree so a fourth entrance cannot be added without one. A HUMAN's row carrying that kind was created through POST /api/orgs/:orgId/agents and should be retired there.
A runner's REST call 401s and the token IS a PAT Its work went terminal. Both credentials die with the thing they were minted for, and for a session that is two writers: applyKernelTransition for cancel / sweeper / dispatch failure, and PATCH /api/agent-sessions/:id for the runner's happy path — a direct db.update the kernel chokepoint never sees.
An agent's write shows in the feed as a person's The token's name lost its machine prefix AND its owner is not kind:'agent', so authenticatePat stamped agency: 'human'. Every consumer reads the FAMILY via isMachineTokenName, so a species added to MACHINE_TOKEN_NAME_PREFIXES is covered everywhere at once — and one minted without being added there escapes the PAT cap, the revoke sweep and the evidence gates together. device: joined that family in ISS-932 for exactly those three reasons.
A device principal 403s inside a handler that looked correct Working as designed. Three middlewares verify a device token and none sets userId, so loadProjectAccess(projectId, userId) fails closed unless the handler honours the device principal explicitly and scopes by row.deviceId. Fixing one half of a read/write pair leaves the other half failing closed.

The moment the token verifies — before any of the three gates is asked — the response is told what the route wanted. Since ISS-974 a REST request whose token verified through beginPatRequest, on a path some permission covers, carries X-Accepted-Forge-Permissions: <resource>:<level> on the 200 as well as on the refusals — a header only on the 403 leaves discovery-by-trial exactly where it was. The name mirrors GitHub's X-Accepted-GitHub-Permissions, and the value is the Forge permission name in the spelling a mint request takes, so it can be pasted rather than translated.

RuleWhy it is that way
Resolved once, by beginPatRequest, from patPermissionWanted That single value goes to the header, to patGrantCovers and to the refusal body's details.wanted. The predicate takes a derived PatPermission and can no longer resolve a path itself — which is what stops the header becoming a second source of truth naming a permission the fence would not have honoured.
A path no permission covers carries no header, never an empty one An empty value would read as “this route requires nothing” on precisely the routes a PAT may never reach.
What earns it is authentication, deliberately not a status code authenticatePat fires onVerified at the instant verifyPat resolves a row, and that callback sets the header — so a token throttled to a 429 is told what the route wanted, while a token that never verified is told nothing. Reading the 429 status as proof of authentication gives the same answer today and hands the permission map to every caller the moment a throttle is added above verifyPat.
Before youKnow this
Widen what a PAT may reach PAT_ALLOWED_PREFIXES is a computed union, not an editable list: the declaration is PAT_PERMISSION_RESOURCES in packages/core/src/auth/pat-permissions.ts, one named resource to the prefixes it covers, and a prefix reaches the union only by belonging to a resource (ISS-972 phase 1). Every entry must still be reachable by a PAT today, which is what forces the grant to be made by someone looking at the route.
Assume /api/pat or /api/orgs could join it Their absence is the whole reason an agent cannot mint another agent.
Touch requireUserOrDevice It now HAS a PAT branch (ISS-932) and resolves a device without setting userId. That declaration is the only thing keeping a token off GET /api/agent-sessions, which with no projectId returns every session of every visible project with messages[] attached.
Mint a new species of machine token It belongs in MACHINE_TOKEN_NAME_PREFIXES and nowhere else, or it is a credential three separate mechanisms silently disagree about.
