1Who is asking — two kinds of caller, nothing else

flowchart TD
  A["a request arrives carrying a credential"] --> B{"is there one?"}
  B -- "no" --> X1["401 — not signed in"]
  B -- "malformed" --> X2["401, and it says the HEADER is wrong
so a client fixes the header
instead of asking the person to log in again"]
  B -- "yes" --> D{"a personal access token,
or a browser session?"}
  D -- "token" --> P1["a TOKEN. It belongs to a person or to an agent,
and it may name the machine it sits on"]
  D -- "session" --> U2["a PERSON, at a keyboard"]
  P1 -- "unknown token" --> X5["401 — invalid"]

A machine has no credential of its own. A box is a registry entry, not a principal: what authenticates is an ordinary token belonging to a person or to a named agent, which merely says which machine it is installed on. So "who did this" always has a real answer.

Refusals stay loud in both directions, and neither surface falls back to the other. A machine is never treated as the person who installed it — that substitution is exactly what this shape removes.

3Three gates, three different questions

flowchart TD
  P4{"Is this ROUTE open to a token at all?
same answer for every token that exists"}
  P4 -- no --> X6["403 — the route answers no token.
It spans every project, so there is nothing
to fence a project-scoped credential on"]
  P4 -- yes --> P5{"Is this a READ or a WRITE,
and may the token do that?"}
  P5 -- no --> X7["403 — read-only token, write attempted"]
  P5 -- yes --> P7{"Was THIS token granted the area
the route belongs to?"}
  P7 -- "granted nothing at all" --> P6
  P7 -- "granted this area" --> P6
  P7 -- "granted only other areas" --> X8["403 — names what the route wanted
AND what the token holds"]
  P6["allowed, and every read below is confined
to the projects the token may see"]

Only the third gate can answer differently for two valid tokens. That is why the first is not called "allowed": a name promising permission, on a check that never looks at the caller, is how the third gate gets skipped by someone who believes it already ran.

Narrowing is opt-in, and that direction is the whole risk. A token granted nothing reaches everything it is otherwise allowed. Reading "granted nothing" as "permitted nothing" would have locked out all 26 active human tokens on the day the feature landed, so the default had to be the permissive one — which means a token is only ever narrowed by someone deliberately narrowing it.

The three gates

  1. The routesame answer for every token that exists
  2. The methodread, or write
  3. The credentialthe only gate whose answer differs between two valid tokens

Two questions, one is not the other

Who OWNS the write. Work started on someone's behalf is written as theirs, because it is theirs.

Who was at the KEYBOARD. A person, or a machine acting with nobody watching.

Both are recorded, side by side, on every write. They disagree for exactly the rows the evidence rules exist to catch — an agent's work claimed as a person's — and nothing but the writer keeps them in step.

When it goes wrong

SymptomWhat actually happened
Refused for lacking projects:read on a route that plainly reads issues A permission is as coarse as the area it sits under. Issues, schedules, knowledge, members and jobs all live under projects, so granting projects:read is close to granting every read, and issues:read covers far less than its name suggests. Known and measured; the fix is a finer split, not a wider grant.
Refused on a route another token reaches fine The route is open; this token was deliberately narrowed. Being granted nothing means everything, so a token nobody ever narrowed cannot produce this refusal.
"Which permission does this route need?" — asked before being refused Every accepted request answers it in a header, not only the refused ones, so a token can be narrowed by walking the paths it will actually use. No answer means one of two things: no permission covers that path at all, or the caller was a person and the fence never ran.
Refused on a route that plainly exists A statement about the ROUTE, not the token. It spans every project the caller can see, so a project-scoped credential has nothing to be fenced against. Permanently the case for the two fleet-wide views; each has a per-project twin that a token can reach.
An agent's calls all fail at once, on a box that was fine It is presenting the machine's old credential, which the agent surface no longer accepts. The box needs a runner new enough to hand each job its own token. The server changes at deploy and the box changes at install, so never deploy the server ahead of the runner release.
An admin-only action is refused for an agent Working as intended. A machine credential is minted able to read and write, never to administer. An operator who wants administrative actions from an agent mints themselves a token carrying that authority and hands it over deliberately — widening the machine mint would restore the ambient admin power this design removed.
"Project not found" to a caller who IS a member They are not a member at the effective role, or the token's project allowlist excludes it. Not-found rather than forbidden is deliberate: forbidden would confirm the project exists to someone who may not see it.
Every box in the fleet fails at once, right after a deploy The machine credential was retired. The old ones cannot be converted, so there is no backfill: each box logs in once. The deploy refuses and names the boxes still holding one rather than taking them dark silently.
A box's call fails where it used to work Either it presents the retired machine credential, or it holds a token that names no machine on a route only a machine may call — refused by name rather than accepted as its owner.
A person cannot sign in and is told the account is an agent Working as intended: an agent account can never be logged into. If a HUMAN's account says agent, it was created through the agent route and should be retired there.
A box's call fails and its credential is valid The work it was issued for is over. Every machine credential dies with the thing it was minted for, and a session can be ended by two different parties — the box finishing, or the system cancelling it.
An agent's write shows in the feed as a person's Its credential is not recognisable as a machine's and its owner is not an agent account, so the write is attributed to a human. Anything minted for a machine must be registered as one, or it escapes the token cap, the revoke sweep and the evidence rules together.
A machine is refused inside a handler that looked correct Working as intended. A machine caller carries no person, so anything written to answer "which projects does this USER have" fails closed. Fixing only the read half of a read/write pair leaves the write half refusing.

Telling a caller what a route wants

Every accepted request carries the permission its route needs, not only the refused ones — a header that appears only on a refusal leaves discovery-by-trial exactly where it was.

RuleWhy
Decided once, and the same value is what the gate then judges Otherwise the header becomes a second answer, free to name a permission the gate would not have honoured.
A route no permission covers carries no header, never an empty one An empty value reads as "this route requires nothing", on exactly the routes a token may never reach.
What earns the header is being authenticated, not the response code A caller throttled for asking too fast still learns what the route wanted; one who never proved who they are learns nothing. Keying it on the code instead agrees today and hands the permission map to everyone the first time a new check lands above authentication.

Before you widen what a token may reach

Before youKnow this
Widen the surface a token may reach It is not an editable list. A route becomes reachable only by being declared part of a named area, and every area must be reachable by a token today — which forces the decision to be made by someone actually looking at the route.
Assume token-minting or org administration could join it Their absence is the whole reason an agent cannot mint another agent.
Loosen what counts as a machine caller It is the only thing keeping a token off the surface that, asked with no project, returns every session of every project the caller can see — with their messages attached.
Mint a new species of machine credential Register it as a machine credential or it is one that the token cap, the revoke sweep and the evidence rules each silently disagree about.
