That one test routes the whole request — everything not PAT-shaped is tried as a user JWT and nothing else is tried at all. Since ISS-932 a box has no credential of its own: devices is a registry of machines, and what authenticates is an ordinary PAT or AAT whose device_id names the box.

The direction of the grant default is the whole risk. A token granted nothing reaches every group, and "nothing" has three shapes that must answer alike: a NULL column, an empty array, a principal built without the field. The migration writes no values, so on the day the column landed all 26 active human tokens were in the first shape. Narrowing is opt-in; a non-empty array is the only narrowing there is.

The three gates

  1. patSurfaceCoversthe ROUTE — same answer for every token that exists
  2. scopeForMethodthe METHOD — read or write
  3. patGrantCoversthe CREDENTIAL — the only gate whose answer differs between two valid tokens (ISS-973)

Which is why the first is no longer patAllowedFor: a name promising "allowed" on a predicate that reads nothing off the principal is how the third gate gets skipped.

Two questions, one is not the other

actor_type — who OWNS the write. A job or session token is minted under the person the work belongs to, so its writes really are theirs.

agency — who was at the KEYBOARD. Two reads OR'd: users.kind === 'agent' for an AAT, the name prefix for job:/session:, which are minted from a human's jobs.created_by and would read human off the kind alone.

They disagree for exactly the rows the ISS-786/812 evidence gates catch, and nothing type-checks that a writer keeps them in step. Both persisted: activity_log.actor_agency, kernel_transitions.actor_agency.

When it goes wrong

SymptomWhat actually happened
403 PAT_PERMISSION_REQUIRED wanting projects:read on a route that plainly reads issues A permission is as coarse as its mount: the router under /api/projects serves issues, schedules, knowledge, members and jobs, so projects:read is a near-universal read grant and issues:read covers only the four flat mounts. Measured at b32bdc2d; fix shape in docs/proposals/pat-permission-granularity-is-mount-shaped.md.
403 PAT_PERMISSION_REQUIRED on a route another token reaches fine The route is on the surface; this token holds a narrower grant set (ISS-973). Absence of a grant is every group, never none — a token never granted anything cannot produce this code.
“Which permission does this route need?” — asked without being refused first Read X-Accepted-Forge-Permissions off the response (ISS-974) — it rides the 200 too. Two absences differ: none on a 403 PAT_NOT_PERMITTED means no permission covers that path at all; none on a 200 means the fence never ran (a JWT, or a PAT with a device_id on a device route).
403 PAT_NOT_PERMITTED on a route that plainly exists The path belongs to no resource in PAT_PERMISSION_RESOURCES. A statement about the ROUTE, not the token — a route resolving no project has nothing for the fence to bite on. /api/me/collaborators and /api/me/ops-health are permanently in this class.
An agent session's MCP calls all 401 at once, on a box that was fine Its .mcp.json carries the box's device token and /mcp stopped accepting one (ISS-931). Needs a forge-runner that writes the job's own token. Core refuses at deploy, a box changes at install — never simultaneous, so do not deploy core ahead of a runner-v*.
An admin-gated MCP tool 403s this token lacks the admin scope By design since ISS-931 — a job:/session: token is minted ['read','write']. For forge_skills.*, forge_runners/forge_config/forge_schedules writes or forge_reconcile, mint a PAT with admin as $FORGE_PAT. Widening the machine mint restores the ambient admin authority ISS-927 removed.
An MCP tool answers NOT_FOUND: project not found or not accessible to a caller who IS a member They are not, on the effective role — or the token's projectIds allowlist excludes it. Not-found by design: a 403 would confirm the project exists to a caller who cannot see it.
Every box in the fleet 401s at once, right after a deploy ISS-932 deleted the device credential. An old token is argon2 in devices.token_hash, unmappable to a PAT, so there is no backfill: each box re-runs forge login once. The migration refuses to drop those columns while a non-revoked device holds one, naming the rows.
A runner's REST call 401s where it used to work Either a device token at requireAnyAuth — that branch is gone (ISS-927) — or a PAT with no device_id on a device route, refused by name (ISS-932). An unattended caller holds a real token: job: at claim, session: on agent:start, device: at pairing.
A person cannot sign in and the error says the account is an agent By design — users.kind = 'agent' is refused at every entrance minting a user JWT, and agent-login-refusal.test.ts scans the tree so a fourth cannot appear. A human's row with that kind was created through POST /api/orgs/:orgId/agents.
A runner's REST call 401s and the token IS a PAT Its work went terminal. Both credentials die with what they were minted for, and a session has two writers: applyKernelTransition, and PATCH /api/agent-sessions/:id — a direct db.update the kernel chokepoint never sees.
An agent's write shows in the feed as a person's The name lost its machine prefix AND the owner is not kind:'agent', so authenticatePat stamped agency:'human'. Every consumer reads the family via isMachineTokenName — a species minted without being added to MACHINE_TOKEN_NAME_PREFIXES escapes the PAT cap, the revoke sweep and the evidence gates together.
A device principal 403s inside a handler that looked correct Three middlewares verify a device token and none sets userId, so loadProjectAccess(projectId, userId) fails closed unless the handler honours the device principal and scopes by row.deviceId. Fixing one half of a read/write pair leaves the other failing closed.

X-Accepted-Forge-Permissions

Since ISS-974 a verified request on a covered path carries X-Accepted-Forge-Permissions: <resource>:<level> on the 200 as well as the refusals — a header only on the 403 leaves discovery-by-trial where it was. The value is the permission name in the spelling a mint request takes.

RuleWhy it is that way
Resolved once, by beginPatRequest, from patPermissionWanted One value feeds the header, patGrantCovers and the refusal's details.wanted. The predicate takes a derived PatPermission and cannot resolve a path itself — which stops the header becoming a second source of truth.
A path no permission covers carries no header, never an empty one An empty value would read as “this route requires nothing” on precisely the routes a PAT may never reach.
What earns it is authentication, deliberately not a status code onVerified fires the instant verifyPat resolves a row, so a token throttled to 429 is told what the route wanted and one that never verified is told nothing. Reading the 429 status as proof of authentication agrees today and hands the permission map to everyone the moment a throttle sits above verifyPat.

Before you widen

Before youKnow this
Widen what a PAT may reach PAT_ALLOWED_PREFIXES is a computed union, not a list: declare in PAT_PERMISSION_RESOURCES (core/src/auth/pat-permissions.ts) and a prefix reaches the union only through a resource (ISS-972). Every entry must be PAT-reachable today.
Assume /api/pat or /api/orgs could join it Their absence is the whole reason an agent cannot mint another agent.
Touch requireUserOrDevice It now has a PAT branch (ISS-932) and resolves a device without setting userId. That declaration is the only thing keeping a token off GET /api/agent-sessions, which with no projectId returns every session of every visible project with messages[].
Mint a new species of machine token It belongs in MACHINE_TOKEN_NAME_PREFIXES and nowhere else, or it is a credential three separate mechanisms silently disagree about.
