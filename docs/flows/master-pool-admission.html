master-pool-admission — what a master may see, and what it may start

The pool answers "what may I claim right now"; the backlog answers "what exists that nobody has decided about yet" — and the design is that they never become one. core/src/devices/{pool,admissible,run-session,pool-routes}.ts · core/src/pipeline/pipeline-config-schema.ts · forge-runner-core/src/daemon/master.rs

One read, two lists

A claimable row is a queued job under a live pipeline_run. A backlog row is an issue at a status declared in pipelineConfig.poolBacklog.statuses — no job, no run, no jobId field. A project that declared nothing gets backlog: []: every project on the fleet but forge-dev.

The master tells the two lists apart itself — since ISS-933 the nudge carries no snapshot, because one typed at a pane is stale by the time the turn reaches it. A master that reads a backlog key as claimable spends its turn on pool claim <issueId> and core answers not_found, naming the job rather than the mistake, so the transcript never says why. An older runner ignores the key and parses items unchanged.

Opening a run — the only way an admissible issue becomes work

Promotion is gone (ISS-933) — a master opens a run session over a GROUP of issues on its own box, and the ledger there refuses a second run over an issue or a worktree. Core learns after the fact.

The ledger row is committed before anything can spawn. That ordering is the deliverable, not an implementation detail: a crash anywhere after it leaves a row recovery can act on, where recording last leaves a live agent in a worktree nothing on the box knows about — measured as pids 334254 and 335001 in one directory.
The admission set is visibility, never dispatch. Admitting a status widens what a master may see; it has never widened what core will start on its own, and after ISS-933 core starts no drive work at all.

Where a contradiction is refused — at the config write, not at dispatch

intakeGate exists so a human moves every arriving issue out of draft; a master that may open runs over drafts is that human. Declaring both is unrepresentable, and the rule lives in the schema so REST and MCP are covered by one copy.

sequenceDiagram
  participant O as operator (UI / MCP / REST)
  participant H as pipeline-config-http.ts
  participant S as pipeline-config-schema.ts
  participant V as pipeline-config-service.ts
  participant D as projects.pipeline_config (jsonb)

  O->>H: PATCH { poolBacklog: { statuses:['draft'] } }
  H->>S: parse the PATCH
  S-->>H: ok — the patch alone breaks no rule
  H->>V: updatePipelineConfig(patch)
  V->>V: merge patch onto the STORED document
  V->>S: assertMergedConfigValid(merged)
  S-->>V: superRefine: intakeGate.enabled && statuses includes 'draft'
  V-->>O: 400 CONFIG_CONFLICT — the schema's own message, naming BOTH settings
  Note over V,D: nothing is written
Validating the patch alone held the rule only against an operator who sent both halves at once, and fell to anyone who sent them one at a time in either order. The merged document is what is validated. A stored config that already fails the schema is not refused: this write did not cause it, and blocking there would answer an unrelated edit with a rule the operator did not break and leave them no edit that succeeds.

Every refusal NAMES what it collided with, and none of them is a fallback. A run refused because another holds its worktree must not quietly get a different directory: an operator told no repo path for <slug> loses ten minutes, one whose run silently used another checkout loses the diff.

Read this before

  • Adding a status to the admissible set — it is derived as issueStatuses minus AUTONOMOUS_DRIVER_STATUSES, never hand-written: a driver status already carries a run and a job.
  • Adding a cross-field rule to pipelineConfig — in the schema, validating the MERGED document, or it holds on one write and falls to two.
  • Adding a key to the pool response — siblings only; a row with no job inside the array the master claims from invites a malformed claim.
  • Adding a cap on how much a master may take — the cm:guard on /api/devices/me/load forbids a computed "you may take N more": batch size is the master's judgement, and a kernel ceiling is the knob this design removed.
