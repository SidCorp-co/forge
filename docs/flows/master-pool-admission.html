master-pool-admission — what a master may see, and what it may start

Two surfaces answer two different questions, and the whole design is that they never become one. The pool answers “what may I claim right now”; the backlog answers “what exists that nobody has decided about yet”. Owner: packages/core/src/devices/ (pool.ts, admissible.ts, run-session.ts, pool-routes.ts), packages/core/src/pipeline/pipeline-config-schema.ts, packages/runner/crates/forge-runner-core/src/daemon/master.rs.

One read, two lists

A claimable row is a queued job under a live pipeline_run. A backlog row is an issue at a status the project declared in pipelineConfig.poolBacklog.statuses — it has no job, no run, and no jobId field at all. A project that declared nothing issues no second query and gets backlog: [], which is every project on the fleet but forge-dev.

The two lists are told apart in the response, and the master reads them itself: since ISS-933 the nudge carries no snapshot of the pool, because a snapshot typed at a pane is already stale by the time the turn reaches it. A master that reads a backlog key as claimable spends its turn on pool claim <issueId>, which core refuses as not_found — and that refusal names the job rather than the mistake, so nothing in the transcript says why. An older runner that has never heard of the key ignores it and keeps parsing items unchanged.

Opening a run — the only way an admissible issue becomes work

Promotion is gone (ISS-933). A master no longer moves an issue to the entry status so core mints a drive job; it opens a run session over a GROUP of issues on its own box, and the ledger there is what refuses a second run over an issue or a worktree. Core learns about it after the fact.

The ledger row is committed before anything can spawn. That ordering is the deliverable, not an implementation detail: a crash anywhere after it leaves a row recovery can act on, where recording last leaves a live agent in a worktree nothing on the box knows about — measured as pids 334254 and 335001 in one directory.
The admission set is visibility, never dispatch. Admitting a status widens what a master may see; it has never widened what core will start on its own, and after ISS-933 core starts no drive work at all.

Where a contradiction is refused — at the config write, not at dispatch

intakeGate exists so a human approves every arriving issue by moving it out of draft. A master that may open runs over drafts is that human. Declaring both is therefore unrepresentable, and the rule lives in the schema so REST and MCP forge_config are both covered by one copy.

sequenceDiagram
  participant O as operator (UI / MCP / REST)
  participant H as pipeline-config-http.ts
  participant S as pipeline-config-schema.ts
  participant V as pipeline-config-service.ts
  participant D as projects.pipeline_config (jsonb)

  O->>H: PATCH { poolBacklog: { statuses:['draft'] } }
  H->>S: parse the PATCH
  S-->>H: ok — the patch alone breaks no rule
  H->>V: updatePipelineConfig(patch)
  V->>V: merge patch onto the STORED document
  V->>S: assertMergedConfigValid(merged)
  S-->>V: superRefine: intakeGate.enabled && statuses includes 'draft'
  V-->>O: 400 CONFIG_CONFLICT — the schema's own message, naming BOTH settings
  Note over V,D: nothing is written
Validating the patch alone held the rule only against an operator who sent both halves at once, and fell to anyone who sent them one at a time in either order. The merged document is what is validated. A stored config that already fails the schema is not refused: this write did not cause it, and blocking there would answer an unrelated edit with a rule the operator did not break and leave them no edit that succeeds.

Every refusal NAMES what it collided with, and none of them is a fallback. A run refused because another holds its worktree must not quietly get a different directory: an operator told no repo path for <slug> loses ten minutes, one whose run silently used another checkout loses the diff.

Read this before

Adding a status to the admissible set — it is derived as issueStatuses minus AUTONOMOUS_DRIVER_STATUSES, never hand-written, because a driver status already carries a run and a job and would offer a row nothing could open a second run over. Adding a cross-field rule to pipelineConfig — put it in the schema and make sure the merged document is what gets validated, or it holds on one write and falls to two. Adding a key to the pool response — siblings only; a row with no job sitting in the array the master claims from invites a malformed claim. And adding a cap on how much a master may take: the cm:guard on /api/devices/me/load forbids a computed “you may take N more”, because batch size is the master's judgement and a ceiling in the kernel is the knob this design removed.
