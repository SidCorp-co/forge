master-pool-admission — what a master may see, and what it may start

Two surfaces answer two different questions, and the whole design is that they never become one. The pool answers “what may I claim right now”; the backlog answers “what exists that nobody has decided about yet”. Owner: packages/core/src/devices/ (pool.ts, backlog.ts, promote.ts, pool-routes.ts), packages/core/src/pipeline/pipeline-config-schema.ts, packages/runner/crates/forge-runner-core/src/daemon/master.rs.

One read, two lists

A claimable row is a queued job under a live pipeline_run. A backlog row is an issue at a status the project declared in pipelineConfig.poolBacklog.statuses — it has no job, no run, and no jobId field at all. A project that declared nothing issues no second query and gets backlog: [], which is every project on the fleet but forge-dev.

The two lists are told apart in the prompt itself, not just in the response. A master that reads a backlog key as claimable spends its turn on pool claim <issueId>, which core refuses as not_found — and that refusal names the job rather than the mistake, so nothing in the transcript says why. An older runner that has never heard of the key ignores it and keeps parsing items unchanged.

Promotion — the only way a backlog row becomes work

Promote does not run anything. It moves the issue to the entry status and lets the dispatch every other caller already uses produce the run and the drive job, then hands back that job's id so the master claims it through the path it was already using. Every refusal is an ordinary outcome on HTTP 200.

The entry gate is checked BEFORE anything moves. That ordering is the invariant, not an optimisation: a gate read after the transition leaves an issue out of draft with no run and nothing explaining why. manual keeps meaning “a human presses Run” — admitting a status widens what a master may see, never what it may decide. Promotion must not be routed through the manual-run path, which bypasses that gate deliberately and for a different reason.

Where a contradiction is refused — at the config write, not at dispatch

intakeGate exists so a human approves every arriving issue by moving it out of draft. A master that may promote drafts is that human. Declaring both is therefore unrepresentable, and the rule lives in the schema so REST and MCP forge_config are both covered by one copy.

sequenceDiagram
  participant O as operator (UI / MCP / REST)
  participant H as pipeline-config-http.ts
  participant S as pipeline-config-schema.ts
  participant V as pipeline-config-service.ts
  participant D as projects.pipeline_config (jsonb)

  O->>H: PATCH { poolBacklog: { statuses:['draft'] } }
  H->>S: parse the PATCH
  S-->>H: ok — the patch alone breaks no rule
  H->>V: updatePipelineConfig(patch)
  V->>V: merge patch onto the STORED document
  V->>S: assertMergedConfigValid(merged)
  S-->>V: superRefine: intakeGate.enabled && statuses includes 'draft'
  V-->>O: 400 CONFIG_CONFLICT — the schema's own message, naming BOTH settings
  Note over V,D: nothing is written
Validating the patch alone held the rule only against an operator who sent both halves at once, and fell to anyone who sent them one at a time in either order. The merged document is what is validated. A stored config that already fails the schema is not refused: this write did not cause it, and blocking there would answer an unrelated edit with a rule the operator did not break and leave them no edit that succeeds.

What each refusal means to an operator

ReasonWhat actually happenedRetry helps?
backlog_disabledThe project declared no poolBacklog.No — a config change
not_in_backlogThe issue is not at an admitted status (it may have moved since the read).No
entry_gatedThe entry stage is disabled or mode:'manual'. The issue did not move.No — a human presses Run
issue_busyA job or open run already exists — usually another master won the race.No, and that is correct
not_foundThis device serves no such project.No — a binding problem
dispatch_failedThe transition landed and the enqueue did not. The detail says whether the status was restored or left with a run for the reconciler.Read the detail first
All six are HTTP 200 with ok:false, the way a refused claim already answers. An entry-gated project and a race lost to another master are both normal; a 4xx would make each look like a broken route and invite a retry loop against a rule that will refuse forever.

Read this before

Adding a status to the admissible set — it is derived as issueStatuses minus AUTONOMOUS_DRIVER_STATUSES, never hand-written, because a driver status already carries a run and a job and would offer a row that can never be promoted. Adding a cross-field rule to pipelineConfig — put it in the schema and make sure the merged document is what gets validated, or it holds on one write and falls to two. Adding a key to the pool response — siblings only; a row with no job sitting in the array the master claims from invites a malformed claim. And adding a cap on how much a master may take: the cm:guard on /api/devices/me/load forbids a computed “you may take N more”, because batch size is the master's judgement and a ceiling in the kernel is the knob this design removed.
