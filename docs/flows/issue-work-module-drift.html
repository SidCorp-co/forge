issue-work-module-drift — how an undeclared coupling becomes a signal, and why it can never fail anything

Two edge sets over one set of nodes, and the difference between them. issue-work-module-attribution owns how an issue acquires the modules this reads; web-v2-module-taxonomy owns the hierarchy this treats as the declaration. This file owns the comparison: which query produces each set, which layer the answer speaks about, and every hop where the report says nothing is declared rather than no drift. Owner: packages/core/src/labels/module-drift.ts, reached through GET /api/projects/:id/modules/drift.

The signal cannot fail anything, and that is a design constraint rather than a default. An undeclared coupling is information: two modules the work keeps linking that nobody wrote down. A gate that failed on it would be satisfied by declaring edges nobody means, and the declaration — the thing the signal measures against — would stop being worth reading within a month. So there is no threshold that 4xx's, no exit code, and no conformance axis. drift is a 200 body an owner acts on, or does not.
The report speaks the module-taxonomy layer, and says so in the payload. layer: 'module-taxonomy' is a field, not a comment, because this repo holds a second module graph at a different granularity: .arch.json's 63 source-path globs (core-labels, web-features), gated by archmap check on the relations axis, and cm:edge annotations on the knowledge axis. An issue is attributed to a product domain, never to a glob, so the observed half can only be computed at the taxonomy layer. This endpoint therefore reads neither of the other two and becomes an authority over neither. Mapping between the layers stays where a project already records it — a module's knowledge node, and docs/modules/<domain>/ — reached from every node in this report through its slug and knowledgeEntryId.
Declared means ancestry, and siblings are answered rather than decided. labels.parent_id is the only module-to-module declaration Forge holds, so two modules are declared connected when one is the other's ancestor: a subtree is declared to hang together. Two children of one parent are not promoted to declared — the taxonomy says they are both parts of something, never that they relate to each other — so their pair stays in undeclared and carries nearestCommonAncestor. That way an owner can tell two cousins under one parent from two unrelated subtrees without the detector having taken that position for them.
knowledge_edges is deliberately not read. It is a free-text (subject, predicate, object) triple store written by LLM memory extraction (memory/extraction.ts), with no module convention in it. Reading it as a module graph would mean inventing that convention, which is the second declared-edge store ISS-951 forbids: a repo that already answers "are these two connected?" twice does not need a third answer that disagrees with both.
count(*) is an issue count only because of a primary key. issue_labels is keyed on (issue_id, label_id), so a grouped pair has exactly one row per issue. Drop that key and every weight in this report silently becomes a junction-row count — which is why the guard naming it sits on the query and not in this file.
