issue-work-comment-body-mandate — how a stage comes to require a component, and how the number that decides it is counted

issue-work-body-render owns how a component body becomes pixels and release-record owns the sibling rule this one is shaped after. This file owns the two hops between them: a comment write consulting a per-stage policy before it is stored, and the count that says whether turning that policy on would refuse anything. It is a flow rather than a function because the decision to mandate is taken outside the code, by a person reading a figure, and the figure is only trustworthy because of where in the write path the stage is recorded. Owners: packages/core/src/body/stage-policy.ts, packages/core/src/body/adoption.ts, packages/core/src/comments/service.ts (insertComment, updateCommentBody), packages/core/src/pipeline/pipeline-config-schema.ts (stageConfigSchema.bodyPolicy), and packages/web-v2/src/features/project-settings/components/body-policy-section.tsx.

Why the stage is stored rather than derived. A drive comment is written while the issue is at open and the issue is closed an hour later. Grouping the metric by the issue's current status would file every one of those under closed and leave open reading empty — which is indistinguishable from nobody adopting. The column is written once, at insert, and an edit never rewrites it: an edit does not move when the comment was written.

Where it still stops

  • Issue descriptions are out. A stage is a thing that writes comments; a description is written once, at create, before the issue has a stage worth naming. The policy and the metric both cover comment bodies only.
  • Kernel-authored comments are out — apply-transition, merge-marker, budget-check and the rest format their own text and insert directly, so they take the markdown column default and store no stage. No stage asked them for a record, so they are neither refused nor counted. steer-session.ts is the exception: a steer goes through insertComment, so it stores a stage and carries the steering principal's own agency — a person reaching into a running agent is exempt, and a master steering through MCP is not.
  • A row written before migration 0221 has stage = null and falls out of every stage rather than into one. The window is forward-looking on purpose.
  • No comment is agent-authored yet. agency comes from the token owner's users.kind, and measured on the forge-beta replica 2026-09-08 02:29Z all 22 users are still human — the agent accounts ISS-932 wave 4 introduced are not provisioned. So the gate refuses nothing and the number counts nothing today. Both are correct, and both stay correct as those accounts land; the two-week adoption floor starts then, not when this shipped.
  • Nothing is mandated anywhere. Which stages should be required is a separate decision per project, each with its own number quoted — the ladder in docs/proposals/body-templates.md §8.
