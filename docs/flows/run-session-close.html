run-session-close — three marks, none of them a report

A run closes on what the world says, never on what it says about itself. Every mark is set by a caller that has just READ the fact back — the setters are named _observed so a caller who has merely finished doing the thing cannot reach one. The measured failure this replaces: a master reported the loop closed having done one and a half of three.

The three marks

flowchart TD
  S{"session terminal?"} -- "core says the session ended" --> S1["session_terminal_at"]
  S -- "no session id AND no pid" --> S1
  S -- "a pid but no session id" --> SU["UNKNOWN — leave it unset"]
  W{"worktree gone?"} -- "the path is absent from disk" --> W1["worktree_gone_at"]
  L{"per issue: lease back?"} -- "the tracker says so on a READ BACK" --> L1["run_issues.lease_returned_at"]
  L -- "the release call returned ok" --> LN["sets NOTHING"]
  S1 --> C{"all three?"}
  W1 --> C
  L1 --> C
  C -- "yes" --> D["closed"]
  C -- "no" --> P["partially closed, and the ledger says WHICH"]
A cheerful response is not evidence. The lease mark comes from asking the tracker again after the release, never from the release returning ok. A stale success is exactly the shape that let a master report a loop it had not closed, and the close function takes NO argument by which a caller could assert a mark — that is what makes “a master's declaration sets none of the three” true by construction rather than by convention.
Per ISSUE, never per run. A run carrying three issues that returned one lease must read as exactly that. One flag for the group makes a partial return indistinguishable from a clean one, which is the whole defect this loop exists to expose.

Who closes it when the master is gone

flowchart LR
  T["daemon sweep · reconcile()"] --> A{"master alive? same boot?"}
  A -- "yes" --> BEAT["beat core — this box still holds this run"]
  A -- "no, or a different boot" --> CL["close the loop from the ledger"]
  CORE["core · run-session-reaper"] --> H{"heartbeat silent 10 min?"}
  H -- "yes" --> REL["fail the session, close the run, NAME the issues freed"]
The beat and the recovery are ONE sweep on purpose. Core reaps a run session that stops beating, so a build that could wire recovery without wiring the beat would reap every healthy run on the box after ten minutes. Split them and nothing but review stands between here and that.
Two triggers, and only the second survives losing power. The local ledger is the fast path and cannot answer for a box that is unreachable — a design in which the unreachable box is the only thing that can release its own work fails however well it handles a dead pane. So core keys on the heartbeat going silent, never on the box reporting its own death.

Why ten minutes, and not the master's three

The daemon's sweep normally runs every 30s but stretches to LIMITED_POLL_INTERVAL (5 min) on a rate-limited box. Ten minutes is two of the SLOWEST beat, not of the fastest: a three-minute bound like the master's would reap a healthy run the moment the box got throttled. A run also holds a worktree and a branch, so taking it back early costs an operator a diff rather than a claim.

What an operator sees on a partial close

StateReads as
session terminal, worktree gone, 3 of 3 leases backclosed — nothing owes anything
session terminal, worktree gone, 1 of 3 leases backpartially closed; the ledger names the two issues still out, and the sweep retries them
worktree still on disknot closed. The mark is unset because the path is THERE, not because anyone failed to report
a pid but no session idunknown, deliberately: a process started whose session this box cannot name. Answering terminal would close the loop over a live agent

Do not

Add a done: bool to the close function — that reopens the exact hole. Give the close a single lease flag for the group. Set a mark from a caller that has finished an action rather than read a fact: the _observed suffix is the reminder, and the only thing enforcing it is that every setter carries it.
