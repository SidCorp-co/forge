metrics-bucketing — a row becomes a point, or silently does not

How one timestamped row reaches one point on a chart, and the one place the answer can be wrong without anything going red. Owner: packages/core/src/metrics/queries.ts, packages/core/src/admin/aggregate-routes.ts.

The bucket key is computed twice, in two languages

A time series here is dense: every bucket in the window appears, whether or not any row landed in it, so a chart plots a continuous line instead of a ragged one. That requires the list of buckets to exist independently of the data — so it is built in JavaScript (bucketTimestamps, bucketBoundaries) — while the counts are grouped in SQL by date_trunc. The two are then joined on string equality of an ISO timestamp.

Nothing checks that the two halves floor to the same instant. They are joined by a map lookup, and a lookup that misses is indistinguishable from a bucket that genuinely had no rows. That is the whole hazard of this flow.

What made the keys differ

date_trunc(unit, ts) on a timestamptz floors in the session timezone, not UTC. The JS half floors in UTC unconditionally. So the two agree only when the database session happens to be UTC — which CI is, and which is why this held green for as long as it did.

Session timezoneA row at 2026-09-06T21:00Z, daily bucketJS keyMatch
UTC2026-09-06T00:00:00Z2026-09-06T00:00:00.000Zyes
Asia/Ho_Chi_Minh2026-09-07T00:00+07 = 2026-09-06T17:00:00Z2026-09-06T00:00:00.000Zno — and on a daily bucket no key ever matches, so the whole series is defaults

The fix is at the query, not at the connection: every bucketed query reads date_trunc(unit, ts AT TIME ZONE 'UTC') AT TIME ZONE 'UTC', which yields the same instant on any session. Setting the session timezone instead is not equivalent — a transaction-mode pooler drops session SETs, and the failure would come back in exactly the silent form, with no line of this code changed to point at.

Why the test reads the source

metrics/bucket-timezone.test.ts asserts the spelling of the SQL rather than running it. That looks weaker than an end-to-end assertion and is the stronger one available here: the failure only exists on a non-UTC session, CI is UTC, so an end-to-end test of this behaviour cannot go red on CI — a green from it would be evidence of nothing. A source assertion goes red in every timezone, and it goes red naming the expression that was reverted.

The reverse also holds and is worth stating: the integration suite is the only place this repo runs against a real Postgres, so a developer box whose cluster is not UTC is the only environment that ever reproduced this. That is where it was found.
