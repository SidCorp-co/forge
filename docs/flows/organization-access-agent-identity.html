An agent's name, its address, and the credential that says it is speaking

three columns, two axes, one thing a revoke may not do

1One string was doing three jobs

flowchart LR
  E["the address a person is registered at"] --> K["the KEY every invitation, reset and sign-in link is matched on
unique across the whole system"]
  E --> A["the ADDRESS typed after an @
unique inside one organization"]
  E --> L["the NAME a person reads
not unique, freely re-typed, accented"]
  K --- N1["stays where it was"]
  A --- N2["moved out: two organizations may each have a @forge-dev,
one organization may not have two"]
  L --- N3["moved out: everybody gets one, people included"]
  classDef ok fill:#e6efe9,stroke:#1f6f4a,color:#14532d
  classDef gone fill:#f6ecef,stroke:#8a3b52,color:#7a2f44
  class K,N1 ok
  class E gone

Until this change an agent's address was recovered by cutting its registered address at the first dot, and nothing stopped two agents in one organization presenting as the same name — one able to act, one not. Nobody of any kind had a name, so every member list, picker and confirmation dialog printed a raw address.

2The name decides nothing, and that is the rule

A name a person can re-type may never be what a permission is looked up by. Whoever takes that name next inherits whatever the previous holder was allowed to do, and nothing in the system would notice. So the name is rendered and never read to decide: not a key, not an address, and no part in working out who an @ refers to. The address is what a mention resolves against, it is unique within the organization, and the database is what refuses a second one rather than a caller remembering to check.

The same rule already governs the table that maps an outside chat username to a Forge person, for the same reason, and that is where this wording comes from.

The credential is shown once, because only a hash of it is kept and there is nothing to read back. Taking every credential away leaves the account and its memberships exactly where they were: that is "stop it acting for now", which is a different act from retiring it.

4Two questions a credential is asked, and only one it can answer

flowchart TD
  C["a request arrives"] --> Q1["WHAT MAY THIS DO?
answered by the memberships of whoever owns the credential"]
  C --> Q2["WHO IS SPEAKING?"]
  Q2 --> S1["signed in through a browser
→ a person, established"]
  Q2 --> S2["a token belonging to an agent account
→ that agent, established"]
  Q2 --> S3["a token belonging to a person
→ NOTHING is established"]
  S3 --> R1["records no claim about who wrote it"]
  S3 --> R2["is treated as a machine wherever a rule has to choose,
so the checks written for machines apply"]
  classDef ok fill:#e6efe9,stroke:#1f6f4a,color:#14532d
  classDef warn fill:#f6ecef,stroke:#8a3b52,color:#7a2f44
  class S1,S2 ok
  class S3 warn
Borrowed authority may act. It may not claim an identity. Most agents run on a person's token, and the old rule read that as "a person is typing" — so every rule written to hold machines to account let through the majority of the machines, and refused the minority that held their own credential. Now a token a person owns claims nothing at all, and where a rule must pick, it picks the careful answer.

One consequence is new ability rather than new refusal: a decision parked because another agent has to settle it can now be settled — by that agent, holding its own credential, and by nothing else. Before, no credential could, because the only test available was the one that was wrong.

5What a revoke may not do

flowchart LR
  RV["an admin removes an agent's authority"] --> B1["it may no longer act — correct, and the point"]
  RV --> B2{"what is the room about?"}
  B2 -- "before: read from the same record that was just removed" --> O1["the room is about nothing"]
  O1 --> O2["a room about nothing is refused to every reader"]
  O2 --> O3["and the last handle may not be taken out,
so nobody can repair it"]
  B2 -- "now: recorded on the room when the agent joined it" --> N1["the room is still about the same project"]
  N1 --> N2["everyone who could read it still can"]
  N1 --> N3["the agent shows as unreachable rather than going silent"]
  classDef bad fill:#f6ecef,stroke:#8a3b52,color:#7a2f44
  classDef ok fill:#e6efe9,stroke:#1f6f4a,color:#14532d
  class O1,O2,O3 bad
  class N1,N2,N3 ok
Removing authority always succeeds, and never closes a room. Two rules that were each right on their own met and made a dead end: an empty room is refused to everybody, and a room's last handle cannot be taken out. What made them meet was reading what a room is about out of the record that says what an agent may do. Those are two questions; they are now two records. The fact was already known at the door — a handle is only let into a room by somebody who holds a role on the project it is joining for — so it is written down there rather than worked out again later.

The same change closes the other half: an agent given a second project later does not quietly widen the rooms it was already sitting in, because each room recorded the project it was joined for.

·What each party may do

org adminsee every agent in the organization, read whether each can act, give a credential, take every credential away, re-type the name.
a personset their own name, in their own words. Nobody else sets it for them.
an agentact with its own credential, within the one project it belongs to. It settles a decision parked on another agent; it never settles one parked on a person.
an ordinary memberread the member list. The agent verbs are refused, and the screen does not offer them.

·What the system refuses, and what it says

a second agent of the same name in one organizationrefused by the database, not by a caller remembering to look.
a person's token settling a decision parked on another agentrefused, naming the credential that would be accepted and where an admin gets one.
an agent settling a decision parked on a personrefused, and told to sign in. It was escalated to a person precisely because a machine should not decide it.
naming a project the agent does not belong torefused by name rather than silently corrected to whichever project it does belong to.

·What the upgrade refuses to paper over

Two agents in one organization that would end up with the same address stop the upgrade, and it names both of them — because the next act is deciding which keeps the name, and naming one does not say what the other is. Nothing is renamed to make the rule fit: whoever is addressing that name is talking to one of the two, and quietly moving it hands them the other.
A room whose agent is already in the broken state above — no project at all — also stops the upgrade by name. It has to be repaired before the room can record what it is about, and the upgrade will not invent an answer.
