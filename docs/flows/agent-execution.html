The master is a resident tmux session, not a per-pass process; its agent_sessions row is the uuid jobs.held_by carries. Taking a job is two acts: prepare takes the hold, start stamps the dispatch and ends it. The daemon assembles the brief — a master holds no device token, so masterPolicy (the project's master-policy fact, outranking the shipped skill) rides /me/runners and needs no runner release to change (ISS-929). The agent stays a daemon child, not a pane, because job_events?sinceSeq is the only signal for an agent that is alive and not progressing.

Rules the shape encodes

  • A new verdict on this path goes above the cc-startup branch in classifyKind — the pre-spawn beat is all deriveCcStartupSignals needs, so anything below it is unreachable.
  • No unbounded wait while holding a lock another job needs. The root lock is per-repo, the permit ceiling per-box; nesting them made one project's claims kill another's queue (ISS-920: 7 repo_lock_timeout in 30 min on codemap).
  • The lock band is a lexical block in dispatch::handle, and ClaudeCodeRunner::start touches nothing in the root. Root work moved back into it re-nests the lock around the permit wait.
  • No release may unwind a dispatch stamp. One that did re-queued two live agents' jobs underneath them (epodsystem, 2026-09-05).
  • The master writes nothing in the checkout it stands in — every agent works in a worktree cut from origin/<base>. That is what makes a detached master safe.
  • REPO_LOCK_WAIT / SESSION_PERMIT_WAIT / PRE_SPAWN_BEAT_BUDGET are derived from each other; the build fails if the ordering breaks.
