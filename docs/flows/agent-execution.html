How a machine takes work, runs it, and stops

a blocked worker is released only by the party that can unblock it

1One worker, many turns — the session outlives the task

flowchart TD
  J["a box takes a piece of work"] --> W["a worker starts, in a workspace of its own"]
  W --> T["it does a turn — thinks, acts, reports"]
  T --> Q{"is there more to do?"}
  Q -->|"yes"| T
  Q -->|"it needs an answer"| PK["it stops and asks. The worker stays alive
so the answer reaches the same one
that asked, with everything it knew"]
  PK --> T
  Q -->|"done, or it died"| E["the worker ends and the box is free"]

A turn ending is not the work ending. Keeping the worker resident across a question is what lets an answer land in the context that raised it — restarting instead would hand the answer to something that never asked.

2When work blocks, who can release it decides what happens

flowchart TD
  B["the work cannot go on"] --> F{"who can unblock it?"}
  F -->|"a person must answer"| H["the box is released — a person may take
hours or days, and holding a machine
idle for that is the whole cost"]
  F -->|"another piece of work"| D["the box is HELD. The wait is short
and measured in minutes"]
  F -->|"a limit was hit"| L["the box is HELD, and retried
on a fixed cadence"]
  F -->|"it simply failed"| X["the box is released, the failure recorded
with what it was doing"]

Only the human branch gives the box back, and that asymmetry is the point: a machine waiting on a machine will be waiting a short time, and a machine waiting on a person will not. Getting this wrong in either direction either wastes a box or loses its place in the work.

What ends a worker

Endingwho decides
The work is finishedthe worker
A person is neededthe worker, and the box is freed
It was cancelleda person
It stopped reportingthe box, after a grace
The box itself diednobody — somebody else closes it later

Only the last one leaves a mess, which is why a grace exists before anybody else may clean up: clearing it early races a worker that may still be alive.

Removing a capability a worker can call

Workers act through a fixed set of named capabilities. Removing one is not a code change that can be made quietly: boxes in the field are running older builds, and a capability that vanishes from under them fails at the moment of use rather than at deploy.

So a removal must be refused by name while any reachable box still expects it. The wrong move — and the one that has to stay impossible — is letting the call fail with a generic error, which tells whoever hits it nothing about what happened or which version they are on.

When it goes wrong

What you seewhat is happeningwhat to do
A box shows as busy but nothing is running on it. A worker died without reporting, and the hold has not expired yet. Wait out the grace. If it never clears, the box lost the ability to report at all — check it can still reach the control plane.
A question was asked but the answer went nowhere. The worker that asked is gone, so there is nothing left holding the context the answer was for. The work has to be restarted; the answer is recorded on the issue and the new worker reads it from there.
Boxes are idle while work waits. Boxes are held behind waits that should have released them — most often a wait on a person classified as a wait on a machine. Check what each held box is waiting for. Anything waiting on a human should have been released.
