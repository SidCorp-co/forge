lifecycle-run-state-operator-surface — a run stops, and a person finds out

Two ways a pipeline_run stops moving, and the two screens that have to say so. lifecycle-pipeline owns how a run and its jobs open, advance and reach terminal without orphans; this file starts where that one ends — at a run that is paused or a step that failed — and follows the row to the sentence a human reads. The test it exists to answer: when nothing is happening, what does the screen say, and can the reader do anything about it from there?

Two questions, two payload fields, and they are not interchangeable. pipelineHealth.waitingOn answers why has this queued step not dispatched; pipelineHealth.pausedRun answers why is the run not running. An issue with no queued job still has the second question, which is exactly the hole ISS-853 closed: the run_not_running gate reaches a paused run only through a queued candidate, and classifyPipelineHealthForIssue returns above that arm when there is none.

Whose resume is promised is the whole of the copy. MACHINE_RESUMED_PAUSE_KINDS is empty in this build and resumeOrphanedPauses frees every kind absent from LIVE_PAUSE_REASON_KINDS on the next sweeper tick, so only two arms are reachable today: an operator's pause, and a retired kind the sweeper is about to clear. A banner that offered Resume run for the second would be asking a person to do a sweep's work; one that stayed silent on the first is the defect ISS-853 was filed for. The branch is taken in core, once, and web-v2 never re-splits the reason string.

Failure → feed: sixteen deaths, however many causes there were

flowchart TB
  A["attempt N fails"] --> RRJ["runs-rollup.ts leftJoin agent_sessions
carries failureCause + failureDetail"]
  RRJ --> RC["resolveFailureCause(raw)"]
  RC -->|"a member of FAILURE_CAUSES"| C1["the cause itself"]
  RC -->|"job_failed · usage_limit · ws-publish-failed"| C2["LEGACY_CAUSE_ALIAS"]
  RC -->|"free text or unknown token"| C3["unclassified — rendered, never hidden"]
  C1 --> SIG
  C2 --> SIG
  C3 --> SIG["signature = jobType · status · cause · outcome · device · detail"]
  SIG -->|"identical to the line above"| FOLD["fold: repeats += 1, positions += N"]
  SIG -->|"anything differs"| NEW["a new line — a device failover or a second cause stays visible"]
  FOLD --> ROW["one line, ×N, the folded positions on a focusable note"]
  NEW --> ROW
The fold is on the whole signature, never on the step. Collapsing by jobType alone is the defect, not the fix: it would hide a device failover and a second cause inside the count. And unclassified is a first-class member with a rendered line — an invisible unclassified rate is how job_failed rotted across 1,787 rows before ISS-877 split it.

What goes wrong, and what the reader sees

FailureWhat the surface doesWhere
The run is paused and the issue's status was never moved The banner names the pause and offers the resume; the issue does not read as healthy derive.ts#deriveBlockerState, first arm
The run is paused and a human is owed an answer (needs_info) The pause wins. The question stays in the comments; "Provide info" would promise a resume the pause forbids same arm, above needs_info
A pause kind core adds after this build shipped Reads as sweeper — calm, no action. The lockstep edge on types.ts is what stops that being wrong for long waiting.ts#PAUSED_RUN_COPY
The resume call fails An error toast with formatApiError; the banner stays, because the pause is still real pipeline/hooks.ts#useRunControl
An attempt failed with a cause this build has no label for unclassified, with its remedy line — counted, never a silent fallback activity.ts#causeOf
An attempt never finished Queued / dispatched / running / held each say what they are; the feed does not go dark activity.ts#openOutcome
Neither surface takes input. VISION §5: the primary surface is a lifecycle a team can audit, not a conversation. Both screens answer with how the record renders — the feed has no text box, and the banner's only control is a verb the API already had.
