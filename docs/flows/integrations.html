Shipping to a provider, and knowing whether it worked

a deploy that builds is not a deploy that serves

1A deploy is only finished once something answers

flowchart TD
  D["a deploy is asked for"] --> B{"did it build?"}
  B -->|"no"| F1["failed, and the old one is still serving"]
  B -->|"yes"| H{"does the new one ANSWER?"}
  H -->|"yes"| OK["deployed. This is the only point
at which that word is true"]
  H -->|"refuses the connection"| R["a reading, not a skip. It built and
cannot serve — that is the case
this gate exists for"]
  H -->|"no answer in time"| R
  R --> U["undo it, back to the last one
known to have served"]

Treating a refused connection as "could not tell" is the failure that makes the whole gate pointless, because that is precisely what a broken deploy looks like. The gate is worth having only if the ambiguous reading is treated as bad news.

2A refused call by a provider means two very different things

flowchart TD
  C["a call to a provider is refused"] --> Q{"which refusal?"}
  Q -->|"it does not know who we are"| A1["the credential is wrong or expired.
Told as: go and re-authorise this integration"]
  Q -->|"it knows us, and says no"| A2["the credential is fine, the permission is not.
Told as: this account lacks access to that thing"]
  A1 --> W["the two must never be worded alike —
one is fixed by re-connecting,
the other by changing permissions,
and doing the wrong one wastes the day"]
  A2 --> W

Every operator instruction this produces is derived from which refusal came back. A provider that returns the wrong one, or a reader that collapses them, sends somebody to re-enter a password that was never the problem.

What can be undone

Controlwhat it does
Stophalts a deploy in flight
Undoputs back the last build known to have served
Automatic undosame, triggered by the gate above

Undo needs a previous build that actually served. On a first deploy there is nothing to go back to, and the honest answer is to refuse rather than to pick something arbitrary.

A running instance should be able to name the commit it was built from

Every service reports which commit it is serving, and that answer is what makes "is the fix live yet?" a question with a real answer rather than a guess from timestamps.

The value has to be stamped in at build time and carried through every hop to the running process. Any hop that drops it turns the answer into unknown — which is not a small loss: it is the difference between verifying a deploy and believing one.

When it goes wrong

What you seewhat is happeningwhat to do
A deploy reports success but the site is down. It built. Nothing checked that it serves, or the check treated a refused connection as inconclusive. Undo to the last build known to have served, then find out why the gate did not fire.
The running version reports an unknown commit. The commit was not stamped at build time, or a hop between the build and the process dropped it. Do not infer the version from deploy timestamps — they are routinely wrong. Fix the stamp.
An integration keeps asking to be re-authorised and it does not help. The refusal is about permissions, not identity, and is being reported as an expired credential. Check what the account may actually reach. Re-connecting cannot fix a permission it never had.
Undo is refused. There is no earlier build recorded as having served. Fix forward. The refusal is correct — rolling back to something unverified is how one outage becomes two.
