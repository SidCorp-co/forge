issue-work-module-rollup-read — how the backlog is counted by module

The read that answers which module is hot, what is open against each and where did the work go this month. issue-work-module-attribution owns how an issue acquires its modules; web-v2-module-taxonomy owns how the taxonomy is authored. This file owns what happens when a reader asks about all modules at once. Owner: packages/core/src/labels/module-rollup.ts, served by GET /api/projects/:id/modules/rollup and rendered by the Issues screen's Modules view (packages/web-v2/src/features/issues/components/module-rollup-view.tsx).

What each bucket promises

FieldMeansWhy it is not something else
ownIssues attributed to this module itself.Separated from inherited so a reader can tell a module that carries the work from one whose children do.
inheritedIssues attributed to a descendant, at any depth, minus any already in own for the same attribution kind.Without the subtraction, an issue that is a secondary on both a parent and its child is counted twice and own + inherited stops being addition.
rollupown + inherited, exactly.It is the number a person means by "the module", and it holds as addition only because inherited already excluded the overlap.
primary vs secondaryTwo blocks, never summed. An issue contributes to its primary module's primary and to each secondary module's secondary.Collapsing them loses the distinction the attribution axis exists for: one issue has exactly one primary and any number of secondaries.
closedawaiting_release, releasing, closed, dropped — the set TERMINAL_FOR_DISPATCH already names.A second definition of "finished" in a counting endpoint is a number that disagrees with the pipeline's own.
recentlyActiveissues.updated_at inside the window.Activity is the only signal every status has; a per-status timeline would be a different flow.
unassignedIssues carrying no module attribution at all.Reported, never dropped and never assigned anywhere: it is how much of the backlog the taxonomy does not cover.

When it goes wrong

What failsWhat the caller seesWhere the reader reads it
The caller is not a member of the project403 FORBIDDEN, before any row is readThe screen's ErrorState with formatApiError and a Retry.
?activeWithinDays outside 1..3650400 BAD_REQUEST naming the fieldSame ErrorState. The bound exists because 0 is a window nothing can fall inside and a huge value is an interval Postgres refuses.
A module's parent_id points at a row that is not a module of this projectSuccess. That module is a root.Its depth is 0. The hierarchy stays reachable rather than dropping a row nobody could then fix.
The taxonomy contains a cycle (only reachable by a writer that bypassed module-service.ts)Success, and the walk terminates.A seen-set bounds both the ordering walk and the descendant walk; a module already emitted is not emitted twice.
There is no second store of module membership, and this read must not create one. Membership is issue_labels joined to kind='module' labels and nothing else. The narrowing happens inside the join condition rather than after it: narrowed afterwards, an issue carrying only a plain label would produce a NULL row of its own, and that row is exactly what the unassigned bucket is read from — so an issue with a plain label and an issue with nothing at all would become indistinguishable.
The read returns attributions, not counts, and the counting happens in TypeScript. A grouped COUNT cannot express identity, and the parent rollup has to know which issues a descendant contributed so it can refuse to count one twice. The row set is one row per (issue, module) attribution plus one per unattributed issue, carrying four small columns.
