The fork that decides whether the flip is countable

Two ways a status changes or a row disappears on jobs, agent_sessions, pipeline_runs: through the application, which stamps a transaction-local marker, or by a hand on a database connection, which cannot. ISS-943 widened ISS-884's fork to any status change on three tables plus deletion — not a new discriminator, just withKernelMarker at a wider set of sites, held up by db/kernel-marker-guard.test.ts.

Two read hops, and which credential each answers. The fan-out answers every project the caller can see, so /api/pipeline is off PAT_ALLOWED_PREFIXES and only a session reaches it — ?projectId= changes nothing, the allowlist judges the route. The project-scoped hop is what an agent or box reads, and until ISS-944 it did not exist.
The marker is set before the write, never after. The trigger is AFTER UPDATE on the row, which fires before applyKernelTransition has inserted its kernel_transitions row — so the trigger cannot look for that row and has to be told. Move the set_config below the UPDATE and every kernel flip this repo performs is charted as manual SQL.
Why the write is wrapped in a transaction. A transaction-local GUC does not survive autocommit, and twenty call sites pass the root db. Before ISS-884 those wrote status and audit row as two commits, so a crash between them left an unaudited terminal flip produced by the audited path.

Where the ruler still stops, deliberately

Two edges of the instrument, not oversights. Both are here because closing them would overcount, which ruins the number exactly as thoroughly as undercounting.
  • No person is named. A psql session carries a database role and an application_name, not a Forge user id, and no reason. direct_sql answers how many and on which issue; it cannot answer who or why.
  • A migration that backfills a status is charged to the metric. A migration is reviewed, merged code, so charging it overcounts — and excluding migrations by application_name would put a spoofable hole in the instrument, which is worse. So the rule is that such a migration stamps the marker itself, stated in 0219's header because nothing can detect the difference. None exists today.
The three ISS-884 called permanent edges, and why they closed. agent_sessions, non-terminal flips and row deletion each needed the marker at more sites, not a different discriminator. Two of the stated reasons were also false: "the retention sweeper deletes jobs legitimately" — jobs/retention-sweeper.ts deletes job_events, and nothing in code deletes a jobs or pipeline_runs row; and the runner's PATCH /:id was invisible to transition-guard.test.ts only because it writes a variable status, which kernel-marker-guard.test.ts catches by reading the .set() shape.
The price of closing them. The session PATCH no longer skips its transaction when the messages array is not mirrored: a marker gated on a runtime condition is one the guard's lexical test cannot see, and exempting that file would exempt exactly the writer whose invisibility left the session class uncounted. Cost: one SELECT set_config per session PATCH.
Manual SQL is never blocked. Sometimes it is the only way to free a stuck fleet, so the trigger only observes — NULL from an AFTER trigger cannot refuse a write. Counting was the deliverable; preventing was explicitly not.
