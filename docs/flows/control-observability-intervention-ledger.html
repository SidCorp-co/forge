intervention ledger — a status flip becomes a number in the north star

Every route by which a job, a session or a run changes status or leaves the database, and which of them the interventions-per-issue metric can see. The question this answers: a person just cancelled something — does the number move, and under what name? Owners: packages/core/src/db/kernel-marker.ts (the marker), packages/core/src/lifecycle/transition.ts (the audited terminal path), packages/core/drizzle/migrations/0217_unaudited_transition_detector.sql and 0219_unaudited_transition_reach.sql (the detector and the view), packages/core/src/metrics/interventions-report.ts (the read, shared by both routes).

The fork that decides whether the flip is countable

There are exactly two ways a status changes, or a row disappears, on jobs, agent_sessions or pipeline_runs: through the application, or by a hand on a database connection. The first stamps a transaction-local marker; the second cannot. Everything below hangs off that one difference.

ISS-884 built that fork for the terminal flip on two tables. ISS-943 widened it to any status change on three, plus row deletion — and the widening was not a new discriminator. Each of the three classes was uncounted because only the TERMINAL writers stamped the marker, so the fix was the stamp at a wider set of sites: withKernelMarker, held up by db/kernel-marker-guard.test.ts.

Two read hops, and which credential each answers. The fan-out answers every project the caller can see, so /api/pipeline is off PAT_ALLOWED_PREFIXES and a session is the only thing that reaches it — adding ?projectId= does not change that, because the allowlist judges the route and never reads the query. The project-scoped hop is the one an agent or a runner box can read, and until ISS-944 it did not exist: the north-star metric was readable from a browser and from nothing else.
The marker is set before the write, never after. The trigger is AFTER UPDATE on the row, which fires before applyKernelTransition has inserted its kernel_transitions row — so the trigger cannot look for that row and has to be told. Move the set_config below the UPDATE and every kernel flip this repo performs is charted as manual SQL.
Why the whole write is wrapped in a transaction. A transaction-local GUC does not survive autocommit, and twenty of the chokepoint's call sites pass the root db. Before ISS-884 those wrote the status and the audit row as two separate commits, so a crash between them left an unaudited terminal flip produced by the audited path — the metric's own instrument creating the hole it was measuring.

Where the ruler still stops, deliberately

Two edges of the instrument, not oversights. Both are here because closing them would overcount, which ruins the number exactly as thoroughly as undercounting.
  • No person is named. A psql session carries a database role and an application_name, not a Forge user id, and no reason. direct_sql answers how many and on which issue; it cannot answer who or why.
  • A migration that backfills a status is charged to the metric. A migration is reviewed, merged code, so charging it overcounts — and excluding migrations by application_name would put a spoofable hole in the instrument, which is worse. So the rule is that such a migration stamps the marker itself, stated in 0219's header because nothing can detect the difference. None exists today.
The three that used to be here, and why they closed. agent_sessions, non-terminal flips and row deletion were all listed as permanent edges by ISS-884. None of them needed a different discriminator; each was uncounted because only the terminal writers stamped the marker. Two of the stated reasons also did not survive contact with the tree, and that is worth keeping rather than quietly deleting: "the retention sweeper deletes jobs legitimately" was false — jobs/retention-sweeper.ts deletes job_events and there is no in-code delete of a jobs or pipeline_runs row anywhere; and the runner's PATCH /:id being a variable status writer made it invisible to transition-guard.test.ts, but kernel-marker-guard.test.ts reads the SHAPE of the .set() argument instead and so catches exactly that writer.
One thing was priced to close them. The session PATCH used to skip its transaction whenever the messages array was not being mirrored, sparing the runner's heartbeat a round-trip. It no longer does: a marker gated on a runtime condition is a marker the guard's lexical enclosure test cannot see, and exempting that one file would have exempted exactly the writer whose invisibility left the whole session class uncounted. The cost is one SELECT set_config per session PATCH.
Manual SQL is never blocked. It is sometimes the only way to free a stuck fleet, so the trigger only observes: it returns NULL from an AFTER trigger and cannot refuse the write. Counting was the deliverable; preventing was explicitly not.
