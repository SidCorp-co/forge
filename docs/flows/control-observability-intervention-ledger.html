intervention ledger — a status flip becomes a number in the north star

Every route by which a job or a run reaches a terminal status, and which of them the interventions-per-issue metric can see. The question this answers: a person just cancelled something — does the number move, and under what name? Owners: packages/core/src/lifecycle/transition.ts (the audited path), packages/core/drizzle/migrations/0217_unaudited_transition_detector.sql (the detector and the view), packages/core/src/pipeline/analytics-routes.ts (the read).

The fork that decides whether the flip is countable

There are exactly two ways a terminal status lands on jobs or pipeline_runs: through the application, or by a hand on a database connection. The first stamps a transaction-local marker; the second cannot. Everything below hangs off that one difference.

The marker is set before the UPDATE, never after. The trigger is AFTER UPDATE on the row, which fires before applyKernelTransition has inserted its kernel_transitions row — so the trigger cannot look for that row and has to be told. Move the set_config below the UPDATE and every kernel flip this repo performs is charted as manual SQL.
Why the whole write is wrapped in a transaction. A transaction-local GUC does not survive autocommit, and twenty of the chokepoint's call sites pass the root db. Before ISS-884 those wrote the status and the audit row as two separate commits, so a crash between them left an unaudited terminal flip produced by the audited path — the metric's own instrument creating the hole it was measuring.

Where the ruler still stops, deliberately

Each of these is excluded because including it would overcount, which ruins the number exactly as thoroughly as undercounting. They are edges of the instrument, not oversights.
  • agent_sessions is not instrumented. The runner's own PATCH /api/agent-sessions/:id writes a session status directly and legitimately, with a variable rather than a literal — so it is invisible to the single-writer guard test too. A trigger there would count every ordinary session completion as an intervention.
  • Non-terminal flips are not detected. queued→dispatched, dispatched→running, a held requeue and a run pause are ordinary code paths that stamp no marker. A hand-written failed→queued re-dispatch is therefore still uncounted; catching it would mean charting every dispatch as manual SQL.
  • Row deletion is not detected. The retention sweeper deletes jobs legitimately.
  • No person is named. A psql session carries a database role and an application_name, not a Forge user id, and no reason. direct_sql answers how many and on which issue; it cannot answer who or why.
Manual SQL is never blocked. It is sometimes the only way to free a stuck fleet, so the trigger only observes: it returns NULL from an AFTER trigger and cannot refuse the write. Counting was the deliverable; preventing was explicitly not.
