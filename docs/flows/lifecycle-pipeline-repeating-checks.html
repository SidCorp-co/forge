What a repeating check does when there is more to look at than one pass can hold

a capped pass that changes nothing never reaches the bottom of the list

1Two kinds of repeating check, and only one of them empties its own list

flowchart TD
  S["a check runs on a timer and finds
more than it can handle in one pass"] --> K{"does acting on an item
take it OFF the list?"}
  K -->|"yes — it ends the item"| R["a repair. Take the oldest handful
each time. The list shrinks, so the
next pass starts further down by itself"]
  K -->|"no — it only tells somebody"| A["a warning. Telling someone changes
nothing about the item, so it is still
on the list next time"]
  R --> RD["everything is reached,
just later than it would have been"]
  A --> AB{"take the oldest handful
every time anyway?"}
  AB -->|"the obvious thing"| BAD["the same handful, forever.
Item 201 is never mentioned
to anyone, at all"]
  AB -->|"what it does now"| GOOD["remember where it stopped and
carry on from there next time,
starting over when it reaches the end"]

This is the whole reason there are two mechanisms instead of one. A capped repair is a delay: it finishes each item it touches, so the list gets shorter and the next pass picks up where the work ran out. A capped warning is a blind spot, because a warning leaves the thing it warned about exactly as it found it — so the cap reads the same page every single time and everything past it is never mentioned. That is worse than the uncapped version it replaced, which at least got to the bottom eventually. Measured: with a plain cap and a list one page longer than the cap, the overflow was surfaced zero times; with the remembered position it is surfaced on the very next pass.

2A pass that ran out of room says so, with the number

flowchart LR
  P["a pass ends"] --> Q{"did it fill its cap?"}
  Q -->|"no"| QUIET["say nothing.
It saw everything there was"]
  Q -->|"yes"| LOUD["record the cap, what it examined,
and where it will resume"]
  LOUD --> WHY["a quiet pass and a full one look
identical from the outside —
both just report what they did"]

Without that line there is no way to tell a calm system from an overwhelmed one: a check that looked at everything and a check that stopped early both come back saying how much they handled. Naming the cap is what turns "it handled 200" into "it handled 200 and there was more". The repairs report which of the four stages filled up, because they are capped together and the one that filled is the one that is behind.

3A check that keeps finding nothing asks less often

flowchart LR
  T["look for queued announcements"] --> F{"anything there?"}
  F -->|"yes"| DO["handle them, and go back to
asking once a second"]
  F -->|"no"| BK["wait twice as long before asking again,
up to eight seconds"]
  BK --> T
  DO --> T

This one ran once a second forever. In practice there was one item waiting and it was one that can never be handled — so every one of roughly 86,400 questions a day stepped over the same stuck item to find nothing. The cost of asking less often is paid only while there is genuinely nothing to do: the first item that appears during a quiet spell waits up to eight seconds instead of one, and the moment anything is handled the check goes straight back to asking every second. A failure counts as something being there, so a subscriber that is struggling is retried promptly rather than more and more slowly.
