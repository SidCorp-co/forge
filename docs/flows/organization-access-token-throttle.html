organization-access-token-throttle

How one Personal Access Token shared by a dispatcher and the agents it runs is metered, why reads and writes are counted apart, and what a 429 tells the client to do. Module: organization-access. Drawn for ISS-961.

Why this flow exists at all

The forge CLI's credential file is per-user, not per-job. So on a box running a dispatching session plus four to six agents, one token carries all of it — every issue read, every comment list, every knowledge search. Until ISS-961 that was one bucket of 600 requests a minute, and a single forge next --why under a wave was answered with twelve rate-limit waits: ordinary reads had spent the budget the writes then queued behind.

The hops

What the 429 carries, and what each part is for

WhereNameWhat a client does with it
headerRetry-AfterSleeps that many seconds, once. The plugin CLI already honours it (src/tracker/rpc.mjs:retryAfter), capped at 60s.
headerX-RateLimit-ResetThe epoch second the window resets — true for the whole window, unlike a delta that moves under a second retry.
headerX-RateLimit-Limit / -RemainingThe ceiling and what is left of the class that was charged, not of the token as a whole.
headerX-RateLimit-ScopeWhich of the two was charged, on every response — so a client can see its read budget draining before it is refused.
bodydetails.retryAfterSecondsThe same number, for a client that reads JSON and not headers.
bodydetails.windowSeconds, .limit, .remainingThe budget in words, so a log line says what was exceeded rather than that something was.
bodydetails.scopeThe one field that says whether to stop entirely. A wave whose reads are exhausted may still write; nothing else in the response tells it so.

Where it refuses, and where it deliberately does not

SituationWhat happensWhy
Token does not verify401, no bucket chargedThe bucket only ever counts tokens verifyPat already accepted, so a guesser never reaches it.
Read budget spent, a write arrivesthe write is servedThe whole point of the split. Before ISS-961 this was a 429.
Three breaches in an hourstill just a 429The auto-revoke that lived here burned four of one user's tokens in a day (2026-09-03) and protected nothing. A 429 here is a throttle and may never escalate.
/mcp body is unparseablecharged write, then the transport reports its own errorThe stricter of the two. An unclassifiable request must not get the larger budget.
A tool this classifier does not knowcharged writeDefault-safe: a newly registered write needs no edit, and a newly registered read degrades to the old 600 rather than escaping the limiter.
A paired box, /ws, the device poolnot metered here at allauth/device-credential.ts is deliberately off this bucket (ISS-932): a daemon does not degrade under a 429, it stops claiming.
Core restartsevery bucket forgetsIn-memory by design — a restart only ever grants a fresh window, never a refusal.

The coupling that is easy to break

mcpRequestClass() must stay mounted above requirePat() in packages/core/src/index.ts. It decides the class; requirePat charges it. Reversed, every MCP call falls back to write and the split stops applying to the one surface it was reported from — and nothing fails loudly, because write is a valid answer. It is declared as a cm:edge ordering at both ends.
The classifier reads a clone of the body. The MCP transport is handed c.req.raw and reads the stream itself, so calling c.req.json() here leaves the transport a used body and every tool call fails with nothing naming the middleware that did it.
