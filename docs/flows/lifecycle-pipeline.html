lifecycle-pipeline

How a run and its jobs open, advance and close without orphans — and what closes the run when the jobs are already done.

The invariant, in both directions

A pipeline_run and its child jobs must reach terminal together. The two directions fail differently and are defended by different code:

  • Forward — an active job under a terminal run. Costs a runner slot: the pool counts it against the box's in-flight cap and no lifecycle event will ever resolve it.
  • Inverse — a running run whose jobs are all terminal. Costs nothing mechanical, which is exactly why it went unnoticed: it makes the UI report work that no box is doing, and every recovery was a hand-driven cancel + transition.

Reading the invariant one way only is how 98 of 114 live runs across 18 projects ended up running with nothing in flight (ISS-923).

Inverse — the jobs finished first

Nothing runs when the LAST job of an open run goes terminal, so the run needs a detector rather than a hook. That detector is a sweeper pass; the terminal write itself still goes through the same closeRun SSOT, so there is never a second writer of a run's terminal status.

  pipeline-sweeper tick (pipeline/sweeper.ts)
        |
        |  ... reapOrphanedOneShotRuns    run has NO jobs, no live session
        |  ... reapOrphanedIssueRuns      backing issue is closed / dropped
        v
  runs-concluded.ts reapConcludedRuns
        |
        |  admits a run only when ALL of:
        |    status = 'running' or 'paused'
        |    it HAS at least one job     (job-less runs go to reapJoblessRuns below)
        |    no job in queued | dispatched | running | held
        |    no job touched within RESULT_QUIET_MINUTES
        |    if 'paused': no agent_session in queued | running | idle
        v
  outcome := last job's status     done -> completed | failed -> failed | cancelled -> cancelled
        |
        v
  runs.ts closeRun(runId, outcome)  -->  cascadeCancelChildJobs  (a no-op: nothing is active)


  runs-concluded.ts reapJoblessRuns          (the ISSUE-kind job-less shape)
        |
        |  admits a run only when ALL of:
        |    kind = 'issue'              (system/interactive go to reapOrphanedOneShotRuns)
        |    status = 'running' or 'paused'
        |    NO jobs at all
        |    started_at older than RESULT_QUIET_MINUTES
        |    no agent_session in queued | running | idle
        v
  outcome := from the run's sessions   a completed one and no failure -> completed
                                       any failure                    -> failed
                                       no session at all              -> cancelled
        |
        v
  runs.ts closeRun(runId, outcome)

The paused arm is narrow on purpose. An operator's hold is a decision no sweeper may undo, so what admits a paused run is not the pause itself but the proof that nothing is left to resume into: every job terminal, an hour of silence, and no session beating. Widen it and the pass starts cancelling deliberate holds.

When it goes wrong

SymptomWhat actually happened
A run sits running for days with no live job The inverse detector did not admit it. Check the four conditions above in order — the usual answer is a job stuck at queued, which is a different defect and must not be fixed by widening this pass.
A run closed completed but its work failed The outcome is read off the last job, so this means the last job was done. A failure earlier in the run that was retried to success is a legitimate completed; a last job at failed closing completed is a real defect.
A run closed while work was still coming Only possible if the next job had not been INSERTed yet. jobs/retry.ts inserts the clone at queued before the delayed enqueue precisely so a backing-off retry always leaves a non-terminal job here.
An operator's paused run was closed It had no live session and every job terminal, so the sweeper judged it unresumable. If the hold was real, the session or the queued job that made it real was missing — that is the defect, not the reap.
The run split into two rows across a gap Expected, not damage. runs.ts openIssueRun opens a fresh run when none is open, which is what makes closing a concluded run safe in the first place.
