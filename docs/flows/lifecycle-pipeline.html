lifecycle-pipeline

What closes a run when its jobs are already done, and what stops it closing while a deploy is unproven.

The invariant, in both directions

A pipeline_run and its child jobs must reach terminal together. The two directions fail differently and are defended by different code:

  • Forward — an active job under a terminal run. Costs a runner slot: the pool counts it against the box's in-flight cap and no lifecycle event will ever resolve it.
  • Inverse — a running run whose jobs are all terminal. Costs nothing mechanical, which is exactly why it went unnoticed: it makes the UI report work that no box is doing, and every recovery was a hand-driven cancel + transition.

Reading the invariant one way only is how 98 of 114 live runs across 18 projects ended up running with nothing in flight (ISS-923).

Inverse — the jobs finished first

Nothing fires when the LAST job of an open run goes terminal, so this half is a detector rather than a hook — but the write still goes through the same closeRun, so a run's terminal status never has a second writer.

The paused arm is narrow on purpose — an operator's hold is a decision no sweeper may undo, so what admits it is not the pause but the proof there is nothing to resume into. Widen it and the pass starts cancelling deliberate holds.

The deploy gate — the one thing that can refuse a close

Every close above asks this first, and only about completed: does the run carry a deploy nobody has heard back from? Before ISS-922 nothing asked — measured 2026-09-06, 50 runs sat completed while their own current_step still read release.deploy.in_flight, and release.deploy.done had never been stamped fleet-wide.

Every hold carries a 30-minute deadlineAt, below RESULT_QUIET_MINUTES (60), so the gate always resolves before the sweeper's window opens and two mechanisms never decide one run. A deferral cannot leak a run: past the deadline the gate answers failed through that same single writer. And the hold write is refused on an already-terminal run — a deploy asked for after its run closed cannot be witnessed by it, so release-coolify.ts logs ERROR rather than stamping a substep it cannot back up.

When it goes wrong

SymptomWhat actually happened
A run sits running for days with no live job The inverse detector did not admit it. Check the four conditions above in order — the usual answer is a job stuck at queued, which is a different defect and must not be fixed by widening this pass.
A run closed completed but its work failed The outcome is read off the last job, so this means the last job was done. A failure earlier in the run that was retried to success is a legitimate completed; a last job at failed closing completed is a real defect.
A run closed while work was still coming Only possible if the next job had not been INSERTed yet. jobs/retry.ts inserts the clone at queued before the delayed enqueue precisely so a backing-off retry always leaves a non-terminal job here.
An operator's paused run was closed It had no live session and every job terminal, so the sweeper judged it unresumable. If the hold was real, the session or the queued job that made it real was missing — that is the defect, not the reap.
A run sits running at release.deploy.in_flight (k/n) Not a leak — k of n deploy targets have reported and the rest have not. It resolves either way within 30 minutes: every target confirms and the run closes, or the deadline passes and it closes failed naming what went unconfirmed.
A run closed failed and every job in it was done The deploy failed, or went unconfirmed past its deadline. current_step names the target and Coolify's reason, and the inbound integration_deliveries row for that deployment_uuid carries the read that decided it.
The run split into two rows across a gap Expected, not damage. runs.ts openIssueRun opens a fresh run when none is open, which is what makes closing a concluded run safe in the first place.
