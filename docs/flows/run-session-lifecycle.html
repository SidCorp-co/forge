run-session-lifecycle — how a group of issues becomes one worktree, one pane, one row

A run session is what replaced the drive job in ISS-933: a master decides some issues are one piece of work and opens ONE session over the group. No job row, no job token, one worktree. The order the four steps happen in is the whole design, so this flow is about the order and about what each refusal says.

The order, and why it is the deliverable

flowchart TD
  M["master decides: ISS-957 + ISS-963 are one piece of work"] --> C["forge-runner pool run --issues ISS-957,ISS-963 --agent grp-957-963"]
  C --> D["daemon control socket · run_open"]
  D --> L{"ledger, ONE transaction"}
  L -- "an issue is held by a live run" --> X1["refused, NAMING the holder"]
  L -- "the worktree path is held by a live run" --> X2["refused BEFORE git touches it"]
  L -- "clear" --> R["runs + run_issues committed"]
  R --> W["git worktree add"]
  W --> S["POST /me/run-sessions — the WHOLE group in one call"]
  S --> P["tmux pane, then pid stamped back"]
  P --> B["the brief typed in: every issue named, the run id for the phase endpoints"]
LEDGER, WORKTREE, SESSION, SPAWN — and reversing any pair breaks something different. Recording first means a crash anywhere after it leaves a row recovery can act on; recording last leaves a live agent in a worktree nothing on the box knows about, which is the measured incident: pids 334254 and 335001 in one directory, 06:12–06:15Z. Opening the core session before the spawn is what lets the close loop read a missing session id as never started rather than as an unknown — reverse those two and a crash in the window leaves a live agent core cannot name.
Both refusals run inside the ledger transaction, before git. A worktree path another live run holds is refused here rather than by git worktree add failing with .worktrees/<name> already exists — the failure that killed ISS-593's first job, arriving from a layer that cannot say which run it collided with.

What the ledger is, and what it refuses to become

ColumnAnswers
run_id, master_session_id, session_idwhose run this is, and the core session that beats for it
worktree_path, pid, boot_idwhere it is working and as what process, under which boot of this box
incarnation, workwhether the PANE is live, and separately whether the WORK is runnable — a waiting run is not a dead one
run_issues(run_id, issue_key, lease_returned_at)membership, many-to-many, so a group of one is a group and a lease returns PER ISSUE
It is a registry, not a queue. A column named cursor, last_event, offset, wake, processed or seq fails the build — those names are how a record of what exists turns into a second dispatcher on the box, racing the one in core.

Two boxes, one issue

The ledger is per box, so it cannot see another box's run. What stops two boxes opening a run over the same issue is core: devices/admissible.ts excludes any issue named in a live run session's pipeline_runs.metadata.runIssues. Delete that clause and each ledger correctly reports no conflict while two agents share one issue.

Do not

Add a second creation path that takes one issue — create_run_group is public and every scalar primitive under it is private, and a source test pins that. Mint a token for a run: it authenticates with the box's own credential and nothing else. Remember the pid from the spawn instead of reading it back from tmux — ensure adopts an existing session as readily as it creates one, so a pid captured only on creation is absent for every adoption, which is the daemon restart residency exists to survive.
