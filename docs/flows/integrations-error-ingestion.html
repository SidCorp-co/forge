An error becomes work — or is refused by name

the default is not to file

1Every error meets the same four questions, and every "no" is spoken aloud

flowchart TD
  P["the error tracker is asked, on a timer,
what is currently broken"] --> C{"does it belong to
a stack we declared?"}
  C -->|"no, or it names none"| RC["refused, and named. Which error,
and which stack it came from —
never a count of how many"]
  C -->|"yes"| S{"is it serious, and still open?"}
  S -->|"no"| RS["refused, and named. How serious
it is, and what we admit"]
  S -->|"we were not told"| RU["refused. Not told is not
the same as not serious"]
  S -->|"yes"| N{"has it hit enough
people, enough times?"}
  N -->|"below what an operator set"| RN["refused, and named. The number
it has, and the number it needed"]
  N -->|"no number was reported"| RZ["refused. A count nobody sent
is not a count of zero"]
  N -->|"yes"| F["filed, unstarted. A person decides
whether it becomes work"]

Every refusal above is written into the run's own record. That is the whole point: a quiet night and a gate that turned away forty errors must not look the same to the person reading it afterwards.

2An error seen again is the same work, never new work

flowchart TD
  A["an error arrives"] --> K{"have we filed this one before?"}
  K -->|"yes"| G{"has it got worse
since we last looked?"}
  K -->|"no"| J["it meets the four questions above"]
  G -->|"yes"| M["one note on the existing item,
carrying the new numbers"]
  G -->|"no"| Q["nothing is said. The numbers are
refreshed and nobody is interrupted"]
  M --> W["the item itself is untouched:
whoever owns it keeps its title,
its notes and wherever they moved it to"]
  Q --> W

The lookup happens before the four questions, and that order is deliberate. An operator who raises the bar today is deciding what becomes work from now on — they are not deciding to go quiet on the things that already are.

3The words an error carries are evidence, never instructions

flowchart TD
  T["an error message — usually containing
whatever a person typed
into the thing that broke"] --> X["characters that hide text,
or reverse how it reads,
are removed as it arrives"]
  X --> Y["it is written into a form
this system wrote: how urgent,
what kind, and where it sits
are decided here and nowhere else"]
  Y --> Z["when a worker is shown it,
it is fenced and labelled
as somebody else's words"]
  Z --> V["so an instruction written
into an error message is read
AS an error message"]

Whoever can break the product can write into this text. Treating it as a report to be quoted — rather than as a form that could fill itself in — is what stops a crash being a way to give orders.

Who decides what

Decisionwhose
How many times, and how many people, before something is filedan operator, on a settings screen — no release needed
Which stacks are watchedwhoever connected the tracker, as named stacks
How often it is askedthe schedule's own timing
Whether a filed item becomes real worka person, always
Its urgency, its kind, its labelsa person. Never the error text

Filed unstarted on purpose. An alert that files something already started can put a machine to work at three in the morning on a fault that flickered once.

Why it is asked on a timer rather than told as it happens

Being told as it happens is faster, and it is lossy: if we are not listening when the message is sent, it is gone for good and nobody knows it existed. Asking on a timer catches up on whatever was missed, because the question is always "what is broken now", not "what changed since".

Being told as it happens is worth adding later — it makes this faster. It cannot replace the asking, because it cannot answer for a stretch when nobody was home.

When it goes wrong

What you seewhat is happeningwhat to do
Nothing is ever filed, and the run reports success. The bar is above everything the tracker is seeing. Each refusal is in the run's record with the number it had and the number it needed. Read the run, compare the two numbers, and move the bar — or accept that nothing there was worth a person's time.
The run fails saying there is nowhere to pull from. No error tracker is connected to this project, or none is declared for it. Connect it. The run fails rather than reporting an empty success, because "nothing was found" and "nothing could be looked at" are different answers.
Errors from a stack that is not ours keep being refused. The declared stack names a different one from the errors arriving, and each refusal names which. Fix the declaration to the name in the refusal. Nothing guesses which stack an error meant.
The same error is filed twice. It should not be: the tracker's own short reference is kept on the item and is what a second sighting is matched on, with the database holding that as a rule rather than a habit. Check whether the two items carry different references — two genuinely different errors can read alike.
An item keeps getting notes with numbers that never change. It should not: a note is added only when the error has got worse. Equal or fewer is a silent refresh. Report it — that is the noise this rule exists to prevent.
