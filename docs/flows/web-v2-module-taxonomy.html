web-v2-module-taxonomy — a module reaches the screen and comes back as an attribution

The browser half of module taxonomy. issue-work-module-attribution owns what the server does with a labels[] write and where it refuses one; this file owns how that write is composed, what the three screens read to compose it, and what the reader is told when the server says no. There is no /modules endpoint anywhere in this flow — every hop rides the labels routes, the issue PATCH, and the issues search.

One fetch serves all three. Core has no ?kind= filter and no modules route, so useProjectModules is useProjectLabels narrowed on kind in the client. Adding a second endpoint would put the Labels tab and the Modules tab on two caches that can disagree about the same row — which one a rename reaches would then depend on which screen you were standing on.

The failure this flow exists to prevent. PATCH /issues/:id replaces the label set wholesale — [] means "clear them all", and the server cannot tell a payload that forgot the issue's plain labels from one that meant to drop them. A picker that sent only its modules would silently delete every bug, ux and regression on the issue, with a success toast. buildModuleLabelWrite (features/issues/hooks.ts) is the single point that merges them back in, and it is the reason that function is exported and unit-tested rather than inlined in the mutation.

Why the module column needed a server change. The search response serialises the raw issues row and joins no labels at all — withCost, withFailureInfo, withPipelineHealth and withAgentSessions were the only hydrations it had. Without withModules the list's Module cell had exactly two options: one GET /issues/:id per row, or no column. The flag is the third (ISS-594).

Where the reader is told something, and where they are not

Server saysScreen shows
CIRCULAR_HIERARCHY"That parent sits under this module — pick one above it." The parent control never offers a descendant, so this only fires on a race with another editor.
PARENT_NOT_MODULE · PARENT_ON_NON_MODULE · INVALID_PARENTToast naming the cause; the row keeps its old parent.
MODULE_IN_USE"Other modules or issues still depend on this one." Raised on demoting a module that is a parent or a primary.
LABEL_IN_USE (409 on delete)"Issues are still tagged with this — remove it from them first." The confirm step fires before the request, so the reader has already agreed to a delete the server then refuses.
PRIMARY_NOT_MODULE · MULTIPLE_PRIMARYToast; the picker stays open with the reader's selection intact.
Project has no modulesNot an error: the picker's EmptyState links to the Modules tab. A picker that rendered an empty list here would be a dead end.
Delete is refused, not confirmed away. DELETE /labels/:id answers 409 LABEL_IN_USE whenever any issue carries the label, so "delete a module that has attributed issues" is not a thing the UI can do behind a confirm — the confirm guards the irreversible case (a module with no issues), and the 409 is what stops the rest. Detaching the module from its issues first is the only path, and the toast says so.
