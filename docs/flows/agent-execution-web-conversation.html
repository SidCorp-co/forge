The Forge UI is the second adapter

ISS-1002 claimed that adding a conversation transport costs four functions and one registration. Rocket.Chat was the first, and a claim with one instance is an assertion. This is the second, and the browser is a stranger enough transport to be a real test of it: it has no server to post to, no backlog of its own, and its speaker is already a Forge user before anything is resolved. Owners: packages/core/src/assistant/conversation-adapter.ts (the four ports), packages/core/src/assistant/conversation-send.ts (the collect, the turn inputs and the recovery drain), packages/core/src/assistant/conversation-routes.ts (the rooms and the send), packages/web-v2/src/features/conversations/ (the screen).

A conversation surface reads the conversation store, and a run surface reads a session. Before this, both read agent_sessions, so what a person opened was a row describing a process on a runner box and what the store recorded was read by nobody. The gate is the count of conversation surfaces that read a session row: it must be zero. A screen whose subject IS a run — the run thread at features/session/components/session-screen.tsx, the sessions index, the pipeline panels — reads a session because a session is what it is about, and keeps every run-shaped verb it had: fork, rerun, regenerate, per-turn edit, cancel.

From pressing enter to an answer

The four functions, and what each is for a browser

PortWhat Rocket.Chat doesWhat the Forge UI does
resolveVenue Reads the room's type off the server and keys the venue on server rid tmid. Takes the room the route already read and authorized. There is no second lookup, because a second lookup could only disagree with the decision that admitted the message.
resolveSpeaker Resolves a chat account against assistant_speaker_links, and can refuse. Cannot refuse. The speaker is the Forge user the session cookie authenticated; a refusal here would be refusing the person who just signed in.
deliver Posts to the room over REST, through the single outbound door. Publishes to each live person's own user: room. Not the project room — a one-to-one conversation in a project room is every member of that project reading somebody else's chat, and it renders identically in the tab that asked.
fetchHistory Fetches the channel or thread backlog the store has never seen. Empty, and that is the answer rather than a stub: the store's own rows are this transport's history, and external-chat.ts already hands them to the model.

Who may read a one-to-one room

A conversation's scope is what it is about — the projects its live handles were added for — and every member of those projects passes the role check. That is the right rule for a channel and the wrong one for one person's chat, so a direct room is read by the people in it and by nobody else, on the list as well as on the read. agent_sessions has had this fence since ISS-522; the conversation store never needed one because nothing read it, and the day a screen did was the day it became a live hole.

The three are different shapes and not different wording, because wording is what a later edit changes without meaning to. features/conversations/types.ts:threadEntries owns the split and types.test.ts fails on a collapse of any two of them.

What the chat surface stopped being able to do

A real loss, stated rather than discovered. The Forge UI chat used to be a Claude Code session on a runner box with the repository checked out. A conversation turn runs in core against the provider with a read-only project toolset: it reads issues, progress, knowledge and memory, and it has no working tree and no shell. The persona says so in its own words, so the same screen cannot answer a question about a file as though it had looked. Six affordances went with the runner — model pick, runner pick, fork, rerun, per-turn edit, regenerate — because each names a run, and a conversation is an append-only log whose appendMessages leaves every row already in it alone. The way back is one function: divertBeforeTurn on the turn inputs, exactly as integrations/rocketchat/turn-inputs.ts uses it for the agent answer mode.
