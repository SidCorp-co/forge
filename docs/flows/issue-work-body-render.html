issue-work-body-render — how a component body becomes pixels, and where it stops being one

An issue description or a comment can be stored two ways: markdown, or html — a body of allowlisted forge-* components. Only the server can tell the two apart, because the scanner and the registry are core-internal and packages/web-v2 has no dependency on @forge/core. This is a flow rather than a function signature because the same bytes take four different routes to the screen depending on who parsed them and when, and three of those routes degrade rather than fail — a body that draws as nothing, as literal <forge-review …> text, or as a card that says less than it should, all return HTTP 200. Owners: packages/core/src/body/prepare.ts (bodyNodes), packages/core/src/body/parse.ts (the scanner), packages/core/src/body/routes.ts (/api/body), packages/core/src/issues/routes.ts (serializeIssue), packages/core/src/comments/tree.ts (buildCommentTree), and packages/web-v2/src/design/patterns/body-view.tsx.

The write, and the preview beside it

The composer never parses. POST /api/body/preview runs the same prepareBody a save runs and hands back the prepared bytes, the warnings and the tree — so the pane draws what would be stored, not what was typed, and a refusal arrives as the kernel's own 400 BODY_INVALID naming the element, the attribute and its legal set. GET /api/body/components is the registry itself, so the insert menu offers exactly what a save accepts.

The failure this prevents: a client-side approximation of the validator. It would disagree with the server on the cases that matter — a mis-nested slot, an attribute outside its enum — and the author would learn about it only from a rejected save with no pane to explain it.
