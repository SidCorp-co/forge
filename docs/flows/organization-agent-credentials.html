organization-agent-credentials — how a machine and a named agent are issued one

An org admin creates an agent, a box is paired, a write is attributed. core/src/orgs/agent-accounts.ts · core/src/auth/{agent-account,agent-login-gate,pat,pat-format}.ts · core/src/devices/{register,credential,pair,login-routes}.ts

An agent is a users row with kind = 'agent', a member of one org and one project. Authorization learns nothing new — effectiveProjectRole and the reads behind it are the same organization_members / project_members rows a person has. Only the flag is new, and it is the seam: the day an agent needs its own table, every reader already asks through one column.

Before it, every machine token borrowed a person's identity — one per job from jobs.created_by, one per unattended session from agent_sessions.user_id. A master agent has no user_id at all, which is why device.ownerId was invented to stand in. Wave 4 deleted both per-work credentials; a box now holds exactly one.

The three refusals that make the flag safe

HoleWhat closes it
An agent row is an unapproved person's account — NULL password, live reset path assertNotAgent at every entrance that mints a user JWT, plus agent-login-refusal.test.ts, which SCANS the tree for callers of signUserToken and fails on one that does not refuse. The failure mode is not a broken entrance, it is a fourth entrance added by somebody who never read the file.
The synthesized address could be claimed or delivered to The local part is random and the domain is agents.forge.invalid. RFC 2606 reserves .invalid so no MX ever resolves it, and users.email being NOT NULL UNIQUE means no person can register it either.
A scoped credential that can mint an unscoped one has no scope Nothing at all: /api/pat and /api/orgs are both absent from PAT_ALLOWED_PREFIXES, so a PAT or AAT reaches neither route. The agent also joins its org as a plain member, which the admin gate on the mint route fails independently. Two refusals, one of them upstream of any role change.

Pairing a box is issuing it a token

sequenceDiagram
  autonumber
  participant CLI as forge-runner
  participant Core as core
  participant Web as browser (org admin)
  participant DB as postgres

  Note over Web,DB: (once, per agent) POST /api/orgs/:orgId/agents
  Web->>Core: handle, projectId
  Core->>Core: assertOrgAccess(orgId, admin)
  Core->>DB: users(kind=agent) + organization_members(member) + project_members
  Core->>DB: mintPat(name=agent:<handle>, boundProjectId)
  Core-->>Web: plaintext, exactly once

  CLI->>Core: POST /devices/login/init (label, platform, machine_id)
  Core-->>CLI: XXX-XXXX, 10 min TTL
  Web->>Core: POST /devices/login/approve (code, agent_id?)
  Core->>Core: agent_id? assertOrgAccess(agent's org, admin)
  Core->>DB: approved_user_id = approver, agent_user_id = the chosen agent
  loop every 2s
    CLI->>Core: GET /devices/login/poll
  end
  Core->>DB: registerDevice(ownerId = agent ?? approver, machine_id)
  Core->>DB: issueDeviceCredential -> PAT(device_id, name=device:<id>)
  Core-->>CLI: device_token = a forge_pat_* string

  Note over CLI,Core: every later call is one species
  CLI->>Core: Bearer forge_pat_… on /ws, /api/devices, /api/jobs
  Core->>Core: verifyDeviceCredential -> row.device_id -> devices row

Two writes, in this order, and neither inside the other's transaction. The pairing code is marked used BEFORE the credential is minted. registerDevice and mintPat run on the ambient db, so a failure between them must leave a spent code and no token — recoverable by asking for another — rather than a live code and a credential already in the wild. Reversed, a pairing secret works twice.

devices.ownerId follows the token's holder, not the approver. When an approval names an agent, the box is registered to that agent. Pointing the row at the person who clicked while the token belongs to the agent would put the two back out of step, which is the state device.ownerId was invented to paper over.

What a token carries, and what each field decides

Field on personal_access_tokensWhat it decides
device_idWhether this token may speak as a machine at all. requireDevice, requireUserOrDevice and the /ws upgrade resolve the box from it; NULL is refused by name and never read as its owner.
bound_project_idThe one project an AAT works on — option A, one AAT one project, so the blast radius of a leak is a project rather than an account.
nameA LABEL, and nothing reads behaviour off it since wave 4. A box's credential is named after its box so a re-pair finds and rotates the same row; a person may hand-mint a token called job:anything and it buys nothing.
device_idWhat keeps a machine's credential off its owner's PAT cap — a property of the credential rather than a convention on its name.
its owner's users.kindagency, and the whole of it. An agent's credential has an agent owner, so the kind answers directly and there is no second term.

When it goes wrong

SymptomWhat actually happened
The deploy aborts naming a list of devices Migration 0215 refusing, as designed. Those boxes still hold a pre-ISS-932 device token, and dropping devices.token_hash under them would take them dark with nothing saying so. Revoke the retired ones, acknowledge the live ones (UPDATE devices SET token_hash = ''), re-run, then forge login on each machine.
A box authenticates /ws but 401s on /api/devices/me/runners Impossible by construction now — both go through verifyDeviceCredential. If it happens, a second resolution path has been added, which is the one thing this flow exists to prevent.
Revoking a device does not stop it Revoking the box and revoking its token are two writes: DELETE /api/devices/:id does both, and verifyDeviceCredential re-checks status as the second defence. A path that flips the status without calling revokeDeviceCredentials leaves a working PAT behind.
An agent's project work 404s Its AAT is bound to one project. That is option A, not a bug — an agent needing a second project is a second agent, and the kind flag is where that decision would be widened.
A retired agent's past writes lost their author They should not have: revokeAgentAccount removes tokens and memberships and never the users row, precisely because activity_log.actor_id and kernel_transitions.actor_id point at it. If the row is gone, something deleted it outside that function.

Read this before

Adding a login entrance — a scanning test fails rather than let you forget. Adding a species to MACHINE_TOKEN_NAME_PREFIXES — one line in auth/pat-format.ts and nowhere else, by design. Giving an agent more than one project — an owner decision option A deferred.
